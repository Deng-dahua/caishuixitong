## 一、审计结论（TL;DR）

| 维度 | 结论 |
|---|---|
| 税务红线库（42 条） | 主线存在、覆盖 9 大域，但**缺 8 类税种/事项**（见 §六） |
| 权威规则库（89 条） | 资产完整、字段齐全，可正常驱动疑点筛查 |

## 三、P0 致命缺陷

### 3.1 三链引擎（线索链/证据链/分析链）完全失效

**位置**：`engine/chain_executor.py:429-433`（`_normalise_rule_id`）、`669-699`（`_build_chain_index` / `_find_chain`）、`590-663`（`run_chains_for_rule`）

**根因**：链索引按 `rule_id` 建，但链定义里根本没有 `rule_id` 字段。

`methodology_canonical_catalog.json` 的 `modules[].clue_paths / evidence_plan / analysis_tests` 经 `fact_rules.load_flat_clues / load_flat_evidence / load_flat_analysis` 扁平化后，每条链只有 `id`（如 `CAN-01-C01`、`CAN-01-E01`、`CAN-01-A01`），**没有 `rule_id`**。

`_build_chain_index` 里：

```python
rid = _normalise_rule_id(item.get("rule_id"))   # item.get("rule_id") → None
if rid is not None: idx[rid] = item             # _normalise_rule_id(None) 返回 ""，不是 None → 恒真
```

`_normalise_rule_id(None)` 走 `str(None or "")` 返回空串 `""`，于是 88 条链全部覆盖到 `idx[""]` 上。

**实测证据**（本审计脚本运行结果）：

```
clue chains: 38 | evidence chains: 25 | analysis chains: 25
index sizes (clue/evid/alc): {'clue': 1, 'evid': 1, 'alc': 1}   # 88 → 3
_find_chain("CAN-01-R01", clue) = None    # 真实 rule_id 查不到
_find_chain("CAN-01-C01", clue) = False   # 链自己的 id 也查不到
```

**后果**：`pipeline.py:2273` 对每个已触发的 rule_id 调 `run_chains_for_rule`，内部 `_find_chain` 恒返回 `None/False`，`results["clue"] = results["evidence"] = results["analysis"] = None`。稽查方法论的核心链资产（「怎么发现的→组织什么证据→主张/反证/裁决」）**完全不参与一键分析**，静默失效、无任何报错。

> 注：`redline_engine.py` 内部另有一套**内联**的 `build_clue_chain / build_evidence_chain / build_argumentation`（第 108–110 行），那是能用的，红线疑点仍能带出线索/证据/论证。失效的是 `chain_executor.py` 这套「JSON 目录驱动」的三链引擎。两者不可混为一谈。

### 3.2 红队证伪四件套 + 跨域协商引擎作用于「被丢弃的中间产物」

**位置**：`engine/pipeline.py:1992-2007`（红队/盲测/幻觉/一致性）、`2363`（`run_negotiation`）、`3715-3721`（输出治理整体替换 `all_findings`）

**根因**：防误判机制跑在「输出治理边界」**之前**，而治理边界之后用**全新 deepcopy 对象**替换了发现列表。

执行时序：

1. `line 1992-2007`：`red_team_falsification / blind_destruction_test / hallucination_check / consistency_rerun_check` 对 `all_findings`（此时的候选发现）打标 `_red_team_warning / _blind_test / _hallucination`。
2. `line 2363`：`run_negotiation` 对同一批对象做 `drop / downgrade / mark`。
3. `line 3715-3721`：`run_output_governance` 重新跑 69 条原子规则，产出**全新对象**（`output_governance.py:64` 用 `copy.deepcopy`），然后 `all_findings = _scenario_execution.get("findings", [])` **整体替换**。

**后果**：第 1、2 步所有 finding 级的防误判标注（证伪警告、盲测崩塌标记、幻觉标记、协商消解/降级）都落在被替换掉的旧对象上，**对最终报告的每条发现零生效**。只有 `red_team / blind_test / consistency / hallucination_count / engine_hub_summary` 的汇总计数被当作诊断元数据写入报告（`pipeline.py:4555-4567`）。

也就是说：**系统声称拥有的「红队证伪、破坏性盲测、一致性复查、跨域消解降级」四道防误判防线，实际没有一道真正拦截或修正最终报告里的任何一条发现。**

## 四、P1 高风险缺陷

### 4.1 跨域协商 `has_finding / has_item` 门控是死代码

**位置**：`engine/cross_domain_negotiation.py:85-123`（NEG-020/021/030/040 定义）、`418-489`（`run_negotiation` 主循环）

NEG-020/021/030 在规则体里写了 `has_finding`（如「须存在经营费用发现」），NEG-040 写了 `has_item`（「缺失资料」），但 `run_negotiation` 只读 `match_a / negate_b / action / has_field / not_tagged`，**从不读 `has_finding / has_item`**。

**后果**：NEG-020 实际行为退化为「只要 `经营实质分析` 域存在**任意**一条发现，就 drop `无经营场所`」，无视「该发现必须是经营费用」这一前提，可能误杀真实的「无经营场所」疑点。NEG-040 的「缺失资料连锁标记」同理过宽。

### 4.2 税务红线税种覆盖缺口（详见 §六）

42 条红线缺 8 类税种/事项：土地增值税、资源税、环保税、关税、非居民（预提所得税）、公积金、契税、消费税、出口退税、股权转让、核定征收。已覆盖的仅房产税、印花税等少量「其他税费」。

### 4.3 陈旧数字缺乏自动校准闸门

**根因**：`tools/audit_consistency.py`（数字/法条一致性校准工具）在 commit `4074d4cf` 被删，之后所有硬编码数字、法条条款号、计数常量失去自动校验，酿成「1720 字符串污染」事故（约 110 处：`刑法第205条→第201720条`、`42条→41720条` 等）。

**现状**：污染已修复（`b537092c` + `dcc685dc`），但 `tools/verify_release.py` 只拦 `pipeline.py` 出现字面量 `1720`，**没有全局的法条条款号/税种名/计数常量的自动比对器**。同类事故会再次发生。

## 五、P2 中低风险 / 优化项

### 5.1 假设引擎 `confidence` 语义混淆（可解释性）

**位置**：`engine/hypothesis_engine.py:502-504`、`519`、`736-741`

`_verify_hypothesis` 里 `confidence = best.posterior - second.posterior`（实为「后验差/gap」），但 `_get_hypothesis_display` 把它当「置信度」百分比渲染；`confidence_delta` 用 `abs(best["evidence_weight"]) * 3` 近似降分幅度。裁决分支本身逻辑正确（缺失型看 `best_posterior>=0.60`，通用型看 gap>0.6），不影响功能，但术语混用降低可解释性。

### 5.2 红队证伪 / 一致性复查是「启发式」而非真实证伪

**位置**：`engine/red_team.py:63-76`、`107-129`

`_attack_with_evidence` 用字符串关键词（`"季节"`、`"一次性"`、`len(combined)>200`）判断是否击破无罪假设，无真实数据检索或概率计算；`consistency_rerun_check` 用 `pct*0.15` 模拟变化、非真实重跑。即便修复 P0-2 时序，其证伪力度也偏弱，建议升级为「按证据源重新计算」的真实证伪。

### 5.3 `hallucination_check` 金额矛盾检测是空壳

**位置**：`engine/red_team.py:144-148`

`amts_detail` / `amts_sug` 提取完金额后**无任何比对逻辑**，算完即弃。当前只有「法条引用模糊」（141–143 行）一项真实检测。

## 八、是否已具备「税务稽查专家」能力？

**结论：部分具备，尚未达到「税务稽查专家」级。**

### 已具备（可交付、可信）

1. **票税账表勾稽**：69 条原子规则覆盖进销项分类、两税收入差异、进销存数量勾稽、工资社保比对等程序性疑点。
2. **红线驱动定性**：42 条红线产出「可定性 / 待补证 / 排除」三态疑点，符合「发现≠确认」铁律。
3. **假设-验证裁决**：竞争假设贝叶斯更新，缺失型「该有的没有」→ 置疑清单，不自动定罪。
4. **输出治理封印 + 文本护栏**：`seal_governed_findings` + `text_guardrails` 去定性化、处罚白名单、`required_human_review` 恒真。

### 未达到（结构性短板）

1. **三链推理空转**：稽查专家「线索→证据→论证」的推理主干没有真正驱动发现。
2. **无有效反向证伪**：红队/盲测/协商不落地，系统缺一道「证伪自己的结论」的防线。
3. **税种覆盖不全**：土增/资源/环保/关税/非居民/契税/消费税等缺失。
4. **无自动一致性校验**：法条条款号、数字常量会再次漂移而无闸门。

**定性**：一键分析 = 「高覆盖规则筛查 + 红线三态定性 + 假设验证 + 严格封印」的**半自动稽查助手**。补齐 P0 两项 + 税种缺口后，可升级为「专家级筛查—研判一体机」。
