## 二、P0 级发现（6 项）

### P0-1 「金额可复算率」验收标准空转：函数重复定义且恒返 100

`main.py` 中 `_check_amount_recomputability` 定义了**两次**：

```
main.py:9164  def _check_amount_recomputability(findings):
main.py:9170  def _check_amount_recomputability(findings):   ← 后者覆盖前者
```

第二定义体不读取任何 findings 内容、不执行任何复算，直接返回 100。同文件 `_verify_cross_account_isolation` 也重复定义（9176、9197）。后果：方法论阶段五项验收标准中的「金额可复算率」与「跨账套隔离」两项**从未真实检验**，任何数据错误都会以 100% 通过。这是对《税务稽查工作规程》报告质量承诺的直接背叛——报告声称经过五标准 gate，实际两项是常数。

### P0-2 七层执行摘要为硬编码表演文案，与实际状态无关

`engine/pipeline.py` `_build_methodology_summary`（5680-5700）：

```python
5687    lines.append(f"第一层·启动: 身份锚定 ✓ 行业穿透 ✓")
5689    lines.append(f"第三层·布网: 42域并行发动 ✓ 多域信号汇聚 ✓")
5692    lines.append(f"第五层·定案: 三性校验 ✓ 证据闭环 ✓ 红队证伪 ✓")
```

无论各层真实执行结果如何（包括验收 failed、场景缺证据），摘要恒显全部 ✓。两个独立问题：①「42域」为魔数，实际业务域为 25；②「定案」二字违反本系统自身的语言立场过滤（RQ3 与五条禁令均禁止检查阶段出现定性用语），`_filter_discovery_language` 在其他环节清除「定案」措辞，此处自己生产。

### P0-3 护栏与目录存在「系统辅助定性」通道，与 RQ3/五条禁令正面冲突

**冲突点一**，`engine/methodology_guardrails.py` 168-184：

```python
168    if source_count >= 3 and finding_score >= 6:
170        finding["required_human_review"] = False
172        finding["determination_status"] = "system_assisted_pending_confirmation"
184        safe_grade = "多源交叉验证-系统辅助定性"
```

注释自述「证据充分时系统可以做辅助定性」。而 `engine/report_standards.py` 的 `apply_report_standards` 强制 `required_human_review=True / automatic_determination_allowed=False`，RQ3 明文禁止自动定性。两模块政策相反：guardrails 先写 False + 「系统辅助定性」话术，report_standards 后覆盖回 True——最终值侥幸正确，但 `determination_status`/`determination_path`（"多源交叉验证→系统辅助定性→人工确认后发布"）等字段携带违规话术穿透到前端与导出。

**冲突点二**，`engine/methodology_catalog.py` 139-140、182-183：

```python
139    "human_review_required": rule_score < 7,
140    "automatic_determination_allowed": rule_score >= 7,
```

按评分给规则发放「自动定性许可」。虽然 `methodology_assets.py` 的 `mark()`（39-43 行）在 API 出口又强制改回 `human_review_required=True`，但同一份 flat_rules 在主流程内部消费时（如 `_build_doubt_library_summary` 直接 `load_flat_rules()`，pipeline.py 5708）读到的是原始违规值。同一数据两种语义，属于体系级自相矛盾。

### P0-4 能力账本与验证蓝图存在与事实不符的硬编码数字

`main.py` `_build_capability_ledger`（7638）：`"methodology_item_count": 242`、`"partial_atomic_support": 175`，而 items 明细仅 53 行（VERIFIED_RULE_CATALOG）。`_build_validation_blueprint`（7672）：`"required_validation_cells": 834`，实跑 765。这些数字通过 `/api/methodology/assets/capability_ledger` 与 `validation_blueprint` 直接供给 v3 页面展示。更严重的是前端把假数字固化为「不变量」：`methodology-v3.js` 202 行 `metric(ledger.methodology_item_count || 0, '账本已登记', '必须为242且无静默状态')`、43 行 `<b>242</b>逐项查看真实能力`——向用户展示的「真实性自检」本身是假的。

### P0-5 共享内容同步机制假通过：提取器与现行文件结构完全脱节

`engine/shared_content_sync.py` 的三个提取器全部失效：

| 提取器 | 期望结构 | 现行实际结构 |
|---|---|---|
| `extract_standards_chapter_body` | `{label:'..',title:'..',body:'..'}` 对象数组 | `tax-report-standards.js` 为 sections 模板字面量 |
| `extract_handbook_chapter_body` | 三元素数组 | `tax-auditor-handbook.js` 为二元数组 `['标题','正文']` |
| `rebuild_shared_map` | 查找 `id="hb-s5"` | 手册无任何 hb-s* id |

提取失败后 `verify_shared_content` 静默 `continue`，最终输出「全部一致」。即：报告编制要求页面、稽查员手册、`shared_content_map.json` 三者之间**实际无任何同步校验发生**，但系统声称校验通过。9 个 text_sync_blocks 的概念一致性完全失守。

### P0-6 行业场景验收 failed（39/153）但系统照常交付

实跑 `run_portfolio_acceptance`：status=**failed**，114 通过 / 39 失败，失败场景包括 ENE-SUBSIDY-REVENUE、ENE-CARBON-TRADING、TRA-FUEL-SPLIT 等（缺支持证据来源/反向证据来源字段）。`_apply_methodology_stage`（main.py 8465）对验收失败仅做降级注记，摘要层（见 P0-2）仍显「证据闭环 ✓」。一份声称「三性校验通过」的报告，其底层场景合同有 25.5% 缺关键证据字段。

## 三、P1 级发现（7 项）

### P1-1 场景总数双口径并存：108 vs 153

`methodology_inventory()`（catalog）统计 industry_scenarios=108（仅计 V2 复审文件场景），`portfolio_inventory()`（portfolio）统计 153（含 `SCENARIO_DETAILS` 生成场景）。`/api/methodology-audit` 用前者、`/api/methodology/coverage` 与 v3 页面用后者。同一系统对「我们有多少场景」给出两个互相矛盾的官方答案。

### P1-2 前端三套被遮蔽的旧渲染器构成影子回退陷阱

脚本加载顺序（`index.html` 255→256）：`tax-pipeline-pages.js` 先执行，`methodology-v3.js` 后执行并覆盖 `window.renderMethodologyPage`。因此 tax-pipeline-pages.js 中约 1500 行方法论相关代码全部死代码：

| 死代码 | 位置 | 遮蔽原因 |
|---|---|---|
| `renderMethodologyPage`（闭环作业版） | 6368 | 被 v3 的 IIFE 覆盖 |
| `METHODOLOGY_PAGE_SECTIONS`/挂载注册表/全部 `_loadMethodology*` 装载器 | 6157-6360 | 仅被 6368 死渲染器引用 |
| `renderAnalyzePage`（结果视图） | 1533-1726 | 仅被死渲染器的 `_queueMethodologyMount('results',...)`（6799）引用 |
| `renderReportSpecPage`/`renderReportSpecStatic`（旧九节报告规范） | 5660-5760 | core.js `report-spec` 直接路由到 `renderReportStandards`，全库无调用 |
| `METHODOLOGY_CSS`/`METHODOLOGY_TOC` | 6091/6135 | 仅被死渲染器引用 |

风险：若 methodology-v3.js 加载失败（404/解析错误），core.js 858 行 `typeof renderMethodologyPage === 'function'` 判定仍为真，**旧版页面静默接管**，用户看到的将是数代之前的旧内容而无任何报错。

### P1-3 测试断言锁定死代码，现行页面零测试覆盖

`tests/test_business_api_alignment.py` 491-632 行读取的是 `tax-pipeline-pages.js`，断言 `METHODOLOGY_PAGE_SECTIONS`、`renderAnalyzePage`、`_renderMethodologyGuide`、`renderUnifiedDomainPanelV4` 等**全部是被遮蔽的死代码内容**；对实际渲染的 `methodology-v3.js` 没有任何一条断言。测试全绿 ↔ 线上页面无保障，形成虚假安全感。

### P1-4 行业别名 KeyError 陷阱：'TRA' 等 8 个别名码不在合法码表

`methodology_catalog.py` 48 行 `ASSET_TO_CODE` 由 V2_SCENARIO_FILES 反向构建，**同文件多键时后写覆盖前写**：

```python
48  ASSET_TO_CODE = {filename.removesuffix(".json"): code for code, filename in V2_SCENARIO_FILES.items()}
    # 'G'(30行) 与 'TRA'(38行) 同指 transportation_scenario_contracts.json → 最终值为 'TRA'
```

`load_reviewed_scenario_asset`（461-463）→ `load_reviewed_scenario_contracts('TRA')` → `load_industry_contract('TRA')`，而 `PORTFOLIO_CODES = A-T + 3 叠加`（portfolio.py 21-23），'TRA' 不在其中 → **KeyError 'TRA'（已实跑复现）**。受影响别名：TRA/MED/CAT/IT/CUL/CBEC/EDU/FIN/ENE 共 9 个文件名映射。当前未爆雷仅因两重巧合：① `load_reviewed_scenario_asset` 全库无调用；② `/api/methodology/assets` 白名单（main.py 7717-7729）只放行 7 个场景文件，transportation/catering/it_software/finance/education/medical/culture/energy/cross_border_ecommerce 九个文件不在白名单。一旦有人补全白名单（合理需求），`prepare_methodology_asset`（methodology_assets.py 27-31）将立即对这 9 个资产抛 KeyError → 500。

### P1-5 方法论阶段摘要自相矛盾：「已核定」与「不自动作出行政认定」并存

`_apply_methodology_stage`（main.py 8465 起）产出的 summary 同时包含「已核定 X 项」与「全部发现均为待核事项，系统不自动作出行政认定」两类措辞。「核定」属定性用语，与后者直接矛盾，且未被语言立场过滤捕获。

### P1-6 「四方交叉验证」「五条禁令」名不符实

`pipeline.py` `_four_way_cross_verify`（5632）：名为四方，实际仅做发票/银行总额比值（0.3~3.0）一类比对。`_check_five_prohibitions`（5602）：文档串称五条，函数体仅实现 ①③⑤ 三条（另存在 `_check_five_prohibitions_full`，两者并存未收敛）。摘要再以「四方交叉验证: 通过」输出（5698），夸大实际检验范围。

### P1-7 前端硬编码 242 与假账本互相锁定

`methodology-v3.js` 43 行 `<b>242</b>逐项查看真实能力`、202 行 `'必须为242且无静默状态'`。前端不变量与后端假数字（P0-4）互相印证，构成「两个假数互为证据」的闭环；真实明细 53 行，用户点开「逐项查看」根本看不到 242 项。

## 六、整改优先级建议

**第一批（P0，建议立即修复）**
1. 删除 main.py 9170/9197 的重复定义，为 `_check_amount_recomputability` 实现真实复算逻辑（抽样核对 finding 金额 = 明细之和），`_verify_cross_account_isolation` 实现真实隔离校验。
2. `_build_methodology_summary` 改为从 quality_report/cross_verify/pipeline_log 动态生成；「42域」改读实际业务域数；删除「定案」措辞。
3. 统一复核政策：删除 guardrails 168-184 的 `required_human_review=False` 通道与 catalog 139-140/182-183 的评分免复核逻辑，全部收敛到 report_standards 的强制人工复核口径。
4. `_build_capability_ledger`/`_build_validation_blueprint` 改为从 VERIFIED_RULE_CATALOG 与 run_portfolio_acceptance 实时统计；同步删除 methodology-v3.js 的 242 硬编码。
5. shared_content_sync 三个提取器按现行文件结构重写，提取失败改为显式失败而非 continue。
6. 39 个失败场景补齐支持/反向证据来源字段，或从 portfolio 剔除直至达标。

**第二批（P1）**
1. 收敛 108/153 双口径为单一权威源。
2. 清除 tax-pipeline-pages.js 三套死渲染器（先确认回退策略：要么删要么显式报错，不允许静默回退）。
3. 测试改为断言 methodology-v3.js + 加载顺序契约。
4. 修 ASSET_TO_CODE 构建（单字母码优先），补齐 API 白名单 9 文件并回归验证。
5. 摘要措辞统一过 `_filter_discovery_language`。
