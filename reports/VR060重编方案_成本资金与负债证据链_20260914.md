# 「采购成本无对公付款资金证据」分析功能重编方案

> 目标规则：VR060 `_scan_core_cost_fund_evidence` → 红线 RL-PTY-001
> 日期：2026-09-14

---

## 一、先把三个专业前提答准（它们决定怎么改）

### 前提 1：主营业务成本怎么认定？**是否必须通过银行付款？**

**认定**：主营业务成本 = 与主营业务收入**直接配比**的成本（商品销售成本 / 服务成本 / 工程施工成本）。
系统现有 `engine/main_biz_cost.py::identify_main_biz_cost()` 已做**三层识别**：
`core_cost_invs`（主营成本）/ `major_expense_invs`（重大费用）/ `minor_expense_invs`（日常报销），
依据 = 品名关键词 + 进销品名重合 + 大额占比。**这一层方向是对的**，需补"判定依据可解释"。

**是否必须银行支付？——不是。**

税法**从未要求**成本必须通过银行支付。资金流只是**证据链的一环**，不是唯一要件。
合法的成本支付方式至少包括：

| 渠道 | 是否体现在"对公转账"里 |
|---|---|
| 银行转账 | ✅ |
| **银行承兑/商业承兑汇票**（出票、背书、贴现） | ❌ 多数只在到期兑付时体现 |
| 信用证 / 保函 | ❌ |
| 平台代付（支付宝/微信等） | ⚠️ 需单独识别 |
| **个人垫付后报销** | ❌ 走个人卡 |
| **现金支付** | ❌ |
| **债务抵销 / 以货易款 / 股东代付** | ❌ |
| 应付账款挂账（赊购，暂不付） | ❌ 本就无付款 |

> **关键结论**：`"无对公付款"本身不构成任何违规或不当`，它只意味着**证据强度下降**。
> 真正的硬要求是：**每一笔成本，要么有"付款"，要么有"负债（应付账款）"——两者至少有一个。**
> **两者都没有 → 才是异常。**

### 前提 2：应付账款能否真实存在？挂账多久？为什么一直不付？

**完全可以，且极普遍。** 赊购是常态：账期 30/60/90/180 天，工程与大宗贸易可跨年。
**年末开票、次年 1–2 月付款是最常见的正常情形。**

因此正确判据必须是**双要件**：

```
            有付款记录？        有应付账款挂账？
真实赊购        否       +        是        → 正常（仅提示账龄，若超 1 年）
已付/垫付       是       +      任意        → 正常（按支付渠道定性）
★真异常★        否       +        否        → 成本凭空列支：虚列成本 / 票未入账 / 已用其他资金支付
```

**挂账时长** = 分析基准日 − 发票日。参考口径：≤ 正常账期（如 180 天）→ 正常；
**> 1 年** → 长期挂账，须追问原因。

**"为什么一直不付"的真实原因清单（前 4 项属可解释，第 5 项才是问题）**：

1. 资金紧张、账期未到
2. 质量争议 / 退货未决
3. **对方已注销、无法支付** → 依法应转营业外收入，否则少计所得额（这是**另一个**风险点）
4. 已用**其他方式抵销**（抵账协议、以货抵款、票据）
5. **根本没有真实交易**（虚开 / 虚列成本）

### 前提 3：企业给个人报销日常经营费用（款项直接付给个人），**有没有额度限制？**

**没有法定金额上限。** 真实、与经营相关、凭证合规即可税前扣除。

但有**五重约束**，这才是系统该判的东西：

| # | 约束 | 系统应如何判 |
|---|---|---|
| ① | 发票须开给**公司**；个人抬头/个人消费不得扣除（差旅个人票有例外） | 看发票 buyer 是否为受检企业 |
| ② | 若实质是**向个人支付劳务/货款**（非报销）→ 须按劳务报酬代扣个税、且需代开发票 | 分流到 VR065（个人服务未代扣代缴） |
| ③ | **进项抵扣**：向自然人支付通常无专票 → 多数不可抵扣 | 看是否有专票/抵扣记录 |
| ④ | **现金管理**：单笔大额现金支付受《现金管理暂行条例》约束（结算起点 1000 元） | 现金渠道加金额阈值 |
| ⑤ | 报销**不得替代工资**（拆薪避个税） | 与工资表交叉 |

> 结论：**"支付给个人的报销款"没有额度上限，但有"真实性 + 凭证合规 + 个税代扣 + 不得抵扣进项 + 现金管理"五重约束。**
> 系统应**按渠道分流定性**，而不是笼统来一句"无对公付款"。

## 二、现状诊断：为什么会误报（根因）

**红线定义与规则实现脱节。**

RL-PTY-001 的 `constituents`（构成要件）第 3 条**本来就写着**：

> 「未通过**应付账款挂账、票据结算、债务抵销**等方式合理解释」

`required_materials` 也有「**应付账款明细**」「采购合同」。

但 `VR060` 的实现**只做了一件事**：把主营成本发票与银行**支出流水**按对手核心名做匹配。
**应付账款、票据、抵销这三项排除，一个都没做。**

而且：

- `accounts_payable`（应付账款明细）**指纹库有解析器，但 `pipeline.py` 零引用** → 数据没接线（与 `fixed_assets` 同类问题）；
- 匹配**无跨期窗口**：只看已提供的流水区间，年末发票的次年付款**必然**判为"无付款"；
- 个人垫付只认"流水对方是自然人"，**不看是否有报销单/费用发票**；
- 输出**只有一条**，语气是"成本真实性存疑"（**这个定性本身预设了错误前提**）。

## 三、重编方案：从「无对公付款→存疑」改为「资金与负债证据链四层核验」

### 核心思想

> 把「是否有对公付款」从**唯一判据**，降级为**证据强度的一个档位**；
> 用 **支付渠道 × 应付挂账 × 账龄** 三轴交叉，**只有三者都对不上**的才列待核。

### L0 主体识别（加固现有）

`identify_main_biz_cost` 输出每张票的**判定依据**（命中哪条规则：品名重合/加工费/大额/费用关键词），
写进 finding 的 `observed_metrics`，做到"可解释、可复核"。

### L1 支付渠道匹配（扩展，不再只看对公转账）

`engine/payment_channel.py::classify_payment_channel(invoice, bank_txs, vouchers)`

| 渠道 | 识别方式 |
|---|---|
| 对公转账 | `bank_txs` 支出行 × 对手核心名 |
| **票据结算** | remark/摘要含 `承兑 / 汇票 / 贴现 / 背书 / 票据`；到期兑付流水 |
| 平台代付 | 财付通 / 支付宝 / 抖音 等（已有） |
| **个人垫付/报销** | 流水对方为自然人 **且** 存在对应**费用类进项票 + 报销凭证** |
| 现金 | 凭证中「库存现金」贷方腿 |
| 债务抵销 / 以货抵款 / 股东代付 | 摘要关键词 + 往来科目勾稽 |
| **跨期窗口** | 匹配窗口 = 发票日 + **N 天账期**（默认 180，可配）；若提供**次年流水**则继续匹配 |

输出：每张票 → `已付(渠道)` / `挂账` / `无解` 三态 + 证据强度分。

### L2 账面负债交叉（**新增 · 最关键**）

`engine/ap_aging.py`：用 **应付账款明细 + 科目余额表**，按供应商算 A/P 余额与**账龄**。

**判定矩阵（新判据核心）**：

| 有付款 | 有 A/P 挂账 | 账龄 | 结论 | 报告动作 |
|---|---|---|---|---|
| 是 | 任意 | — | 正常 | 不输出（或"信息"级） |
| 否 | **是** | ≤ 180 天 | **正常赊购** | 不输出 |
| 否 | **是** | > 1 年 | 长期挂账 | 提示：核资金/纠纷/**对方注销应转收入**/抵销协议 |
| 否 | **否** | — | **真异常** | 待核线索（调查优先级）：虚列成本 / 票未入账 / 其他资金支付 |
| 否 | 是 | — | 但 A/P 之后被**现金/个人卡**冲平 | 三流不一致，渠道合规提示 |

### L3 渠道合规分层（替代笼统"存疑"）

- **个人报销**：有**费用发票 + 报销单**、金额与经营相称 → **不提示**
- **个人收款**：无票 / 劳务性质 / 大额高频 → 提示"疑似向个人支付劳务或货款，须核个税代扣与真实性"（并联动 VR065）
- **大额现金**：单笔超阈值 → 现金管理合规提示
- **票据结算**：提示补齐票据链（出票/背书/贴现）佐证

### 输出改造

从**一条**（"无对公付款 → 成本真实性存疑"，中风险/调查优先级）改为**分层输出**：

| 层 | 内容 | 定性 |
|---|---|---|
| 资料质量 | 流水未覆盖期间/账户、缺 A/P 明细 | **提示补件，不指向企业过错** |
| 待核线索 | 无付款 **且** 无 A/P 挂账 | 真疑点（调查优先级） |
| 长期挂账 | 有 A/P 且账龄 > 1 年 | 提示核实原因 |
| 渠道合规 | 个人收款 / 大额现金 / 票据 | 按渠道提示 |

**文案必须去掉"成本真实性存疑"这类定性**，改为"资金与负债证据链不完整，需补充佐证"。

### 红线同步改造

RL-PTY-001 的**名称与 suspect 本身含错误预设**（"无对公付款资金证据"暗示"必须对公付款"）：

- 名称建议改为：**「成本列支的资金与负债证据不足：真实性待核」**
- `suspect` 去掉"成本无真实资金流支撑"的绝对表述，改为"未以付款或负债形式形成可核验的闭环"。
- `constituents` 保留三条，并**明确前置**："须先排除应付账款挂账、票据结算、债务抵销"。

## 四、需要接线 / 新建的东西

| 项 | 现状 | 动作 |
|---|---|---|
| `accounts_payable`（应付账款明细） | 指纹库有解析器，pipeline **0 引用** | **接线**（同 `fixed_assets` 的修法） |
| 票据台账 | 无解析器 | 先用 remark/摘要关键词兜底；后续可加解析器 |
| 次年银行流水 | 需企业提供 | 系统提示补件，补后未匹配自然消失 |
| 报销单 / 费用类发票 | `pur_invs` 已有费用类 | 复用 `minor_expense_invs` |
| 账龄引擎 | 无 | 新建 `engine/ap_aging.py` |
| 渠道识别引擎 | `fund_matching.py` 仅对公+平台+个人 | 新建 `engine/payment_channel.py` |

---

## 五、实施步骤（可分四批做）

1. **接线 `accounts_payable`** + 新建 `engine/ap_aging.py`（按供应商 A/P 余额与账龄）
2. 新建 `engine/payment_channel.py`（多渠道识别 + 跨期窗口）
3. **重写 VR060** 为 L0–L3 分层输出（含判定矩阵、文案去掉定性、分层 finding）
4. **改红线 RL-PTY-001** 名称/suspect/constituents + 全量回归 + 一致性闸门

每批都：写验证脚本（正例/反例/真实数据零误报）→ 跑 `pytest` + `tools/audit_consistency.py` → 提交。

## 六、对本例（公司1）的预期变化

| 供应商 | 情形 | 新结论 |
|---|---|---|
| 西安三顾行 85,049.5（12-26） | 年末票，付款在次年 | 跨期窗口内 → **降为正常/信息** |
| 深圳梦阳 26,548.67（11-27） | 同上 | **降为正常/信息** |
| 西藏松赞 17,698.11（01-13） | 年初票整年未付 | 查 A/P：有挂账→长期挂账提示；**无挂账→保留待核** |
| 安徽康翔 33,097.35（01-08） | 同上 | 同上 |

即：**这一项会从"一条笼统的存疑"变成"分层、可解释、可复核"的结论**，
且误报（跨期）自动消解，真疑点（无付款且无挂账）被保留并加重。
