## 一、你会看到什么（结果级验收）

### 1. 打开 `/users`（用户管理页）

从上到下你会看到：

1. **顶栏**：`👥 用户管理` + 当前登录人（`用户名（角色1、角色2）`）+ 三个跳转链接
   （`角色管理` / `审计日志` / `返回主界面`）—— **链接本身按权限显隐**：
   没有 `role.manage` 的人看不到「角色管理」，没有 `audit.view` 的人看不到「审计日志」。
2. **工具栏**：搜索框（用户名/显示名）、组织下拉、每页条数、搜索/重置，
   以及 **`＋ 新建用户` 按钮**（无 `user.manage` 权限时**整个按钮不出现**）。
3. **表格 11 列**：ID / 用户名 / 显示名 / 角色（标签）/ 组织 / 账套数 /
   **手机号 / 身份证号 / 银行账号** / 状态 / 操作。
   - 这三列是**脱敏列**：内部角色（系统管理员）看到明文；审计员等角色看到
     `138****5678`、`110***********1234`、`6222****33`、姓名 `张某`。
   - 表尾有一行**脱敏留痕**：「本次对外版本按角色「检查人员（金额可见、身份脱敏）」完成脱敏：…」
     —— 改了要看得见。
4. **操作列**：`编辑`（改显示名/联系方式/角色/组织/账套）与 `启用/停用`。

### 2. 打开 `/roles`（角色管理页）

- **角色清单**：5 个内置角色（系统管理员 / 企业财务 / 税务师 / 复核专家 / 审计员），
  含编码、范围（tenant/platform）、类型（内置/自定义）、权限数、说明。
- **角色 × 权限矩阵**：13 个权限点 × 全部角色，`✓` = 具备。一眼能看出
  「企业财务没有 `user.manage`」「审计员没有任何写权限」。
- **角色 → 脱敏策略表**：5 个角色各落到哪套脱敏策略（`internal` / `enterprise` / `auditor`）。
- **`＋ 新建自定义角色`**（无 `role.manage` 时不出现）：勾选权限点即可建新角色；
  **重建内置角色会被拒**并提示改 `config/rbac.json`。

### 3. 打开 `/audit-logs`（审计日志页）

- **筛选**：动作下拉（**中文名 + 动作码**，来源=审计动作唯一权威表）、关键字、起止时间、每页条数。
- **表格 7 列**：ID / 时间（北京时间）/ 操作人 / 动作（中文标签，登录类为橙色、管理类为红色）/
  对象 / 说明 / 账套。
- 你会在这里看到**登录成功、登录失败、退出登录、越权访问被拒、用户创建、用户修改、角色创建**
  七类 P0-8 新动作，以及 P0-1~P0-7 的全部业务动作（资料上传/发起分析/报告导出/风险复核…）。
- **看不到别人组织的事**：非超管只能看到**本组织成员**的留痕。

### 4. 主界面左侧菜单（`/`）

「三、系统」组下新增三条：`👥 用户管理` / `🔐 角色管理` / `🧾 审计日志`，
分别带 `data-perm="user.view"` / `"role.manage"` / `"audit.view"`
—— **无权限的角色根本看不到这些菜单项**（由 `/static/js/rbac-nav.js` 按服务端下发的权限集合显隐）。

### 5. 登录页（`/login`，既有页面）

既有登录页照常工作；后端 `/api/v1/auth/login`（任务书要求的新路径）与既有
`/api/auth/login` **共用同一个实现**，所以两条路径的限流、Cookie、留痕行为完全一致。

### 6. 打开下载的文件

- **资料/报告下载**：PDF/图片**真嵌入水印**（`mode="embedded"`，实测字节数增加）；
  XLSX 等无法嵌入的格式**明确告知**"水印信息随附于响应头"，**不假装已加水印**。
- 报告水印文字含**复核标识**：未复核的报告显式写「**未经人工复核**」，已复核写「已复核（李四）」。

## 二、核心实现说明

### 2.1 三层权限模型（每层一个唯一权威，互不替代）

| 层 | 回答什么 | 唯一权威 | P0-8 是否新建 |
|---|---|---|---|
| ① **功能权限（RBAC）** | 这个人能不能做这件事 | `engine/rbac.py::rbac_allows()`（**唯一判定点**） | ✅ 新建 |
| ② **数据权限（账套）** | 这个账套他能不能看 | `security.SessionContext::can_access_company()` | 沿用（未改） |
| ③ **项目权限（成员）** | 这个项目他能不能改 | `engine/project_service.py::_can_write()` | 沿用（未改） |
| ＋ **组织层（租户）** | 他属于哪个组织、组织形态 | `engine/rbac.py::visible_tenant_ids()` | ✅ 新建 |

### 2.2 关键设计决定（含"为什么这样做"）

1. **`users.role` 保持两值 `CHECK(role IN ('admin','user'))`，不改**。
   它是 SQLite 建表期约束（无法 `ALTER ... CHECK`），且 `SessionContext.is_admin`、
   `security_web._ADMIN_PATHS`、历史数据全部依赖它。P0-8 把它**解释**为：
   `role='admin'` ⇒ 等价持有 `system_admin`（全权限）；`role='user'` ⇒ 由
   `user_roles` 表决定细粒度角色，无记录则回落 `default_role`。
   ⇒ 既有守卫**零改动**即兼容，新角色体系与旧语义并存且不冲突。

2. **角色/权限/映射的"数据"放在 `config/rbac.json`（唯一数据表），代码只加载+薄转发**。
   新增一个角色或权限点**只加一行数据**，不改任何逻辑分支（符合"通用规则而非特例"的要求）。

3. **角色→脱敏只做"映射"，不重写脱敏规则**。
   「要不要脱、脱哪几项」的唯一权威仍是 `config/report_compliance.json::redaction_roles`；
   「怎么脱」的唯一权威仍是 `engine/redaction.py`。本层只声明
   「哪个 RBAC 角色按哪套策略出参」，且**取值必须落在已登记的脱敏角色键内**（闸门校验）。

4. **不静默放行**：未知权限码 / 未知角色码 / 空会话 ⇒ 一律 `False`；
   `require_permission()` 抛 403 且消息里带上当前角色（便于自查，不泄露数据）。

5. **租户隔离"业务数据层"不另立第二套**：账套/资料/项目/风险/报告仍由
   `allowed_company_ids` + 项目成员承担；P0-8 只新增**组织层**（谁是同组织的人）
   与**功能权限层**。留痕的租户边界用「本组织成员的用户 id 集合」表达
   （成员变更后边界自动跟随，不引入第二张映射表）。

6. **`tenant_id IS NULL` 的账号（含 `APP_ADMIN_USERNAME` 引导超管）归属默认组织**，
   只在查默认组织时并入；否则引导超管写下的留痕"留了却没人看得到"（本轮实测踩到并修正）。

7. **字段级人名脱敏**（新增 `redaction.mask_person_name_field`）：
   文本级 `redact_names()` 靠称谓/身份词作锚点，裸字段值 `"张会计"` 没有任何锚点
   ⇒ **一个字都不会改**（实测：审计员看到的仍是「张会计」，属"跑了但没生效"）。
   字段级以"字段语义"为锚，复用同一套姓氏/复姓权威表。

8. **身份库初始化只此一处**：`security.init_security_db()` 同时幂等建立授权表
   （roles/permissions/role_permissions/user_roles/tenants），避免出现
   「库已初始化但授权表缺失」的中间态（自检/离线 CLI 会看到不完整的身份库）。

### 2.3 数据表与迁移（沿用项目 migration 底座，**不引入 Alembic**）

- **新表 5 张**（落在 `data/security.db`，与 `users` 同库 —— 角色是身份的一部分）：
  `roles` / `permissions` / `role_permissions` / `user_roles` / `tenants`。
- **`users` 幂等补列 5 个**：`display_name` / `phone` / `id_card` / `bank_account` / `tenant_id`
  （**既有 9 列列名与顺序一字未动**）。
- 内置角色/权限每次启动按配置 **upsert 同步**；**自定义角色（builtin=0）原样保留**，不被覆盖。

### 2.4 接口（6 个任务书要求 + 2 个配套）

| 方法 | 路径 | 权限 |
|---|---|---|
| POST | `/api/v1/auth/login` | 公开（`security.is_public_path` 已登记） |
| GET | `/api/v1/users` | `user.view` |
| POST | `/api/v1/users` | `user.manage` |
| GET | `/api/v1/users/{user_id}` | `user.view`（跨组织 ⇒ 404） |
| PUT | `/api/v1/users/{user_id}` | `user.manage` |
| GET | `/api/v1/roles` | `user.view` 或 `role.manage` |
| POST | `/api/v1/roles` | `role.manage` |
| GET | `/api/v1/audit-logs` | `audit.view` |

> 是否越权的**唯一判定**在 `engine/rbac.rbac_allows()`；接口层不自行判断角色（避免第二套口径）。

### 2.5 审计留痕（写入唯一入口未变）

- 新增 7 个动作（**只在 `ACTIONS` 末尾追加**，顺序不动）：
  `auth.login` / `auth.login_failed` / `auth.logout` / `auth.denied` /
  `user.create` / `user.update` / `role.create`，并在 `ACTION_CN` 成对登记中文名。
- **越权也留痕**：管理员路径越权、跨账套越权、CSRF 失败三类 403 全部记 `auth.denied`。
- 读取侧 `audit_trail.list_records()` **新增可选过滤**（user_id / q / actions / 日期区间），
  过滤条件由**唯一构造点** `_build_audit_filters()` 生成 ⇒ `count()` 与列表**永不漂移**。

## 五、未完成 / 风险

### 5.1 未完成（如实列出，未做减法）

1. **SaaS 多实例级的租户隔离未做**：当前 `tenants` 提供**组织归属 + 形态标记**
   （`saas` / `private`），隔离执行仍靠"组织成员集合 + 账套授权"。**同一实例内**的多组织隔离已生效；
   但"不同租户使用不同数据库/不同实例"的**物理隔离**未实现（需要部署层支持，属运维范畴）。
2. **角色-权限图形化编辑（勾选保存到内置角色）未做**：内置角色的权限改动仍需改
   `config/rbac.json`（这是有意的单一权威）；页面只支持**新建自定义角色**。
3. **用户的密码重置 / 强制改密未接入新接口**：仍走离线 CLI `manage_users.py reset-password`。
4. **审计日志导出（CSV/Excel）未做**：任务书只要求"查看"，未要求导出。
5. **`role_permissions` 的自定义角色权限调整（PUT）未做**：只支持 `POST` 新建；
   调整权限需重建（当前无删除接口，避免引入删除语义风险）。
6. **前端权限门控仅覆盖菜单与主要按钮**：页面内个别次要控件仍可能可见但点击后 403
   （服务端**始终**拦截，不影响安全，只影响体验）。

### 5.2 风险与已识别边界

1. **`users.role='admin'` 是"全权限"后门**：既有引导超管与 `manage_users.py --role admin`
   创建的账号可绕过细粒度角色。这是**有意保留的兼容行为**（移除会让既有管理员全部失效），
   但意味着"给某人 admin"= 给全部权限，运维须谨慎。
2. **留痕的租户边界依赖"组织成员集合"**：若某用户被改到其他组织，其**历史留痕**的可见性
   会随之迁移（按当前成员判）。这是"无第二张映射表"的代价，属**有意的口径选择**，
   已在 `_visible_actor_ids()` 注明。
3. **`user_roles` 覆盖式写入**：`PUT /users/{id}` 传 `roles` 会**整体替换**（不是增量）。
   前端已按此语义实现，接口文档亦写明"覆盖式"。
4. **`audit_logs` 无租户列**：租户过滤靠内存裁剪（非超管路径最多取 5000 行后过滤）。
   数据量大时效率下降；若未来留痕量级增长，需要给 `audit_logs` 加 `tenant_id` 列
   （**幂等加列**即可，不影响历史数据）。
5. **重复角色判定为"最严"**：多角色时脱敏策略取**脱敏项最多**的那一套（安全优先），
   可能出现"某角色本可看明文却因另一角色被遮盖"。若业务需要"取并集"，需显式改
   `rbac.redaction_role_of()` 的比较规则。
6. **本机生产身份库已实际迁移**：`data/security.db` 已新增 5 张表与 5 个用户列
   （幂等、可重复执行、既有列未动）。若需回退，删表/删列即可（SQLite 3.35+ 支持 `DROP COLUMN`）。
