## 一、工商信息：你的判断基本成立，但要区分两件事

你说「你是精通如何免费获取企业工商信息的，但没有接入给财税稽查系统」。
**实测结论：接入了一个（公示系统），但通道当前不可用；其余免费渠道确实没接。**

### 1.1 系统里**已接入**的通道（实测清单）

配置权威：`config/business_info.json::providers = ["local_db", "gsxt"]`

| 通道 | 类型 | 实测状态 | 证据 |
|---|---|---|---|
| `local_db`（本地库） | 免费、离线 | **可用** | 实测命中「深圳海更数字传媒有限公司」，来源标为「本地账套库（companies）」，confidence 0.95 |
| `gsxt`（国家企业信用信息公示系统，页面抓取） | 免费、无 Key | **不可用** | 实测 **HTTP 521**（风控拒绝），两个 UA 均 521，先访问首页拿 cookie 后仍 521 |

**外部通道实测原文**：

```
查询「腾讯科技（深圳）有限公司」      ok=False  reason=HTTP 521
查询「阿里巴巴（中国）有限公司」      ok=False  reason=HTTP 521
```

**关键：不是本机网络问题** —— 同环境实测：

```
百度               HTTP=200 长度=29506
腾讯               HTTP=200 长度=119074
国家统计局          HTTP=200 长度=140578
税务总局            HTTP=200 长度=144199
国家企业信用信息公示系统  HTTP=521   ← 唯独工商类站点被风控
```

### 1.2 `local_db` 的数据到底从哪来（这点必须说清）

**不是从外网抓的。** `companies` 表由 `engine/project_service.py:202` 在**建稽查项目时**写入：

```sql
INSERT INTO companies (name, uscc, industry_code, registered_capital, established_date,
                       legal_representative, address, business_scope, company_type, created_at) ...
```

即：用户建项目 → 项目信息回填到账套库 → 之后「自动查填」再从账套库读回来。

⇒ **当外部通道不可用时，所谓"自动查填"实际是"把用户自己填过的值再读出来"**，
对**新企业（本地库没有的）完全不产生新数据**。这才是使用者实际感受到的落差。

### 1.3 其余免费渠道：实测谁真能通（这是"没接入"的部分）

我实测了 6 个常被认为"免费可取"的公开源：

| 数据源 | 实测 HTTP | 能否取数 | 可接入性判断 |
|---|---|---|---|
| 国家企业信用信息公示系统 | **521** | ❌ | 风控拦截；仅在出具《信息公示报告》后有效期短、且需人工过验证码 |
| 信用中国（行政处罚/失信） | **412** | ❌ | 412 Precondition Failed，需特定 Header/风控令牌 |
| 工信部 ICP 备案查询 | **521** | ❌ | 风控拦截（且仅有网站备案，无工商登记字段） |
| 全国法院被执行人（执行信息公开网） | 200 | ⚠️ 页面含"验证" | 需过验证码才出结果，不能无人值守 |
| 中国裁判文书网 | 200 | ⚠️ 页面含"验证" | 同上；且**涉诉 ≠ 工商登记信息**，不是本文要的字段 |
| 深圳市场监管局 | 200 | ⚠️ | 地方局站，非全国统一接口，逐地适配成本高 |

**结论（如实）**：
- **工商登记字段（法定代表人/注册资本/经营范围/登记状态）的权威源就是公示系统**，
  而它在无人干预（验证码/滑块）的前提下**取不到**。这是**反爬机制**，不是我的能力问题，
  也不是"我没写代码"；
- 真正"免费且可无人值守"的替代：部分是**地方税务/市监公开数据**、部分是**付费 API**
  （天眼查/企查查，需 token —— 系统里已预留 provider，配置 token 即启用）；
- **搜索引擎兜底**：系统已实现（`SearchEngineVerifier`，走搜狗检索四个维度），
  但它只能判断"搜到/搜不到"，**不是工商登记字段的来源**。

### 1.4 ★ 核实中发现一处「声称 > 实际」，必须报告

`engine/enterprise_report.py:6479` 的注释写着：

> 「免费通道（国家企业信用信息公示系统+搜索引擎）**已实装**」

而后半句是**实际存在的**，前半句**当前取不到数**。这是同一类问题的第二次出现
（上一轮刚处理过 `apply_template` 声明章节顺序但不重排）。
→ 建议：把注释与报告内文案改为**如实描述实测状态**（例如"公示系统通道已实现但因风控
   当前不可用，需人工配置 GSXT_COOKIE 或改用付费通道"），避免读者误以为工商核验真的生效了。

**这一项我没有擅自改** —— 它涉及报告对外文案（合规措辞），需要你确认口径。

## 二、五类报告的关系：不是五种不同报告，是「1 份分析 + 4 种裁剪」

### 2.1 报告清单实况

| 你提到的 | 系统实际实现 | 位置 |
|---|---|---|
| 分析报告 | **一键分析链**的阅读页（不是"生成报告"的一种视图） | `/reports` 首个页签 |
| 生成报告（全景） | 视图 `full` | 导出链 |
| 生成报告（分税种专项） | 视图 `tax_specific` | 导出链 |
| 生成报告（管理层摘要） | 视图 `management` | 导出链 |
| 生成报告（税务自查） | 视图 `self_check` | 导出链 |

**它们是两类东西**：前者是"看报告"，后四者是"出报告"（同一份底稿的 4 种裁剪）。

### 2.2 「生成报告的基础是分析报告吗？」—— **是，有代码与实测双重证据**

**代码证据**（`engine/report_service.py:735-741`）：

```python
collected = _risk_data(cid, session)          # ① 从分析产出的发现集合取
payload = {}
got = RISK.load_payload(cid, session)         # ② 从分析载荷取
payload = got.get("payload") or {}
```

`load_payload` 读的是 `company_{cid}_full.json` —— 正是**一键分析**落盘的产物
（由 `main._persist_one_click_result` → `report_payload.dump_payload` 写入）。

**实测证据**：本项目账套 1 的载荷 `scripts/four_reports/company_1_full.json` 存在（36 MB），
`build_document` 能据此产出全文；若删掉该载荷，四个视图都会退化为空内容。

⇒ **结论：生成报告完全以分析结果为基础**。它不重新分析，也不独立取数。
两者**共用**同一份发现集合与同一份载荷。

### 2.3 ★ 但实测发现一个实质问题：`tax_specific` 与 `full` **正文完全相同**

这是**你这个问题最有价值的发现**，我用差异比对严格证明了：

```
【full / 全景】        章节数 = 12  条目上限 = 不限
【tax_specific / 分税种专项】 章节数 = 12  条目上限 = 不限   ← 与 full 一字不差

抹掉报告名称/视图名/时间戳后，两者差异 = 4 行，全部是时间戳与页脚水印文本
   - "v": "2026-10-19T17:10:08+08:00"
   + "v": "2026-10-19T17:10:09+08:00"
   - "watermark_text": "...（全景）..."
   + "watermark_text": "...（分税种专项）..."
```

**而系统对 `tax_specific` 的声明是**（`engine/report_views.py::VIEW_DESC`）：

> 「按税种组织的明细视图：风险总览与明细按税种分组展开，便于分税种自查与沟通」

**实际**：`tax_detail` 章节在**两个视图里都存在且内容相同**，都已经是按税种分组
（实测该章节确为「【增值税】10 项 /【企业所得税】9 项 /【未标注税种】6 项 /【个人所得税】3 项」，
每个税种一个表）。也就是说 —— **按税种分组这件事 `full` 也做了**，
`tax_specific` 没有再"更聚焦"。

⇒ **`tax_specific` 与 `full` 目前是重复的**（唯一区别是封面上的名称字样）。
这是一个**真实的实现缺口**（"声称 > 实际"的第三处），不是我的误解。

### 2.4 四个视图的**真实**差异（实测，可直接验收）

| 视图 | 章节数 | 保留章节 | 真实差异 |
|---|---|---|---|
| `full` | 12 | 全部 | 基线 |
| `tax_specific` | 12 | 全部 | **与 full 相同（缺口）** |
| `management` | 7 | 去掉 data_source/tax_detail/evidence/legal_basis/attachments | 实测 `rectification` 表行数 18 → **5**（上限生效）；`omitted` 如实登记被裁章节 |
| `self_check` | 8 | 去掉 key_risks/evidence/legal_basis | `tax_detail` 完整保留（实测 10+9+6+3+1… 与 full 相同） |

**上限是否生效（实测）**：
- `management` 的 `VIEW_ITEM_LIMIT = 5` **生效**（整改建议 18 行 → 5 行）；
- `KEY_RISK_LIMIT = 10` 生效（`key_risks` 的 kv 块恒为 10）；
- 但 `doc["limit"]` 顶层字段实测为 `None`（真实值在 `context.limit`）——
  **字段位置与含义易误读**，建议核对。

## 三、建议（按优先级，均需你确认后我再动手）

| # | 事项 | 为什么值得做 | 风险 |
|---|---|---|---|
| 1 | **`tax_specific` 要么真做"税种聚焦"、要么下线或改名** | 现状是"两个入口同一份内容"，用户会以为拿到了不同报告；且 `VIEW_DESC` 的声明与实现不符 | 改动 `report_views.py` 一处 + 报告文案；需你定方向（赋能 or 收敛） |
| 2 | **把工商通道的实测状态写进报告与注释** | 消除"已实装"的误导；让报告读者知道"外部核验本次未取得" | 涉及报告对外文案，需你定合规措辞 |
| 3 | **补一个"免费通道真的能取到"的方案** | 见下 | 需要你选路线 |

### 关于第 3 项，可选的路线（各有代价，我不替你选）

| 路线 | 免费？ | 无人值守？ | 代价 |
|---|---|---|---|
| A. 公示系统 + 人工过验证码后配置 `GSXT_COOKIE` | 免费 | ❌ 需人工 | 每次风控升级都要重配；系统已支持该环境变量，**零开发量** |
| B. 接入地方市监/税务公开数据（逐省适配） | 免费 | ✅ 部分 | 全国 30+ 省市各自一套页面，维护成本高；覆盖不全 |
| C. 付费 API（天眼查/企查查，需 token） | ❌ | ✅ | 已有 provider 骨架，配 token 即启用；按调用量计费 |
| D. 搜索引擎兜底（已实装）+ 明确标注"结果仅供参考，非登记原文" | 免费 | ✅ | 只能给"线索"，**不能作为工商登记字段来源** |

**我的判断**：如果目标是"新企业也要能自动拿到完整工商登记字段"，**A + C 组合最现实**
（A 保免费基线、C 保覆盖率）；B 的维护成本与覆盖缺口不成比例；D 只能当补充。
