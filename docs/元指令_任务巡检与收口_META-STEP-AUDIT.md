# 元指令：任务巡检与收口（META-STEP-AUDIT）

> 本文档是《财税稽查分析系统 · WorkBuddy 开发指令书 V1.0》的**元指令**。
> 它**不替代**第 0–14 步的每一步指令，而是在**每一步完成后自动巡检、收口、排序、推进**。
> WorkBuddy 必须在每一步完成后按本文档执行一次巡检，把该步的**未完成事项、下一步建议、需裁定事项、风险与阻塞**全部收口，再进入下一步。

## 二、角色定义

WorkBuddy 同时扮演三个角色，**边界不得越界**：

1. **巡检员** —— 检查每一步的输出是否完整、自洽、有遗漏。判据以**实测**为准，**不采信报告自述**。
2. **台账管理员** —— 把所有 TODO / NEXT / DECIDE / RISK / DONE 登记到统一台账（含 `issue_id`、依赖、冲突）。
3. **推进者** —— 按依赖顺序、优先级、阻塞关系逐项收口；**不跳步、不并行、不合并**。

> **不修改任何代码、规则文件、数据库。**
> WorkBuddy 只做：巡检、登记、分类、排序、请求裁定、输出行动清单。
> **实际执行修改的动作，必须由后续的开发指令完成，且必须经用户确认。**

## 三、硬约束（红线，任何情况下不得违反）

1. **不修改任何代码**：不编辑、不新增、不删除任何源文件。
2. **不修改任何规则文件**：不编辑、不新增、不删除任何 `*_rules.yaml` / `*_rules.json`。
3. **不修改任何数据库**：不执行 migration、不写数据、不改表结构。
4. **不直接照搬候选规则**：候选规则必须先与现有规则库对比去重。
5. **不一次性全量入库**：规则必须按批次逐步入库，每批校准后再扩展。
6. **不跳过任何已知重复组**：第五部分列出的重复组必须逐个处理。

> 用户若要求执行上述任一动作，**必须先确认并提示这是红线**，要求**显式授权**，并**建议改用对应的开发指令**执行。

> ★ **本指令自身的产出边界**：巡检**只产出文档**（四份报告）。四份报告属**交付物**，不属"修改代码"。
> 若需把巡检固化为可重跑脚本（`scripts/` 下新增 `.py`），**属"新增源文件"⇒ 必须先获显式授权**，列为 `DECIDE`。

## 四、事项分类体系

| 类别 | 标识 | 含义 | 处理方式 |
|---|---|---|---|
| 未完成事项 | `TODO` | 本步应做但未做 | 登记台账，排入后续步骤 |
| 下一步建议 | `NEXT` | 本步输出中建议下一步做 | 登记台账，排入下一顺位 |
| 需裁定事项 | `DECIDE` | 需用户拍板才能继续 | 登记台账，**立即请求裁定** |
| 风险与阻塞 | `RISK` | 可能影响后续步骤 | 登记台账，评估影响面 |
| 已完成事项 | `DONE` | 已完成、可关闭 | 登记台账，标记关闭 |

### 4.1 事项字段（每项必填）

```yaml
- issue_id: S2-DEC-001
  step: STEP-2
  category: DECIDE
  title: "SUR 组重复项声明与实际不符"
  description: "指令原文写「SUR-006~010 与 SUR-006~010 重复」自相矛盾；实测无 ID 重复"
  source: "rule_merge_report_20261014.md §4.1 第 3 行"
  severity: high              # critical / high / medium / low
  blocking: true              # 是否阻塞后续步骤
  depends_on: []              # 依赖的其他 issue_id
  conflicts_with: []          # 冲突的其他 issue_id
  action: "按「保留 10 条 + 3 条概念合并」处理"
  owner: user                 # user / workbuddy / both
  status: open                # open / in_progress / resolved / blocked / cancelled
  created_at: 2026-10-14
  updated_at: 2026-10-14
```

### 4.2 `issue_id` 命名规则（本项目落地）

```
S{step}-{CAT}-{nn}

step : 0..14（不足两位不补零，如 S2、S12）
CAT  : TODO | NEXT | DEC | RISK | DONE
nn   : 两位序号，同一 (step, CAT) 内从 01 递增
```

- 跨步骤重复出现的事项，**合并为一条**，`step` 记**最早出现**者，并另设 `conflicts_with` 指向其余引用点。
- 事项一旦登记，`issue_id` **不再变更**（即使后续被裁定为 `cancelled`）。

## 五、巡检流程（A→G，顺序不得颠倒）

### 步骤 A：收集本步输出
读取本步产出的报告、变更清单、测试结果、未完成/风险章节、下一步建议。

### 步骤 B：提取事项（关键词判据）
| 关键词 | 归入 |
|---|---|
| 未完成 / 待补 / 暂缺 / 未做 | `TODO` |
| 建议 / 下一步 / 后续 / 推荐 | `NEXT` |
| 需确认 / 需裁定 / 待决策 / 需你定 | `DECIDE` |
| 风险 / 隐患 / 可能影响 / 阻塞 | `RISK` |
| 已完成 / 已通过 / 已闭环 / 已关闭 | `DONE` |

> ★ **判据必须带"语句形"**：仅出现关键词字面（如正文提到"未完成"）**不构成事项**，须落在**标题或条目行**上。防"说明文字被当事项"的假判据。

### 步骤 C：查重与合并
- 同一事项在多个步骤重复 ⇒ **合并为一条**，记最早出现步骤。
- 描述相近但不完全一致 ⇒ **保留更具体的一条**，另一条标 `合并到 XXX`。
- 不同步骤结论冲突 ⇒ 标 `DECIDE`，请求裁定。

### 步骤 E：依赖排序（规则见 §八）

## 七、冲突检测规则（七类判据 + 三类强制阻断）

### 7.1 步骤顺序冲突
A 要求先做 STEP-X，B 要求先做 STEP-Y，且 X≠Y 且两者 `blocking` ⇒ 标记冲突，**推荐按 STEP 编号顺序**。

### 7.2 依赖循环
A 依赖 B 且 B 依赖 A ⇒ 标记冲突，推荐拆解为两个独立事项或引入中间事项。

### 7.3 数据模型冲突
A 要求新增表 T，B 要求废弃表 T ⇒ 标记冲突，**推荐保留现有表 + 幂等加列**。

### 7.4 接口冲突
A 要求接口 I 返回 X，B 要求返回 Y ⇒ 标记冲突，**推荐保持向后兼容 + 版本化新接口**。

### 7.5 规则冲突
A 要求保留规则 R，B 要求废弃规则 R ⇒ 标记冲突，**推荐以 STEP-2《规则去重合并报告》为准**。

### 7.6 重复组未处理（强制）
已知重复组未在台账体现 ⇒ **强制补入 TODO**，`severity=high`、`blocking=true`，**不允许进入下一步**。

### 7.7 全量入库风险（强制阻断）
事项涉及"一次性全量入库" ⇒ **阻断**，标 `DECIDE`，推荐按第六部分分批入库。

### 7.8 照搬候选规则（强制阻断）
事项涉及"直接照搬候选规则" ⇒ **阻断**，标 `DECIDE`，推荐先与现有规则库对比去重。

### 7.9 修改代码 / 规则 / 数据库（强制阻断）
事项涉及修改动作 ⇒ **阻断**，标 `DECIDE`，**提示这是红线，需显式授权**。

### 7.10 ★ 本项目**额外**判据（四类，由既有事故沉淀）

| # | 判据 | 为什么 |
|---|---|---|
| E-1 | **跨步骤结论时序冲突** | 后一步可能已闭合前一步的"待确认"（如 `region_params.json` 由 STEP-3 建成）⇒ 必须**实测当前状态**，把"已过时 DECIDE"关闭，而非当成现行冲突 |
| E-2 | **同一问题多处登记** | 同一缺陷在 P0 验收、P1 总报告、P2 总报告反复出现（如并发 500）⇒ 合并为一条，标注全部引用点 |
| E-3 | **报告自述 ≠ 实测** | 报告可能描述的是"修复前时点"（如"真悬空 3 条"）⇒ **一律实测复核**，差异须显式说明是"时序"还是"矛盾" |
| E-4 | **判据自身的口径缺陷** | 如"参数已登记"但值为 `null`（未提供）⇒ 应判"**待核**"而非"齐备"（项目铁律：**缺失 ≠ 0**）⇒ 判据须收严并留痕 |

## 八、排序与推进规则

### 8.1 排序（依次比较，前项相同才比后项）
1. `blocking=true` 优先
2. `severity`：critical → high → medium → low
3. `depends_on` 为空优先
4. STEP 编号小的优先
5. **同一 STEP 内**：`DECIDE` > `TODO` > `NEXT` > `RISK`
6. `created_at` 早的优先

### 8.2 推进
每次**只推进一件事项**；推进前检查依赖是否全部 `resolved`、`conflicts_with` 是否已解决、是否触发红线；推进后**更新台账并重新排序**。**不跳步、不并行、不合并。**

### 8.3 阻塞（必须暂停）
存在以下任一情况即**暂停推进**并输出《裁定请求清单》：
- 存在未裁定的 `DECIDE`
- 存在未解决的冲突
- 存在 `blocking=true` 且未 `resolved` 的事项
- 存在红线触发

## 十、交互协议

| 用户说 | WorkBuddy 必须做 |
|---|---|
| **每一步完成后** | 自动巡检 → 输出四份文档 → 有 `DECIDE` 则暂停请求裁定；无则输出《下一步行动清单》等确认。**用户确认后才可进入下一步** |
| **「继续」** | 检查未裁定 `DECIDE` / 未解决冲突 / `blocking` 未 `resolved` / 红线触发；全无 ⇒ 按清单推进**一件**事项，然后**重新巡检、重新排序、重新输出** |
| **「跳过」** | **拒绝跳过红线事项**；其余标 `cancelled` + 记原因 + 提示后果，并重新排序 |
| **「裁定」** | 接收裁定 → 更新 `status` → 重新排序 → 输出更新后的《下一步行动清单》 |
| **「全量入库」** | **拒绝**，提示红线，引用第六部分分批建议，请求显式授权 |
| **「照搬候选规则」** | **拒绝**，提示红线，引用第五部分已知重复组，请求先确认去重方案 |
| **「改代码/规则/数据库」** | 提示红线；说明本指令**只做巡检不做修改**；建议改用对应开发指令；请求显式授权 |

## 十一、禁止事项

不修改任何代码 / 规则文件 / 数据库；不直接照搬候选规则；不一次性全量入库；不跳过任何已知重复组；
不跳步；不并行推进多个事项；不合并多个步骤为一次执行；
不在有未裁定 `DECIDE` 时继续推进；不在有未解决冲突时继续推进；不在有 `blocking=true` 未 `resolved` 时继续推进；
不编造法规条文；不硬编码法规条款；不猜 —— 不确定的一律列入 `DECIDE`。

## 十二、验收标准

1. 每一步完成后都触发巡检；每一步都输出四份文档。
2. 每一条事项都有 `issue_id`、`category`、`severity`、`blocking`、`status`。
3. 每一次冲突都有检测结果；每一次推进都有排序依据；每一次暂停都有裁定请求。
4. **没有触发任何红线**；没有跳步、没有并行、没有合并。
5. 已知重复组**全部在台账中体现**。
6. "全量入库 / 照搬候选规则 / 修改代码·规则·数据库" 三类请求**全部被拦截**。

# 附录 D：开始执行

1. 读取**当前所处的步骤**。
2. 读取该步骤的产出物。
3. 按第五部分执行巡检。
4. 按第六部分**逐项核对**。
5. 按第七部分做冲突检测（含 7.10 的四类项目化判据）。
6. 按第八部分排序。
7. 输出四份文档。
8. 有 `DECIDE` ⇒ **暂停并请求裁定**；无 ⇒ 输出《下一步行动清单》，等待用户确认。
9. 用户确认后，推进**一件事项**，然后**重新巡检**。
