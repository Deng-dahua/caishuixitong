## 诊断 2 · 综合疑点认定要件数（疑点2 / 10 / 11）

### 2.1 配置里到底有几条？

```bash
./.venv/Scripts/python.exe -c "
import sys; sys.path.insert(0,'.')
from engine.trigger_conditions import determination_criteria_of as d, trigger_conditions_of as t
for k in ('SYN-MULTI-TAX-PROFILE','VR012','VR019'):
    print(k, '触发条件', len(t(k)), '条 ｜ 认定要件', len(d(k)), '条')"
```

**实测输出**：
```
SYN-MULTI-TAX-PROFILE 触发条件 1 条 ｜ 认定要件 1 条
VR012 触发条件 1 条 ｜ 认定要件 1 条
VR019 触发条件 1 条 ｜ 认定要件 1 条
```
⇒ **配置里各有 1 条**（`C1`，`is_precondition=true`，即"现象/前提条"）。

### 2.2 配置里有 C1，为什么产物里"认定要件数 = 0"？

**根因**：`engine/trigger_conditions.classify()` 的 `determination_criteria` **只从 `checkpoints`
（逐要件核对记录）构造**，**从不回退配置**。而这 3 个疑点是"无红线绑定的综合/规则发现"——
它们**没有 `constituents`**（没有构成要件）⇒ `constituent_checkpoint.build_constituent_checkpoints()`
返回空 ⇒ `checkpoints = []` ⇒ `criteria = []` ⇒ **产物 0 条，配置 1 条**。

**证据链（修复前）**：
```bash
# 修复前产物
./.venv/Scripts/python.exe -c "
import json; d=json.load(open('scripts/four_reports/company_1_full.json',encoding='utf-8'))
ps=d['enterprise_readable_report']['confirmed_problems']
for p in ps:
    if p.get('seq') in (2,10,11):
        b=p['trigger_determination']; print(p['seq'], b['risk_code'], '认定要件', len(b['determination_criteria']))"
# 实测（修复前）：2 SYN-MULTI-TAX-PROFILE 认定要件 0 ／ 10 VR012 认定要件 0 ／ 11 VR019 认定要件 0
```

**这不是"如实"，而是 bug**：配置里明明登记了"该指标要核哪条"，产物却一条都不列 ⇒
读者看不到该核什么，门禁也查不出（见 2.3）。

### 2.3 门禁 TDS-① 是否对它们生效？为什么？

| 判据 | 层级 | 是否覆盖这 3 个疑点 | 结论 |
|---|---|---|---|
| **TDS-①（风险指标必须同时定义触发条件与认定要件）** | **配置级**（读 `config/risk_conditions.json`） | **✅ 生效**：这 3 条在 `config/risk_conditions.json` 里各登记了 1 条触发条件 + 1 条认定要件（前提条），判据通过 | 生效 ✓ |
| **TDS-⑤⑥⑦⑧（产物级：块齐全 / 触发命中⇔疑点成立 / 要件↔状态一一对应 / 前提条必须写符合情形）** | **产物级**（读 `company_1_full.json`） | ⚠ **形式上通过、实质上漏判**：`criteria=[]` 与 `criterion_status={}` 是**空 ↔ 空**，**一一对应**（`[] == []`）⇒ TDS-⑦ 不报错；TDS-⑧ 遍历 `determination_criteria` 时**空数组直接跳过** ⇒ 前提条"必须写符合情形"**没有被检查** | **漏判漏洞**（判据本身不完整，不是"没生效"） |

**⇒ 门禁漏洞根因**：产物级判据**只约束"已存在的要件"，没有约束"配置里有、产物里必须也有"**
（即缺一条**同源一致性断言**）。这与 Skill 6/7 的"漏登记"是同一族缺陷。

### 2.4 已做的修复（C 情况的处置）

| # | 修法 | 位置 | 实测 |
|---|---|---|---|
| 1 | `classify()` 在**核对记录为空**时**回退配置里的认定要件**：前提条且触发已命中 ⇒ `checked_hit` + 「符合情形」；其余 ⇒ `not_checked` + 「本项为综合/规则发现、未绑定构成要件，本轮未作逐条核对」 | `engine/trigger_conditions.py`（`classify()` 内，新增 `if not crits:` 分支） | 3 个疑点现各 **1 条**认定要件、C1 为「符合情形」 |
| 2 | **门禁补同源一致性断言**：`产物 determination_criteria 条数 == 配置条数`（仅当该风险键在配置登记过） | `tools/audit_consistency.py::check_trigger_determination_separation()`（TDS-⑨ 新增） | 真实产物 `ERROR 0`；**反向验证**（把疑点2 要件清空）⇒ **报红**：`结构化块认定要件 0 条 ≠ 配置 1 条` |
