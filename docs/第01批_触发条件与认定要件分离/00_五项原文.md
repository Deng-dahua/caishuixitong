【问题定义】
当前系统在多个疑点中出现同一类逻辑错误：
- 疑点1：第1条构成要件为"存在红字发票或作废发票（红冲行为）——存在即成立"，系统已查到13张红字发票，但核对结论写"未形成核对结论"。
- 疑点3：第1条构成要件为"工资表列支人数与社保参保人数存在差异"，系统已查到工资6人、社保5人，但核对结论写"未形成核对结论"。
- 疑点4：第1条构成要件为"银行账户经营性入账金额与同期申报收入、开票收入存在差异"，系统已查到9个月差异超过25%和10万元，但核对结论写"未形成核对结论"。
- 疑点12：第1条构成要件为"固定资产入账、投入使用、计提折旧的时点链条不闭合"，系统已查到2笔固定资产付款，但核对结论写"未形成核对结论"。
根因：系统把"触发条件"和"认定要件"混为一谈，统一叫"构成要件"。触发条件用于判断"是否列为疑点"；认定要件用于判断"风险是否成立"。两者不可混同。
【Skill 名称】
触发条件与认定要件分离 Skill
【Skill 职责】
1. 每个风险指标必须定义两类条件：
- 触发条件（trigger_conditions）：出现什么信号就列为疑点。
- 认定要件（determination_criteria）：满足什么条件才认定风险成立。
2. 疑点形成时，记录触发了哪条触发条件。
3. 逐条核对认定要件时，分别记录每条要件的状态。
4. 报告输出时，明确写：
- 本项因触发条件X而列为疑点。
- 认定要件共N条，已满足M条，待核实K条。
- 疑点成立，但风险是否成立待定。
5. 触发条件已满足的，必须写"符合情形"，不得写"未形成核对结论"。
6. 认定要件中若含"现象/前提条"，状态判定规则：
- 前提条已满足 → 写"符合情形"。
- 前提条未满足 → 不列为疑点。
【输入】
- 风险指标定义（含触发条件、认定要件）
- 疑点数据
- 核对结果
【输出】
字段：
- risk_code：风险编码
- trigger_conditions：触发条件清单
- trigger_status：每条触发条件的命中状态
- determination_criteria：认定要件清单
- criterion_status：每条认定要件的核对状态
- 疑点是否成立（布尔值）
- 风险是否成立（布尔值）
- 结论表述
【系统修改点】
1. 数据模型：
- 风险指标表增加 trigger_conditions 字段。
- 认定要件表增加 is_precondition 字段（标记前提条）。
2. 报告模板：
- 每个疑点开头写"本项因触发条件X而列为疑点"。
- 每个疑点结尾写"认定要件共N条，已满足M条，待核实K条；疑点成立，风险是否成立待定"。
3. 质量门禁：
- 不得出现"已列为疑点"但"未触发任何触发条件"。
- 不得出现"未涉及任何一条构成要件"但"已列为疑点"。
- 前提条已满足时必须写"符合情形"。
4. 配置 JSON：
{
"risk_code": "RISK_RED_INVOICE_001",
"trigger_conditions": [
{"id": "T1", "desc": "存在红字发票或作废发票", "auto": true}
],
"determination_criteria": [
{"id": "C1", "desc": "存在红字发票或作废发票", "is_precondition": true},
{"id": "C2", "desc": "红冲发生在敏感时点"},
{"id": "C3", "desc": "红冲无对应退货单、折让协议等合法事由"}
]
}
【测试用例】
1. 单元测试：
- 疑点1：13张红字发票 → 触发条件T1命中 → 疑点成立；认定要件C1应写"符合情形"，不得写"未形成核对结论"。
- 疑点3：工资6人、社保5人 → 触发条件T1命中 → 疑点成立；认定要件C1应写"符合情形"。
- 疑点4：9个月差异超25%和10万元 → 触发条件T1命中 → 疑点成立；认定要件C1应写"符合情形"。
- 疑点12：2笔固定资产付款 → 触发条件T1命中 → 疑点成立；认定要件C1应写"符合情形"。
2. 集成测试：
- 用疑点1、3、4、12做回归样例。
- 确保所有疑点均正确区分触发条件与认定要件。
3. 回归测试：
- 用当前报告做失败样例。
- 修复后做通过样例。
- 输出《回归测试报告》。
