## 1. 交付物：条件 DSL 解释器 `engine/rule_dsl.py`

### 1.1 为什么是它

候选库 460 条**全部带机器可读的 `logic` 表达式**，实测语言极小：

| 需要的语法 | 实测出现 |
|---|---|
| 比较 `> < >= <= == !=` | 278 / 30 / — / — / 140 / 39 |
| 函数 `abs` / `min` | 45 / 1 |
| 组合 `and` / `not` / `or` | 203 / 20 / 1 |
| 四则算术 | 85 |
| 时间窗/循环（**不支持**） | 7 |

⇒ 与其引入通用表达式引擎（重、且语法面大），不如**按实测边界实现最小解释器**，并对超出边界的部分**显式拒绝**。

### 1.2 三条硬约束（写进实现）

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **三值逻辑**：字段缺失 / 参数待核 / 除零 ⇒ `UNKNOWN`，**绝不默认 False** | 若缺数据默认 False，等于把「没查」说成「没问题」——违项目铁律「缺失≠0」 |
| 2 | **不取数**：变量值由调用方注入（`resolver`），本模块只求值 | 取数口径的唯一权威是 `var_map` 与各引擎模块；复制口径＝多头维护 |
| 3 | **白名单**：函数与否定形容词未登记 ⇒ 解析期报错 | 「看起来像自然语言就猜语义」＝静默顶替 |

### 1.3 支持与**有意不支持**的语法

**支持**：比较、四则（`+ - * /`）、`abs()/min()/max()`、`and/or/not`、括号、`params.<名>` 阈值引用、布尔字面量 `true/false`、`X not met`（≡ `not X`）、标识符内含 `&`（如 `R&D_expense`）。

**有意不支持**（留 Python，属**要件化类**）：

| 语法 | 条数 | 为什么不做 |
|---|---|---|
| `A not in B` | 3 | **集合成员判定**，需集合值语义；用数值比较模拟会得出**错的结论** |
| `X for n months` / `for` | 4 | **时间窗/循环**，需要跨期上下文 |

### 1.4 行为样例（可复现）

| 表达式 | 绑定 | 结果 | 说明 |
|---|---|---|---|
| `output_tax - input_tax > params.gap` | `{output_tax:120, input_tax:30}`, `gap=5` | `True` | 正常求值 |
| 同上 | `{output_tax:120}`（缺 `input_tax`） | `None` | ★ **缺字段 ⇒ UNKNOWN**，不是 False |
| `a > params.t` | `t=null`（如地区参数待核） | `None` | ★ **参数待核 ⇒ UNKNOWN** |
| `a / b > 1` | `b=0` | `None` | ★ **除零 ⇒ UNKNOWN**（不返回 0、不崩） |
| `a > 0 and b > 0` | `{a:0}`（缺 `b`） | `False` | Kleene 短路：一侧为假即可判假 |
| `a > 0 or b > 0` | `{a:0}`（缺 `b`） | `None` | 一侧为假、另一侧未知 ⇒ 未知 |

| 层 | 判据（是否需要上下文） | 条数 | 落点 |

### 2.1 阈值类（已外置）

阈值**不是**以「规则」形态存在的 —— 它以**参数表**存在：

| 参数表 | 内容 |
|---|---|

| `config/region_params.json` | **地区参数**（法定口径 + 待核位，**不预设地方值**） |
| `config/tax_limits.json` / `industry_params.json` | 系统侧限额与行业参数 |

⇒ 改阈值**只需改数据**，这一层**已达成** T-6 目标。

### 2.3 表达式规范化（本轮已处理）

首轮解析时 23 条报错，逐一归因后**全部消解**（均为候选库的写法问题，非语义不清）：

| 原写法 | 条数 | 处置 |
|---|---|---|
| `X not met`（自然语言否定） | 16 | **支持为显式语法糖** `≡ not X`；形容词限于白名单 |
| `R&D_expense` 含 `&` | 5 | **允许标识符内含 `&`**（`&` 作算符仍不支持） |
| `true` / `false` | 45+18 处 | **作为布尔字面量**（原先被误当变量 ⇒ 误判「字段未取到」） |
| 综合 | | 解析率 432 → **453** |

## 3. 可外置的**真实瓶颈**：字段取数口径缺口

| 指标 | 数值 |
|---|---|
| 候选 `logic` 引用的**不同字段名** | **611** |
| `var_map` 已登记取数口径 | **73** |
| **无取数口径（缺口）** | **538**（被引用 743 次） |

### 3.1 缺口按性质分两类

| 类别 | 个数 | 性质 | 落地方式 |
|---|---|---|---|
| **布尔标志位**（`*_abnormal` / `*_missing` / `*_not_met` / `*_met` …） | **66** | **不是「取数字段」，而是「判定结论」** ⇒ 本质属**要件化类** | 由检测器产出，**不进 `var_map`** |
| **数值字段** | **472** | 可从账/票/报表/申报表取数 | 补 `var_map` 取数口径 |

> ★ 该分类按**命名特征**识别，**仅为线索、须人工确认**：`conditions_not_met` 这类名字对应的其实是一个**判定**，不是一条取数。

### 3.2 ★ 缺口按**规则实现状态**分档（决定「该不该补」）

> **为什么必须分档**：538 个缺口里若不加区分地去补口径，会有相当一部分**补了也无处可用** —— 因为引用该字段的规则本身还是 `missing`（未实现）/ `placeholder`（判据未定义）。按规则状态切开，T-6 的「可收敛部分」才**可对账**。

| 分档 | 规则数 | 字段数 | 被引用次数 | 处置 |
|---|---|---|---|---|
| **已实现规则**（`covered` / `partial`） | **258** | **329** | **511** | ★ **T-6 第 1 批**：字段真需补口径 |
| **未实现规则**（`missing` / `placeholder`） | **188** | **209** | **232** | 随规则入库时一并处理，**不计入当前缺口** |

> **判据**：`covered` 表示「系统已有实现」⇒ 其字段**理应已能取到**，只是没登记 `var_map`；`partial` 表示「部分覆盖」⇒ 字段口径需补齐才能完整判定。二者是**真缺口**。`missing`/`placeholder` 的字段口径**依赖该规则先被实现**，现在补属**超前投入**。

### 3.3 推进路径（可增量、可对数）

1. **每补一个字段口径 ⇒ 减一行 `gap_fields`**（登记表见 `config/rule_dsl_scope.json`）；
2. 补口径时必须**复用既有唯一权威**（`numparse` / `fieldkit` / `account_classifier` / `industry_resolver` / `industry_benchmark`），不得为候选规则另写一份取数；
3. 布尔标志位**不进 `var_map`**，而是由检测器产出并登记 `redline_id` 归属（项目既有机制），否则无法进覆盖率统计。
