## 2. 核心实现说明

### 2.1 ★ 层级边界：只做任务层，绝不重写引擎

```
任务层（本模块 engine/analysis_task.py）   8 步 / 5 状态 / 取消 / 重试 / 超时 / 项目↔作业链接
   ↓ 调用
业务层（既有）            main._launch_analysis_task → main._run_analysis_thread
   ↓
引擎层（唯一收敛点）       main._execute_tax_risk_analysis → engine.pipeline._run_analyze
   ↓ 落盘
作业流水（既有权威）       engine/analysis_jobs.py（JSONL）
运行态（既有）            main._analysis_tasks（内存，毫秒级进度）
```

**为什么不另立一套进度与状态**：引擎已在上报 `current_step`(1–7) / `progress` / `current_module`。
本模块**不重算、不猜测**，只按**声明式映射**翻译成任务层事实。

### 2.2 8 步模型与映射（唯一处，可断言）

| 任务步 | 名称 | 对应引擎步 |
|---|---|---|
| 1 | 校验资料完整性 | 0（引擎未开始） |
| 2 | 解析未解析文件 | 1（资料扫描/解析） |
| 3 | 数据标准化 | 2（目标实体识别） |
| 4 | 数据质量检查 | 3（域分析，含数据校验） |
| 5 | 规则扫描 | 4（规则引擎+链驱动） |
| 6 | 风险评分 | 6（行业对标 + Phase4 综合定性） |
| 7 | 生成风险发现 | 5（方法论噪声过滤） |
| 8 | 生成报告草稿 | 7（正式报告输出） |

**★ 实测事实**：`engine/pipeline.py` 的 `_report(..., step=N)` **上报顺序不是 1..7**，
而是按文件行号 `1, 2, 3, 4, 6, 5, 7`（行 614 / 1543 / 2215 / 2767 / 2813 / 4569 / 5888）。
映射表把该顺序翻成**严格递增**的 2..8，否则前端会**跳步**。
闸门 `TaskStepMapTests`/基线自检断言：① 单调递增；② 无重复；③ **每个任务步都可达（无死步）**。

### 2.3 5 状态与判定优先级（唯一判据处）

| 任务状态 | 中文 | 来源 |
|---|---|---|
| `PENDING` | 排队中 | 内存 `running` 且进度=0、步骤=0 |
| `RUNNING` | 执行中 | 内存 `running` |
| `SUCCESS` | 已完成 | 内存 `done` / 落盘 `done` |
| `FAILED` | 执行失败 | 内存 `error` / 落盘 `error` / `blocked`（主体一致性拦截） |
| `CANCELLED` | 已取消 | 内存 `cancelled`、`deleted`（报告已删）、取消旗标、超时 |

**判定优先级（顺序不可颠倒）**：
① **已终局 ⇒ 用终局事实**（★ 取消**不得**覆盖终局：对已完成作业点取消若被覆盖成 `CANCELLED`，
就对不上流水里那条 `done` —— **两种事实一个名字**）；
② 取消/超时 ⇒ `CANCELLED`；③ 内存运行态；④ 落盘说在跑而内存无记录（重启后）⇒ 如实 `RUNNING`。

### 2.4 ★ 取消的语义（如实声明，不夸大）

**引擎无法被硬中断**：`engine/pipeline.py` 的 `_report`/`_module` 对 `progress_callback`
是 `try/except: pass`，回调里抛异常会被吞掉。故取消 = 三件事：

1. **置旗标**（`cancel_requested`，由 `main._analysis_lock` 保护）；
2. **丢弃结果**——`main._run_analysis_thread` 写回处加**取消守卫**（4 处同行内改）：
   `result` 置 `None`、`status` 记 `cancelled`、`progress` **不置 100%**、`message` **不写"分析完成"**；
3. **终态记 `cancelled`**——`_register_job_finished` 把"取消"与"失败"**分开登记**
   （取消**不计失败率、不触发失败告警**）。

**边界（如实写入"未完成/风险"）**：引擎线程会**自然收尾**（不立即停止）；取消期间内存态仍是
`running` ⇒ **并发闸门照旧拦住同账套的新任务**（口径一致，不是漏洞）。

**实测（`_smoke_p04b`）**：发起 → 取消 ⇒ 4 秒后引擎收尾 ⇒ 流水 `cancelled`、
内存 `result is None`、`message="已取消（本次结果不予采用）"`、`progress=99`（非 100）。

### 2.5 重试（只允许失败/已取消）

* `SUCCESS` **不允许**重试（400，说明原因）——完成的作业重跑是**另一件事**，应由用户显式发起；
* `FAILED` / `CANCELLED` 允许 ⇒ **新建一次作业**，`retry_of` 指回原作业（项目↔作业链接里记一行）；
* `blocked`（主体一致性拦截）归 `FAILED` —— 对用户即"没出报告"。

### 2.6 超时（可配置，按"取消"语义）

* 阈值 `ANALYSIS_JOB_TIMEOUT_SECONDS`（默认 **3600 秒**）；**非法值回默认并留痕**（不静默当 0）；
* 超时 ⇒ 请求中止（置旗标）+ 状态 `CANCELLED` + 错误文案 `TIMEOUT_NOTE`（"结果不予采用（可重试）"）；
* **终局后超时不再生效**（已完成就是已完成，不得被超时改写）；
* **孤儿作业自愈**：服务重启后内存无运行态、落盘无终态 ⇒ `GET` 时登记 `error`（"服务重启中断"）
  —— 否则它会**永远停在"执行中"**。列表接口一律 `commit_timeout=False`（**读操作不得有副作用**）。

### 2.7 项目↔作业链接（append-only）

* 存放 `data/analysis_task_links.jsonl`（一行一链接：`job_id` / `project_id` / `retry_of` / `created_by`）；
* **为什么不入外部库也不入既有流水**：这是**任务层独有**的事实（"属于哪个项目""重试自哪个作业"），
  放进业务作业流水会污染其口径；为一个字段建 SQLite 表也不值。**新增一类链接 = 加一行数据**；
* ★ **并发复用不写链接**（它不是一次新作业）；
* ★ `jobs_of_project` 必须**先按 job_id 折叠、再按 project_id 过滤**（反过来则换过项目的作业会
  同时出现在两个项目历史里 —— **单元测试实测抓到**）。

### 2.8 资料完整性闸门（任务第 1 步，引擎之前）

* 判据只有一条且**不猜**：项目下**一份资料都没有** ⇒ 400（"项目下没有任何资料，无法发起稽查分析"）；
* **不做**"必查资料齐备度"判定作为阻断条件 —— 那属于**报告层**（`enterprise_report`
  的 material_readiness，含业态剔除口径），在此重算等于另立一套口径；
* 返回**事实计数**（总数 / 待解析 / 已解析 / 分类计数）供界面展示。

### 2.9 权限（与 P0-1/P0-2 同一口径）

* 有项目链接 ⇒ 走 `project_service.get_project`（P0-1 权威判定项目可见性）；
* 无链接（历史作业/非项目入口发起）⇒ 退回**账套可见性**判定（`session.can_access_company`），
  **绝不因此拒绝**（否则老作业全变 404）；
* 跨租户 ⇒ **404 而非 403**（**不泄露存在性**）；
* ★ 边界转换：下游 `ProjectError` / `DocumentError` 统一转 `AnalysisTaskError`
  （否则穿透成 **500** —— P0-2 已踩过同一坑）。

## 4. 未完成 / 风险

| # | 项 | 说明 | 级别 |
|---|---|---|---|
| 1 | **取消是"软取消"** | 引擎无法硬中断（`pipeline._report` 吞回调异常）；取消后线程自然收尾、期间占并发额度。已如实写入界面与 `meta.cancel_semantics` | 中 |
| 2 | **进度百分比来自引擎** | 引擎用粗粒度估算（如域分析阶段长期 97–99%）；本模块只翻译不重算。**8 步清单**才是可靠的阶段指示 | 低 |
| 3 | **任务未挂到 `analysis_sessions`** | 引擎另有 `data/analysis_sessions/`（运行期状态拆分产物），本模块未接。**建议 P0-6 一并收敛**（否则"任务"与"会话"两处各有一套运行期事实） | 中 |
| 4 | **超时默认 3600 秒偏宽** | 大账套全量分析可能真的超过；届时会被判超时取消。**需业务确认合理阈值** | 中 |
| 5 | **无"排队"实态** | `PENDING` 只在"任务已建、引擎尚未进入第 1 步"的窗口出现（约几十毫秒），**没有真正的队列调度**（同账套直接复用、不同账套直接起线程） | 低 |
| 6 | **重试不继承 force 语义** | `retry` 固定 `force=True`（重新完整执行）。若失败原因是"上游数据未修好"，重试仍会失败 | 低 |
| 7 | **WebSocket 未纳入** | 引擎已有 `/ws/pipeline/{task_id}`（毫秒级推送）；本页用 1.5 秒轮询（**沿用既有接口，未改一行**）。可后续切换 | 低 |
| 8 | **API 前缀两种风格并存** | 存量 167 端点无前缀、新增用 `/api/v1`（**待你裁定**，见 §7） | 低 |

## 5. ★ 本轮修正的真实缺陷

| # | 问题 | 根因 | 处置 |
|---|---|---|---|
| 1 | **完成/失败均无审计** | 原审计只有起点 `analysis.start`，**终态无任何留痕**（4 条终态路径分散在 `_run_analysis_thread` 的 try/except 里） | 在**唯一终态漏斗** `job_finished` 里登记 `job.finished`（一处覆盖四态），失败时**不虚记** |
| 2 | **跨租户返回 500** | 下游 `ProjectError`/`DocumentError` 穿透（API 层只捕 `AnalysisTaskError`） | 加**边界唯一转换处** `_as_task_error` / `_get_project`（P0-2 已踩过同一坑） |
| 3 | **`cancel_pending` 恒为假** | 判据写成 `cancel_requested and status == RUNNING`，而置旗标后状态已判为 `CANCELLED` | 改判 `cancel_requested and not 已终局` |
| 4 | **取消可覆盖终局** | 原 `_task_status` 把取消放在最前 | 改为**终局优先**（顺序不可颠倒） |

| 6 | **重启后作业永远"执行中"** | 孤儿作业无看门狗 | `GET` 时登记 `error`（"服务重启中断"）；列表只读不提交 |
