## 五、存储与扩展性

| 项 | 读数 |
|---|---|
| data 目录总量 | 132.9 MB |
| accounting.db | 7964.0 KB |
| security.db | 200.0 KB |
| uploads | 14.4 MB（6 个项目目录） |

**扩展性：不支持水平扩展**，依据（本项目已实测）：

1. **SQLite 单写者**：两个进程指向同一 `security.db` 会撞 `attempt to write a readonly database`（阶段 3 实测，直接导致 `/api/auth/me` 与 `create_user` 随机 500）；

2. **状态在本地磁盘**：`data/` 下的 JSONL（`events.jsonl`、`report_versions.jsonl`）与上传文件都是本地文件，多实例无法共享；

3. **无请求级分布式锁**：分析任务在进程内跑（`engine/analysis_jobs.py`），多实例会重复执行。

⇒ 当前架构是**单机单实例**设计。垂直扩容（更强 CPU/内存）可行，水平扩容需要先换存储层（DB + 对象存储 + 外部队列）。

## 六、根因分析（为什么法规库慢 7 秒）

`engine/legal_library.py::article_entries`（L89-121）的执行顺序：

```text
for r in LC.library_file_entries():      # ① 7680 条**全部**遍历
    if 关键词不匹配: continue
    d = _decorate_article(r)            # ② 每条都做版本装饰（读版本表、算状态）
    rows.append(d)
rows.sort(...)                          # ③ 全量排序
return rows[start:start+size]           # ④ 最后才切片分页
```

⇒ **① 全量 + ② 逐条装饰 + ③ 全量排序**，与 `page_size` 无关：要 20 条也要跑完 7680 条。这是 **O(N) 每请求**，而 N 会随法规入库继续增长。

**建议改法**（不动业务语义）：

- ② 的装饰**只为当前页的 20 条做**（把 `_decorate_article` 移到切片之后）；

- ① 的过滤用**预建索引**（法名/条款号/关键词倒排或简单的前缀索引表）；

- 或加**进程内缓存**（`legal_library.json` 很少变，可缓存解析结果 + 版本映射），缓存失效按文件 mtime。

> 预估：②③ 两项改造后 P50 可从 7300 ms 降到 **<100 ms** 量级（因为切片后只处理 20 条，排序也只需在过滤结果上）。

## 七、优化建议

| 编号 | 问题 | 类型 | 影响面 | 修复成本 |
|---|---|---|---|---|
| **PF-01** | **法规库检索 P50 7312.6 ms**：全量遍历 7680 条 + 逐条装饰 + 全量排序，最后才分页（O(N)/请求，随法规增长继续恶化） | 性能型 | 法规库/专题/材料 3 页 | **低**：把装饰移到切片后 + 加 mtime 缓存，预估降到 <100 ms |
| **PF-02** | **并发扩展性差**：P50 随并发线性恶化（1→30 并发恶化约 19 倍），RPS 饱和在 ~13 | 性能型 | 全站 | **中**：短期靠垂直扩容 + 减少每请求全量计算；长期需换 PostgreSQL + 对象存储 + 外部队列 |

| **PF-04** | 存储全在本地磁盘（DB + JSONL + uploads），备份/扩容都受限 | 灾备型 | 全站 | **中**：见阶段 9（备份）建议，一起考虑 |

## 八、压测边界（必须知道）

- **本机回环**压测：不含真实网络延迟与带宽限制，真实部署的绝对值会更高；

- 并发用**线程**模拟（`ThreadPoolExecutor`），不是多机压测；

- 数据规模为**当前隔离库**（2 个项目、22 份资料、8 MB 主库），不是生产体量；法规库 7680 条是真实全量；

- **单次采样的波动很大**：同一脚本在同一实例上两次采样，法规库 P50 分别为 7312.6 ms 与 3691.8 ms、RPS 峰值 13.7 与 32.2。报告中的判定**一律取较差值**（保守），不取有利值。

- 未做：长时间稳定性（内存泄漏/句柄泄漏）、峰值写入压测、多实例压测。
