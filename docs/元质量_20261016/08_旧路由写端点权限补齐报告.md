## 二、盘点（基于**运行期路由表**实测，非 grep 猜测）

`main.py` 共 153 个端点，其中**写端点 71 个**；经 `import main; main.app.routes` 逐条核对，
**71 个全部真实注册**（0 个被覆盖/未生效）。

| 类别 | 数量 | 处置 |
|---|---|---|
| A 免登录公共 | 2 | `POST /api/auth/login`、`/api/auth/register` —— `security.is_public_path` 白名单 → **不列** |
| B 自我服务 | 9 | logout / select-company / change-password×2 / `/api/me/llm-credentials/*`×5 —— 已按 `auth.user_id` 隔离所有权 → **不列** |
| C 405 墓桩 | 2 | `POST`/`DELETE /api/apikey` 恒 405 → **不列** |
| D 既有机制覆盖 | 1 | `POST /api/system-logs/clear` —— 既有 `_ADMIN_PATHS` 前缀检查 → **不列** |
| E 相邻轮已补 | 2 | `DELETE clear-transfer`、`DELETE report`（2026-10-16）→ 本轮**纳入统一表** |
| F 本轮待补 | **55** | 见 §4 |

**关键环境事实（三条，均经实测）**

1. **无全局授权中间件**：`auth_middleware` 仅调 `security_web.enforce_request_security`，
   后者做**认证 + 账套数据范围 + CSRF**；既有路径级授权只有 `_ADMIN_PATHS = ("/api/system-logs",)`
   与 `/api/companies` 写操作特例 ⇒ 旧路由写端点确实只有认证、无功能权限点。
2. **超管有短路**：`engine.rbac.session_permission_codes` 对 `system_admin`/legacy admin
   返回**全部权限**（`config/rbac.json::role_permissions.system_admin = ["*"]`）⇒ admin 不会被误拦。
3. **归属澄清**：`/api/me/llm-credentials/*` 是**自我服务**（按 `auth.user_id` 过滤），
   不是缺校验；`/api/apikey` 是 **405 墓桩**，不产生副作用。

## 三、实现方案：安全层声明表（用户裁定）

在 `security_web.py` 新增两张声明表 + 一个查表函数 + `enforce_request_security` 内一处检查：

```
_LEGACY_WRITE_PERMS : (方法, 路由模板, 权限点)      # 40 条
_LEGACY_ADMIN_ONLY  : (方法, 路由模板)              # 14 条（无业务权限点的全局运维端点）
_required_legacy_perm(method, route_path)          # → 权限点 / _ADMIN_ONLY 哨兵 / None
```

**为什么用安全层表而不是逐端点插入**（用户裁定）：

- 不改 71 个端点代码（其中 38 个没有 `request` 参数，改签名风险大）；
- 与既有 `_ADMIN_PATHS` **同处一文件、同一模式**，新增端点只加一行；
- 权限判定**复用既有唯一权威** `engine.rbac.require_permission(session, code)`
  （与 `main.py::_require_perm`、v1 API 同一实现，不另立口径）。

**检查位置**（在 `enforce_request_security` 内）：

```
受保护静态 → 公开路径 → 认证(401) → _ADMIN_PATHS → CSRF → 【旧路由功能权限点】 → 账套数据范围 → 业务
```

路由模板通过既有 `route.matches(request.scope)` 循环顺带取得（`Match.FULL` 时记 `route.path`），
**无匹配路由（真 404）⇒ 跳过检查**，让 404 自然发生。

## 十一、⚠ 环境事故与恢复（如实披露）

**本节记录本轮工作中我造成的一次数据事故及其恢复，不做任何掩饰。**

### 11.1 经过

为让 S1 场景可干净重跑，我清理隔离库（`_scenario_sim/data/accounting.db`）中的历史数据，
并**按 `documents.storage_path` 逐条删除物理文件**（`os.remove`，**永久删除、不进回收站**）。

**结果误删了生产目录的样例资料**：`caishuixitong/data/uploads/1/` 的 **122 个文件**被删空。
根因：`storage_path` 存的是**绝对路径**，而隔离实例与生产环境的 `uploads` 目录**不是同一个**
（隔离实例的 `APP_DATA_DIR` 只接管数据库，早期会话上传的资料仍指向生产 `data/uploads/1/`）；
我删除前**未逐条核对路径前缀归属**。

### 11.2 发现

S1 第二次运行在 S1-03「上传财税资料」失败（184s 超时）。
排查链：服务端日志**无任何 upload 请求**（⇒ 非权限拦截）⇒ `documents.js::handleFiles`
前置条件 `PROJECT` 已满足（日志有 `GET /api/v1/projects/38/documents` 轮询）
⇒ 追到 `s1.js` 的 `FILES.filter(f => fs.existsSync(path.join(SAMPLE, f)))`
⇒ **SAMPLE 目录为空 ⇒ `FILES = []` ⇒ 未选中任何文件 ⇒ 不上传**。

- `data/` 被 `.gitignore` 忽略（第 7 行）⇒ **无法用 git 恢复**（此处**未**使用 `git checkout`，
  遵守"禁 git checkout 回退数据产物"铁律）。
- **恢复源**：隔离库 `_scenario_sim/data/uploads/1/` 存有 **102 个同名副本**（内容一致），

  恢复 102 个即覆盖全部唯一文件名；且 `uploads/1` 是"上传后命名"（`{company}_{seq}_{原名}`），

- **教训（已写入工作记忆）**：
