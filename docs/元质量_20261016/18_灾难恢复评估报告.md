# 灾难恢复评估报告（阶段 9）

> 任务：META-QUALITY 阶段 9 · 灾难恢复评估  
> 日期：2026-10-17  
> 原则：**数据丢了能恢复，服务挂了能重启**  
> 方式：8 维度取证 + **真实备份/恢复演练**（4 步全跑）  
> 证据：`_quality/STAGE9_DR.json`（演练逐步读数）

---

## 一、结论

| 维度 | 判定 | 依据 |
|---|---|---|
| **数据备份** | **无** | 系统无备份功能：取证到的 7 处 backup 全是假阳性（清理 *_bk 表 / 税审规则文本）。本次演练证明**数据库可被在线快照**（S1 通过），但**没有人/没有调度在做**。 |
| **备份恢复** | **无（手工可行）** | 演练 S4：用备份覆盖可完整恢复（22 行全部回来、integrity=ok，耗时 0.005s）。但需**停服**，且无「一键恢复」入口。 |
| **服务重启** | 部分 | 无 systemd/supervisor/Windows 服务注册；靠手动双击 `start8001.bat`。进程崩溃后**不会自动拉起**（本轮多次出现「8001 未监听」即此因）。 |
| **故障转移** | 无 | 单机单实例；SQLite 单写者，多实例会撞 readonly（阶段 3 实测）。无主备/无切换。 |
| **降级** | 部分（业务级，非运维级） | 引擎有大量 `FALLBACK` 业务兜底（如 `_NO_BLIND_CONSTITUENT_FALLBACK`）；但**无运维降级开关**（如「停用 AI、只跑规则」「只读模式」）。 |
| **熔断** | **无** | 全库 0 处熔断（circuit breaker）。外部依赖（LLM、webhook）失败时仅单次 try/except，无「连续失败即熔断一段时间」的保护。 |
| **限流** | 有 | `main.py:12810` IP 级滑动窗口限流中间件；`security_web.py:372` 登录失败限流（带 Retry-After）。 |
| **幂等** | 部分 | ①分片上传幂等（`documents_api.py:126` 同 chunk_index 重传覆盖）；②风险复核对重复处置**幂等拒绝**（「本次未产生变更」）。但**分析任务/报告生成无幂等键**，重复提交会产生新任务/新版本。 |

**最要紧的一句**：**数据库本身能被安全备份与恢复（演练已验证），但系统没有把这个能力变成功能** —— 没有调度、没有保留策略、没有恢复入口，也没有人知道该怎么做。真出事时，恢复动作全靠临时判断。

## 二、备份/恢复演练（真实执行，4 步）

> 全程在临时目录进行；**源库只读复制，未做任何写入**。

| 步 | 动作 | 结果 | 耗时 |
|---|---|---|---|
| S1 | 在线备份 `VACUUM INTO` | 46 张表 / 4720.0 KB | 0.04 s |
| S2 | 备份校验 | `integrity_check=ok`；行数一致=True | — |
| S3 | 模拟灾难 | `documents` 从 22 行 → 0 行 | — |
| S4 | 从备份恢复 | `documents` 回到 **22 行**、`integrity=ok` | 0.005 s |

**演练结论**：

- ✅ **备份可行且在线**（`VACUUM INTO` 不需要停服务，是一致性快照）；

- ✅ **备份可校验**（`PRAGMA integrity_check` + 行数比对，两道）；

- ✅ **恢复可行**（覆盖即可，22 行全部回来）；

- ❌ **恢复必须停服**（覆盖文件时服务持有句柄）；

- ❌ **没有任何自动化**：备份要人记得做，恢复要人会做。

## 三、优化建议

| 编号 | 问题 | 类型 | 影响面 | 修复成本 |
|---|---|---|---|---|
| **D-01** | **无备份调度**：能力有（演练已验证）、功能没有 | 灾备型 | 全系统数据 | **低**：加 `scripts/backup.py`（`VACUUM INTO` + 保留 N 份 + 校验）+ 计划任务 |
| **D-02** | **无恢复入口**：恢复要停服 + 人工覆盖 | 灾备型 | 全系统数据 | **低**：加 `scripts/restore.py`（先备份当前库再覆盖，失败自动回滚） |
| **D-03** | **服务崩溃不自动重启**（本轮多次「8001 未监听」） | 灾备型 | 全站可用性 | **低**：注册 Windows 服务（nssm）或加看护脚本 |
| **D-04** | **无熔断**：LLM/webhook 连续失败会一直重撞 | 灾备型 | AI 辅助/通知 | **低**：连续 N 次失败 → 冷却 M 秒（内存计数即可） |
| **D-05** | **分析任务/报告无幂等键**：重复提交产生新任务/新版本 | 数据错误型 | 分析/报告 | **中**：加 `Idempotency-Key`，同 key 短路返回 |
| **D-06** | **无运维降级开关**（只读模式/关外部依赖） | 灾备型 | 全站 | **低**：加 2 个配置项并在关键入口判断 |

> D-01/D-02/D-03 是**投入小、救命**的三条，建议优先做。

## 四、边界

- 演练在**隔离数据副本**上进行，未触碰生产库；未做「真删生产库再恢复」的破坏性测试。

- 未验证：备份文件**异地存放**、备份**加密**、**跨版本兼容**（旧备份能否被新版本读）。

- 未做：多机演练、断电演练、磁盘满演练。
