## 二、最重要的发现：静态资源版本号漏项（系统级）

**这不是我改出来的问题，是本来就存在、且被闸门漏掉的。**

- 现象：`sync_asset_versions.py` 的正则只匹配**已经带 `?v=`** 的引用；
  闸门 `check_static_asset_cache_version` 同样只查"已有 `?v=` 是否过期"。
  ⇒ 对"**根本没有 `?v=`**"完全无声。
- 实测：**22 个页面 / 40 处**引用没有版本号，包括
  `risks.js`、`projects.js`、`extract.js`、`documents.js`、`users.js`、
  `reports.js`、`rules.js`、`templates.js`、`rule_versions.js`、`security.js` 等。
- 后果：浏览器按**含 query 的 URL** 缓存。这些文件的前端改动**可能永远到不了用户** ——
  与 2026-10-02 那次"改了这么多报告还是没变化"是同一类事故，只是更隐蔽。
- 修复：同步工具新增"补齐缺失的 `?v=`"；闸门新增 ERROR 判据。补齐后引用数 **84 → 124**。
- **这解释了此前"资源版本已同步（28 页 / 55 引用）"的自信从哪来**：
  统计口径只覆盖了"已带版本号的引用"，**声称的范围大于实际覆盖的范围**。
  再次印证项目铁律：判据要先量化再断言。

## 三、R-02：把"复制粘贴"变成"单一权威"

### 收敛前（实测）

| 函数 | 份数 | 差异 |
|---|---|---|
| `_session` | **10** | 9 份完全相同，1 份写法略异（功能等价） |
| `_call` | **8** | 结构完全同构，只差异常类 |
| `_require_perm` | **6** | 完全相同 |
| `_request_perm` | **6** | 完全相同（另有 `_perm`、`_admin` 变体） |

### 为什么这必须修（不是洁癖）

`_require_perm` 是**权限判定的边界**。10 份副本意味着"改一处忘一处"，
一旦有人只在其中一处加了新校验，就会出现"某些接口用旧口径判权限" ——
**阶段 2 登记的 71 个权限缺口，机制上就是这么来的**。

### 做法

- 新增 `engine/api_common.py`：`session_of` / `admin_of` / `require_perm` / `request_perm` / `call_boundary`；
- **保留 `_call` 这个壳**（8 个文件几十处调用，改签名风险远大于收益），
  但它只做一件事：声明"本域捕获哪一类异常"，逻辑全部转发 `call_boundary`；
- 迁移脚本 `scripts/_r02_api_boundary.py`：AST 定位行区间（不靠正则切字符串）、
  迁移前备份 `.r02_backup/`、逐文件 py_compile；
- 闸门 `check_api_boundary_single_source`：再定义那几个函数即 ERROR，`_call` 未转发也 ERROR。

### 关键设计：`call_boundary` 为什么要求显式异常类型

不能写成"捕获所有 Exception 再看有没有 status" —— 那会把**代码缺陷（NameError 等）
伪装成 400**，把崩溃掩盖成"用户输错了"。这是项目明令禁止的静默吞异常。
所以：**逻辑一份，异常类型由调用方声明**。测试 `test_call_boundary_does_NOT_swallow_undeclared_errors`
专门锁这条。

### 验收

- 19 个文件迁移后全部编译通过；调用点一处未改；
- 实测全部域接口：`/ projects` `/risks` `/system/*` `/reports` `/rule-versions`
  `/report-templates` `/users` `/roles` `/ai-assist` `/industry-indicators` `/legal-library`
  `/tax-models` 全部 200；未登录一律 401；
- 闸门反向验证：注入一份 `_session` 副本 → 精确报"第 41 行重新定义了 `_session`" → 还原后 0 问题；
- 相关域既有测试 21 项失败 **全部在 baseline**，且 **stash 往返对照**（把 R-02 改动暂存后
  同样失败）证明**不是本轮引入**。

## 四、O-01：print → logger（138 处）

### 为什么分两批而不是一次清干净

一次性改 398 处会同时改动几十个业务文件的执行路径，风险远大于收益；而且
**半迁移比不迁移更危险**（日志格式不一致、异常栈丢失、有的 print 是给命令行看的回显）。
所以上一轮只落基础设施，本轮迁移**风险最低、收益最高**的四个文件：

| 文件 | 迁移 | 说明 |
|---|---|---|
| `database.py` | 51 | 建表/加列/迁移日志 —— 正是"启动时发生了什么"最需要留痕的地方 |
| `main.py` | 30 | 启动摘要/缓存恢复等；保留 2 处命令行回显 |
| `audit.py` | 11 | 审计动作 |
| `engine/enterprise_report.py` | 46 + 1 手工 | 报告生成链（`file=sys.stderr` 那处手工改） |

**分级口径**（不是一律 info）：含"失败/错误/异常/告警/超时/不可用/冲突/跳过" ⇒ `warning`，其余 `info`。

### 一个真实的技术障碍

`engine/__init__.py` 会导入 `context/memory/phase1…` 等重量级模块，而 `database.py`
若 `from engine.logging_setup import ...` 会形成**循环导入**。
⇒ 日志实现下沉到根目录 `logkit.py`（只依赖 `runtime_storage`），
`engine/logging_setup.py` 保留同签名转发，既有调用点不改。

### 验收

- 138 处迁移 + `main.py` 30 处后，相关域测试失败集合**与迁移前逐条一致**；
- 闸门 `check_print_budget`：总数从 398 降到 **50**，预算冻结 55（**只许减不许增**）；
  反向验证：注入 4 处 print → 精确报"print 4 处超过预算 2"。

## 五、H-05：批量解析（真正的高频痛点）

### 先纠一个上轮的说法

上轮报告写"风险复核已有 bulk_review 后端、前端未接" —— **实际前端已经接了**
（`risks.js` 有全选本页/清空/批量执行，走 `/risks/bulk-review`）。资料页也有批量删除。
这是我在写建议时**没有核对前端实现**造成的失真，本轮更正。

### 真正的缺口：解析页只能一份份点

解析页是「下拉选一份 → 点开始解析」。恢复后正好有 **102 份待解析资料** ⇒ 要点 102 次。

### 实现

- `engine/extract_service.parse_batch`：逐条独立执行、部分失败不回滚、单次上限 50、
  `only_pending` 默认只挑「待解析 / 解析失败」，**不重解析已成功的**（省时间也省风险）；
- `POST /api/v1/projects/{id}/extract-batch`（`document.write` 权限）；
- 页面新增「批量解析」面板：范围选择 + 本次最多（1~50）+ 逐条结果（成功/失败原因）。

### 验收（真实 HTTP）

```
total=3 ok=3 failed=0
  {'document_id': 363, 'status': 'ok', 'tables': 1, 'fields': 6, 'issues': 2, ...}
  {'document_id': 362, 'status': 'ok', 'tables': 1, 'fields': 5, 'issues': 0, ...}
  {'document_id': 367, 'status': 'ok', 'tables': 1, 'fields': 4, 'issues': 0, ...}
```
`limit=99` 被挡（422）。测试 8 项，其中一条抓到**真 bug**：`int(0 or 50)` 会把 `limit=0`
静默变成 50（用户以为跑了 0 份，实际跑了 50 份）—— 已修并加注释。

## 六、O-03 / O-04

### 阈值告警（5 条规则）

| 规则 | 阈值 | 级别 | 冷却 |
|---|---|---|---|
| `ERR_RATE_HIGH` | 5xx > 1% 且样本 ≥50 | critical | 15 分钟 |
| `P95_SLOW` | P95 > 3000ms 且样本 ≥50 | warning | 30 分钟 |
| `DISK_LOW` | 可用 < 15% | critical | 6 小时 |
| `BACKUP_STALE` | > 48 小时未备份 | critical | 12 小时 |
| `JOB_FAIL_HIGH` | 作业失败率 > 20% 且样本 ≥10 | warning | 1 小时 |

三条设计原则：
1. **规则是数据**：新增阈值只加一行，不改判定分支；
2. **必须冷却**：持续故障不冷却会刷屏，告警本身失效（有专门测试）；
3. **取不到数据 ≠ 正常**：`_backup_age_hours()` 返回 None（从未备份）必须触发，
   不能当绿灯 —— 这是最危险的假阴性（有测试）。

实测：`GET /api/v1/system/alerts` 返回 5 条规则当前值与是否触发；
本机当前 `BACKUP_STALE=17.3 小时前`（未超 48h，不报），磁盘 35.6%（不报）。

### 请求关联 id

- 中间件读 `X-Request-ID`（有则沿用），没有则生成 8 位；
- 写入 `contextvars`（**不是 thread-local**：async 下同线程会串味，有测试锁）；
- 日志每行带 `[rid=...]`，无上下文时显示 `-`；
- 响应头回传。
- 实测：带 `X-Request-ID: mytest-1234` 请求 → 响应头原样返回该值；不带则生成 `8d3f76d4`。
