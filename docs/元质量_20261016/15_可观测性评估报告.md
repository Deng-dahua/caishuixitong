| 维度 | 判定 | 关键事实 |
|---|---|---|
| **日志** | **不达标** | 产品代码 **print 412 次 vs logger 只有 6 次**；14 个功能域**全部 logger=0**。print 无级别、无结构化、不可采集/检索 —— 线上排障只能靠翻 stdout 文本 |

| **链路追踪** | 部分 | `trace_id` 44 处，但集中在 main.py（11 处）；多数 API 域 0 处 ⇒ **跨模块请求无法串起来** |

| **仪表盘** | 部分 | 有业务数据大屏（/dashboard）与引擎仪表盘；**无运维指标仪表盘**（CPU/内存/QPS/错误率趋势） |

> **一句话**：**审计强、日志弱、指标零、告警薄**。系统能回答「谁做了什么」，但**回答不了「现在跑得怎么样、哪里慢、为什么错」**。

## 四、优化建议

| 编号 | 问题 | 类型 | 影响面 | 修复成本 |
|---|---|---|---|---|
| **O-01** | **产品代码 print 412 次、logger 仅 6 次**：无日志级别、无结构化、无法按模块/级别采集。线上排障只能翻 stdout | 可观测型 | 全部后端 | **中**：先加统一 `logging` 配置（`caishui` logger + 文件轮转 + JSON 格式），再把 412 处 print 分批替换（高价值处优先：异常、审计、任务状态） |
| **O-02** | **零指标**：无 CPU/内存/QPS/延迟/错误率采集，无法回答「能扛多少并发」「哪里慢」 | 性能型 | 全部后端 | **中**：加 `/metrics`（Prometheus 文本格式，纯标准库即可实现），先暴露 6 个基础量（请求数/延迟分位/错误率/活跃会话/DB 大小/队列长度） |
| **O-03** | **告警只有「完成通知」**，无阈值告警：错误率飙升、任务连续失败、磁盘将满时无人知道 | 可观测型 | 全部后端 | **低**：复用已有 webhook 通道，加 3 条规则（错误率>5%/任务连续失败 3 次/磁盘>90%） |
| **O-04** | **trace_id 覆盖率低**：只有 main.py 11 处，API 域基本 0 处 ⇒ 跨模块请求无法串联 | 可观测型 | 全部 API | **低**：在鉴权中间件统一生成 `X-Request-ID` 注入 `request.state`，日志里带上它即可，无需改各端点 |
| **O-05** | **无运维仪表盘**：业务大屏只展示风险数据，看不到系统自身健康度 | 可观测型 | 运维 | **中**：新增 `/ops` 页（读 /metrics），展示 QPS/延迟/错误率/DB 大小 |

> 审计日志已达标准，**不建议再动**（它已是本系统最强的可观测能力，240 处埋点 + 唯一权威 `audit_trail`）。

## 五、判定口径

| 维度 | 判据 |
|---|---|
| 日志 | 该域实现文件内 `logger.info/warning/error/debug/exception` 的真实调用数；**print 不计为达标**（不可分级、不可采集） |
| 指标 | 全库 `prometheus`/`/metrics`/`psutil`/`cpu_percent` 等命中数 |
| 链路追踪 | `trace_id`/`request_id`/`X-Request-ID` 的真实引用数（≥5 判有，1~4 判部分） |
| 告警 | 是否存在阈值/触发条件/升级策略（仅有通知、无阈值不算告警） |

| 审计日志 | 该域 `_audit`/`audit_log` 埋点数（≥3 判有，1~2 判部分） |
