# 裁定：S3-05「复核专家与报告生成」（MQ2-O4）

> 任务编号：**MQ2-O4**（用户裁定事项）
> 日期：2026-10-17
> 触发：阶段 2 的 S3-05 判据在补权限后失败，提示
> `无权执行该操作（需要权限：report.generate；当前角色：review_expert）`

---

## 一、问题

S3（复核专家审批）的第 5 步原判据为「**复核专家在界面上点『生成报告』，产出带复核标识的报告**」。
MQ2-D1 补权限后该步骤被 **403 拦截**，因为 `config/rbac.json` 中 `review_expert` **无** `report.generate`。

两种解释必须择一：
- **(a)** 复核专家确实需要 `report.generate` ⇒ 改 `rbac.json` 加权限；
- **(b)** 复核专家不该出报告 ⇒ **判据写错了**，应改判据。

---

## 二、取证（四条，逐条可自查）

### 证据 1｜角色设计已书面排除该权限

`config/rbac.json` → `roles[review_expert]`：

> **独立复核岗：只读项目与资料，可复核风险与查看审计留痕，不发起分析、不导出报告。**

⇒「**不导出报告**」是**刻意设计**（与 `auditor` 的"只读监督岗"并列的职责分离），不是遗漏。

### 证据 2｜没有独立的「复核审批」端点

`reports_api.py` 全部端点：
`GET /reports/meta`、`GET /reports/versions`、`GET /reports`、`POST /projects/{id}/reports`、
`GET /reports/{id}`、`GET /reports/{id}/download`。

⇒ 「复核标识」**只能**随「生成报告」产生（该端点 `summary` 亦明写
「生成报告（视图 + 格式 + **复核标识**）」）。
**但**——该端点请求体文档同时写明：

```
"reviewed": true|false|null,   # 省略 ⇒ 按账套**实际**处置记录推断
```

⇒ 复核标识**不必手填**；可省略，由后端推断。

### 证据 3｜后端已实现「按处置记录推断」，含复核人

`engine/report_service.py::build_document`（约 693–705 行）：

```python
reviews = _reviews(cid)                     # 取该账套的复核处置记录
done_any = any((reviews.get(str(f.get("risk_no") or "")) or {}).get("reviewed")
               for f in findings)
if reviewed is None:
    reviewed = bool(done_any)               # 省略 ⇒ 按事实推断
who = str(reviewed_by or "")
if reviewed and not who:
    for f in findings:                      # 从处置记录取**复核人**
        m = reviews.get(str(f.get("risk_no") or "")) or {}
        if m.get("reviewed"):
            who = str(m.get("updated_by") or ""); break
review_label = "已复核" + ("（%s）" % who if who else "") if reviewed else "未经人工复核"
```

且 `engine/risk_review.py::_actor(session)` 把处置留痕的 `updated_by` 写成
**会话用户名**（`str(getattr(session, "username"))`）⇒ 复核人是**服务端取的**，不可由客户端伪造。

前端亦与此一致：`static/reports.html` 的「人工复核标识」下拉**默认值即空**
（`<option value="">按实际处置记录推断</option>`），`reports.js` 发送
`reviewed: rv === '' ? null : (rv === '1')`。

⇒ **「复核」与「出报告」本就设计为两个角色**：复核专家处置 → 持 `report.generate` 的角色生成 →
复核标识与复核人由后端推断带出。

### 证据 4｜若给复核专家加权限，将破坏职责分离（SOD）

该角色设立目的即「**独立**复核」。若复核人自己出报告，则"独立复核"名存实亡
（原本由他人复核 → 现在是自核自出）。这与 `auditor`（只读监督）同属**刻意的职责分离**设计。

## 三、裁定

> **不改 `config/rbac.json`** —— `review_expert` 保持**无** `report.generate`。
> **修正 S3 判据**为真实设计链路。

理由归纳：证据 1（设计书面排除）+ 证据 3（后端已实现推断，说明两角色分工是既定设计）
⇒ 冲突的根源是**判据写错了**（阶段 2 由我编写），不是权限模型缺一行。

**新判据（更强，不是放宽）**：
复核专家**复核处置**（`risk.review`）→ 持 `report.generate` 的角色生成报告（**不勾复核标识**）
→ 断言报告 `reviewed=true` 且复核人**取自处置记录**。
原判据只验证"能生成"；新判据验证**跨角色的复核→报告链路真的贯通且标识由事实推断**。

### 5.1 关于推断出的复核人是 `sim_advisor` 而非 `sim_expert`

这是**次序效应，不是缺陷**：推断取「**序遍历中第一条**有处置记录的发现」；
本次运行中税务师（S2）处置了 13 条、复核专家（S3-05）处置了 1 条，故先命中税务师。
判据因此断言「复核人 ∈ **实际做过处置的用户集合**」而非写死某个用户名——这才是该机制的**正确不变量**。
（若要"复核人=最后处置者"需改推断口径，属另一议题，**本轮未改**，登记为观察项 MQ2-O9。）

### 6.1 S4-04 失败的归因（**非本裁定引入**）

本轮 S4-04（配置权限）因 `#btn-new` 点击超时失败。**决定性归因**：

1. 服务端日志显示该时段 `/api/auth/me` 返回 **500**（`sqlite3.OperationalError: attempt to write a readonly database`）；
2. ⇒ `rbac-nav.js` 权限视为空 ⇒ 隐藏全部 `data-perm` 节点 ⇒ `#btn-new` 不可点（MQ2-O8）；
3. 该错误**跨轮次存在**：**最早那轮日志 52 次**、server2–8 **0 次**、本轮 **8 次**
   ⇒ 属**既有环境/DB 并发问题**，非本裁定改动引入（异常发生在 `get_session`，我的权限检查在其**之后**）；
4. 高发条件与本轮已知环境因素一致（`get_session` 每请求都写 `security.db`，WAL 下跨进程访问即可能只读）。

⇒ 判定为**测试环境 flake**。**已随本轮重跑核对**：S4 **5/5 通过**（S4-04 正常通过）
⇒ 结案为环境瞬时问题，**非产品缺陷、非本裁定引入**。
