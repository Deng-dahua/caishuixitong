## 一、结论

| 环节 | 是否自动化 | 是否可靠 | 是否可追溯 | 问题 |
|---|---|---|---|---|
| **持续集成** | 无 | 否 | — | **无 CI 配置**（`.github/`、`.gitlab-ci.yml`、`Jenkinsfile` 全部不存在）。提交代码不会自动构建。 |
| **持续测试** | 无（有手动脚本） | 否 | — | 无自动化测试流水线；但有 **62 个 `_verify_*.py` 脚本 + 2209 条 pytest 用例**，可手动一键跑。能力有、自动化没有。 |
| **持续部署** | 无 | 否 | — | 部署方式：手动双击 `start8001.bat`（或 `start.sh`）。 |
| **蓝绿部署** | 无 | 否 | — | 单实例单端口，无蓝绿。 |
| **灰度发布** | 无 | 否 | — | 无流量切分能力。 |
| **回滚** | 部分 | 是 | 是 | **代码**可回滚（git 有完整历史，本轮已用 `git checkout` 恢复过文件）；**数据**无版本化（DB 无迁移框架，回滚代码不保证兼容旧表结构）。 |
| **版本管理** | 部分 | 是 | 是 | git 提交历史完整（本轮新增 4 次提交）；但 **0 个 tag**，无版本号体系 ⇒ 「当前是哪个版本」只能靠 commit hash。报告里有 `V81/V84` 等版本号，但那是**报告版本**不是**系统版本**。 |
| **环境管理** | 部分 | 是 | 是 | 有 `APP_DATA_DIR` 环境变量隔离（本轮所有测试都用独立目录，**机制有效**）；但无「开发/测试/生产」三套配置文件的约定，也没有环境标识。 |

**汇总**：自动化 **0** · 部分 **4** · 无 **4**（共 8 环节）。

**一句话**：**这是一套「手工交付」的系统** —— 没有 CI、没有 CD、没有灰度、没有版本号，但有**很厚的自检脚本**（62 个）与**完整 git 历史**。换句话说：**质量意识在，工程化基础设施不在**。

## 三、优化建议

| 编号 | 问题 | 类型 | 影响面 | 修复成本 |
|---|---|---|---|---|
| **CI-01** | **无版本号**：0 个 tag，「当前什么版本」说不清 | 文档型 | 交付/验收 | **极低**：`git tag v1.0.0`（当前状态打第一个基线），之后每次交付打 tag |
| **CI-02** | **无自动测试流水线**：2209 条用例靠人记得跑 | 效率型 | 代码质量 | **低**：加 `.github/workflows/ci.yml`（或本地 `pre-push` hook）跑 `pytest -q` + `tools/audit_consistency.py` + `tools/verify_release.py` 三道 |
| **CI-03** | **无 CHANGELOG 与版本号联动** | 文档型 | 交付 | **低**：与 DOC-05 合并做 |
| **CI-04** | **回滚只回代码不回数据**：DB 无迁移框架 | 灾备型 | 升级/回滚 | **中**：加轻量迁移记录表（`schema_version` + 每次 DDL 登记），回滚前检查兼容性 |
| **CI-05** | 无环境标识（开发/测试/生产共用一份代码无标识） | 效率型 | 运维 | **低**：加 `APP_ENV` 并在启动日志与页脚显示 |

> 建议先做 **CI-01 + CI-02**（合计半天工作量），投入产出比最高：版本可说清、回归可自动。

## 四、边界

- 本阶段**不要求**系统具备云原生 CI/CD（当前是单机内部系统，强行上灰度/蓝绿无收益）；判定按「**有没有把已有能力自动化**」而非「是否先进」。

- 未评估：构建产物体积、依赖锁定完整度（`requirements.lock` 存在）、供应链安全扫描。
