## 二、O1｜整改记录不再接受不存在的账套

**修前**：`create_remediation` 直接把 `company_id` 写进 `RemediationRecord`，**无任何存在性校验**
⇒ 实测 `company_id=999999` 也能建成功，产生指向不存在账套的**孤儿台账**。

**修后**（`main.py`）：

```python
from database import RemediationRecord, Company
if not db.query(Company).filter(Company.id == company_id).first():
    raise HTTPException(404, "账套不存在")
```

**口径**：与 `delete_company` 同源（都查 `Company` 行），不新造一套判定。

## 三、O2｜复核不存在账套返回 404（不再冒充 500）

**修前**：`review_tax_risk_docs` 不校验账套，一路走到 `_run_analyze` 抛异常 ⇒ **500**。
这在语义上是错的：**客户端传了不存在的账套**属 4xx，不是服务端故障；
500 还会让前端/监控误判为系统异常。

**修后**：先查 `Company` 行，不存在即 `HTTPException(404, "账套不存在")`。

## 四、O5｜删项目级联处置资料

### 4.1 修前的实际后果（实测）

- 删项目 10 后，`documents` 仍残留 **20 条**；
- 另发现 **102 条 `project_id=1` 的孤儿资料**（项目 1 早已不存在）；
- 后果：**项目删了、资料还在** —— 列表按项目过滤查不到，按账套统计却算进去，数据自相矛盾。

### 4.2 修后口径（两级，默认不误删）

| 情形 | 行为 |
|---|---|
| 项目下有资料、**未传** `cascade=true` | **409**，消息报出资料数量，要求调用方显式确认 |
| `cascade=true` | 删 `documents` 及其解析子表；**物理文件 `move_to_trash`（可恢复）** |
| 项目下无资料 | 直接删除（与修前一致，不打扰用户） |
| 账套与报告 | **不碰** —— 报告删除的唯一权威仍是 `main.purge_company_analysis_artifacts` |

**为什么不默认级联删除**：删除项目时若静默带走 N 份资料，属**不可逆的连带破坏**；
按「删除优先进回收站」铁律，物理文件也只**移入回收站**（`move_to_trash`），

### 4.3 ⚠ 修复过程中我自己引入的第二处缺陷（同轮发现并修复）

**首版实现**无条件执行 `SELECT id, storage_path FROM documents WHERE project_id=?`，
而 `documents` 表是**运行时按需创建**的（`engine/document_store.ensure_schema`）——
**老库/新库可能根本没有该表** ⇒ 抛 `no such table: documents`，把"删项目"整个打死。

**实测证据**：全量回归中 `test_project_api::test_project_api_end_to_end` 由绿变红（新增 1 项失败）。

**修法**（不吞异常，显式判表）：

```python
has_docs = conn.execute(text(
    "SELECT 1 FROM sqlite_master WHERE type='table' AND name='documents'")).fetchone() is not None
docs = conn.execute(...).fetchall() if has_docs else []
...
if has_docs:
    for table in (...):   # 每个子表也先判存在
        exists = conn.execute(... name=:t ...).fetchone() is not None
        if exists: conn.execute("DELETE FROM ...")
```

**并加 2 条防复发用例**：
- 静态：函数体内必须有 `sqlite_master` 守卫，且**不得**用裸 `except Exception` 掩盖；
- 运行期：子进程起一个**没有 documents 表**的库，建项目后直接删除必须成功。

## 五、O6｜上传目录跟随 `APP_DATA_DIR`（实测已闭环）

**上轮登记为"未完全跟随"**。本轮**实测复核**：

```
$ APP_DATA_DIR=...\_probe_data python -c "import main; print(main.UPLOAD_DIR)"
UPLOAD_DIR = ...\_probe_data\uploads
$ ... print(main._get_company_upload_dir(1))
           = ...\_probe_data\uploads\1
```

⇒ 代码层**已跟随**（`UPLOAD_DIR = str(RUNTIME_UPLOAD_DIR)`，`runtime_storage.UPLOAD_DIR` 由 `APP_DATA_DIR` 派生）。

**结论**：O6 不是代码缺陷。上轮误删事故的真实成因是**历史遗留数据**——
早期会话上传的资料 `storage_path` 写的是**绝对路径**且指向生产 `data/uploads/1`，
而隔离实例的 `APP_DATA_DIR` 只改变**新**文件落点，**不改旧记录的绝对路径**。

⇒ O6 改判为「**已闭环（代码正确）**」，并把真正的教训固化到铁律：
**`storage_path` 是绝对路径 ⇒ 跨环境操作前必须按环境校验归属**（已写入 `MEMORY.md`）。
