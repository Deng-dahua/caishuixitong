## 一、（b）P0 两条

### 1. PF-01 法规库检索性能

| 项 | 修前 | 修后 |
|---|---|---|
| `article_entries(limit=20)` 纯函数 | **3532 ms** | **4.7~32.5 ms** |
| `GET /api/v1/legal-library` HTTP | **3692~7313 ms** | **36~45 ms**（首次冷缓存 121 ms） |
| 单次请求的版本查询次数 | 7692 × 4 | ≤ 本页不同法数（通常 <20） |

两处根因，都修了：
1. `legal_citation.library_file_entries()` 每次请求重新解析 7.6k 条 JSON（26 ms）
   ⇒ 加 **(文件名, mtime_ns, size)** 缓存（文件一变键就变，不会读到旧内容）；
2. `article_entries` **先全量装饰、最后才分页** ⇒ 改「筛选 → 排序 → 切片 → 按法去重装饰」。

**行为不变**：`total=7692`、排序键 `(law, article)` 升序、`only_current` 语义、分页语义全部实测一致。

守护：`tests/test_legal_library_perf.py`（9 项）。核心判据是**装饰次数必须等于本页条数**；
反向验证：把实现改回"全量装饰" ⇒ 2 项精确变红（已实测）。

### 2. S-10 数据备份 + D-02 恢复入口

**能力**（`engine/backup.py`）：
- **在线一致快照**：SQLite 用 `VACUUM INTO`（不停服、不受 WAL 影响），**不做文件 copy**；
- **可验证**：每份备份写 `manifest.json`（每文件 sha256 + 字节数 + 库 `integrity_check` + 行数）；
- **保留策略**：默认 14 份（`APP_BACKUP_KEEP`），`pre-restore` 快照永不轮转；
- **轮转走权威出口**：`runtime_storage.purge_file`（进回收站，可恢复），不用 `os.remove`。

**调度**：`main.py` lifespan 起守护线程，每小时判一次 `is_due()`（默认 24h 间隔）。
**实测**：服务重启后 17:17:59 自动生成了第一份 `daily` 备份 —— 不是"配了没跑"。

**入口**：
- 界面：侧栏「💾 备份与恢复」（`/backup`，仅管理员）—— 清单 / 立即备份 / 校验 / 恢复指引；
- 命令行：`scripts/backup_cli.py list|create|verify|restore`。

**恢复为什么不在网页上点一下就做**：覆盖运行中的 SQLite 文件会损坏库。网页给的是
**可执行命令**（停服后执行），恢复前自动生成 `pre-restore` 后悔药，恢复后自动核对行数。

守护：`tests/test_backup_restore.py`（13 项），含 4 项反向验证 + 事故回归。

## 五、没做的 & 为什么（不做假账）

| 项 | 为什么没做 |
|---|---|
| O-01 的 412 处 `print` 全量迁移 | 一次性改几十个业务文件的执行路径，风险远大于收益。正确顺序是「基础设施 → 新代码只用 logger → 分批迁移」，本轮完成了前两步。**半迁移比不迁移更危险**（日志格式不一致、异常栈丢失）。 |
| H-05 10 个模块的批量操作 | 需逐页改前端交互（全选、批量提交、部分失败处理），工作量大且容易引入交互缺陷；风险应单独一轮做。 |
| R-02 `_session`/`_call` 等重复实现 | 涉及 9 个 API 文件的公共层收敛，改错会连带权限口径漂移；应作为独立重构轮。 |
| PF-02 并发扩展性（RPS 13~32） | 根因是 SQLite 单写者 + 每请求全量统计，属架构级改造（换库或加缓存层），不适合在功能轮里夹带。 |
| DOC-03 独立部署手册 | 运维手册 §1/§6 已覆盖部署与发版要点，单独成册留待与交付流程一起定稿。 |
