# 排查：服务器进不去（`start8001.bat` 双击后静默不启动）

- 日期：2026-10-14
- 涉及文件：`start8001.bat`、`scripts/start_server.bat`、新增 `.gitattributes`
- 提交：`11f5cd7e`
- 结论：**根因是启动脚本以 LF-only 行尾检出**，与「端口被占」「代理」「前后端不一致」等此前怀疑方向**全部无关**。

---

## 一、现象

用户报告：「服务器还是进不去」。上一轮已把临时进程停掉、让用户自行双击 `start8001.bat`，
但双击后浏览器仍打不开 `http://127.0.0.1:8001`。

## 二、排查（全部为实测，非推断）

| 检查项 | 结果 |
|---|---|
| 8001 是否监听 | **无监听**（`netstat` 为空） |
| 是否有 python 进程 | **无** |
| 直连测试（`curl --noproxy '*'`） | `Failed to connect`（非 502，说明本机确实没服务） |
| `.venv\Scripts\python.exe` | 存在 |
| `uvicorn` | 已安装（0.34.3） |
| `import main` | 成功，`app` 存在 |
| 手动跑 `uvicorn main:app` | **成功**，8001 LISTENING，`GET /` 302、`/api/v1/...` 401 |

⇒ 服务端本身完全正常。问题在**启动脚本本身**。

**决定性实验**：真实运行一次 `start8001.bat`，捕获其全部输出：

```
'宝守护变量，否则用户在界宝?rem' 不是内部或外部命令
'UARD' 不是内部或外部命令
Starting on http://127.0.0.1:8001  (Ctrl+C to stop)
'""' 不是内部或外部命令          ← 这一行本该是启动 python 的命令
请按任意键继续. . .
```

最后一行退化为空字符串 ⇒ **python 从未被执行**；同时 `set` 语句被拆碎。

## 三、根因（字节级确认）

```
start8001.bat              size=1012  CRLF=0  bareLF=21  nonascii=384
scripts/start_server.bat   size= 460  CRLF=0  bareLF=11  nonascii=  0
```

两个脚本**全部是 LF 行尾**（无 CRLF）。

**失效机制**：

1. `cmd.exe` 按系统 ANSI 代码页（本机 GBK/936）解码批处理行的内容；
2. 文件内容是 UTF-8，中文注释的字节按 GBK 每 2 字节重组；
3. 当某行（含前导 `rem `）的多字节部分为**奇数长度**时，最后一个字节会与行尾换行符配对；
4. **LF-only** 情况下被吃掉的是 `\n` ⇒ **该行没有行尾符了** ⇒ cmd 继续读下一行，把两行**粘连**；
5. 粘连后 `rem`/`set` 不再处于行首：`set "CODEBUDDY_SAFE_DELETE_BULK_GUARD="` 被拆出 `'UARD'`，
   最终 `"%APP_PYTHON% -m uvicorn ...` 一行退化为 `""`。

**为什么 CRLF 能修好**：CRLF 下被吃掉的是 `\r`，`\n` 幸存 ⇒ 仍然正常断行。

**旁证**：`scripts/start_server.bat` 是**纯 ASCII**（`nonascii=0`），
不存在字节错位，因此**一直是可用的**——这也说明「杀手是 LF + 多字节」的组合，
而不是「中文注释」本身。

### 何时引入（git 时间线）

`git log --follow` 三个提交的 bat 行尾/字节实测：

| 提交 | CRLF | bareLF | nonascii | 状态 |
|---|---|---|---|---|
| `d63773d8`（最早） | 0 | 10 | **0** | 纯 ASCII ⇒ **LF 无害，可正常工作** |
| `142f7c32`（batch-delete 三层根治） | 0 | 17 | **261** | **首次引入中文注释** ⇒ **从这一刻起失效** |
| `d1eae9ad`（Secure cookie） | 0 | 21 | 384 | 继续失效（又补了中文注释） |

⇒ 故障在 `142f7c32` 引入。这也解释了此前的误判：纯 ASCII 时期真跑是好的；
加了中文注释后**再没人真跑过这个 bat**，于是「功能正常、只是注释乱码」的旧结论一直沿用。
（该旧结论已在 `memory/2026-10-14.md` 中标注勘误。）

> ⚠ 勘误：项目早期结论「bat 中文注释在 cmd 下乱码但功能性行纯 ASCII ⇒ 不影响启动」
> **是错的**。当时是拿等价命令（不含 bat 解析过程）验证的，没有真跑这个 bat。
> 真实情况是：中文注释 + LF 行尾会**直接导致启动失败**。

## 四、修复

1. 两个 bat 行尾统一为 **CRLF**（文本内容一字未改）；
2. 新增 `.gitattributes`：

```
*.bat text eol=crlf
*.cmd text eol=crlf
```

从**仓库层面**锁定 CRLF，不依赖任何机器的 `core.autocrlf`。

## 六、给用户的正确用法

双击 `C:\Users\Administrator\WorkBuddy\2026-08-04-21-37-33\caishuixitong\start8001.bat`

- 窗口会**一直开着**（这是设计，关掉窗口 = 停服务）；
- 窗口里应出现 `Uvicorn running on http://127.0.0.1:8001`；
- 浏览器访问 **`http://127.0.0.1:8001`**（本机 `localhost` 优先解析到 IPv6 `::1`，
  而服务只监听 IPv4，建议直接用 `127.0.0.1`）。

## 七、遗留提示

- 该 bat **没有端口占用检测**：若服务已在运行，重复双击会报 `address already in use`。
  建议后续加「端口已监听则直接打开浏览器」的分支（本轮未做，未扩范围）。
- 本机 `http_proxy` 存在（会话级 `127.0.0.1:22805`）。浏览器若配置了系统代理，
  访问 `127.0.0.1` 可能被代理拦截；诊断时务必用 `curl --noproxy '*'`。
