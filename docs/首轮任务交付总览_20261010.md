## 5. 建议的第一个开发任务

### 建议：**P0-A 规则/法规/报告三版本命中留痕闭环**

**三条硬理由**

1. **它是目标 P0 与 P1 的交汇点**：指令 3.5 要求"每个风险必须可解释、可追溯、可查看计算过程和原始数据来源"；指令 3.8 要求"规则版本、法规版本、报告版本留痕"。**现状缺的正是"命中时的规则版本"**。
2. **它是已取证的现状真缺口**：现有 finding 带 `trace_id` / Provenance / 法规版本 / 报告版本，但**规则版本未随 finding 落盘**；`config/legal_versions.json` 只管法规，规则自身无版本。规则一旦修改，无法回答"这条历史结论当时按哪版规则算的"。
3. **零破坏、可测、符合"增量"**：纯新增数据表 + 字段 + 出口，不改判定逻辑、不改技术栈、不删既有。判定结果应零扰动（用 `scripts/run_companies.py 1` + 产物 diff 证明）。

**切片范围（一个垂直切片）**

1. 新增 `config/rule_versions.json`（唯一权威）：每条 RL/VR 的 `version` + `effective_from` + `changed_note`；**新增同类对象 = 加一行**。
2. 新增 `engine/rule_versions.py`：`version_of(rule_id)` / `stamp(finding)` / `snapshot()`。
3. 在 `_rule_finding` 与红线 finding 构造处**打版本戳**（`rule_version` + `rule_set_version`）。
4. 报告载荷与证据链暴露"本次分析所用规则集版本 + 逐条命中规则版本"。
5. `engine/audit_trail.py` 记录分析事件时带 `rule_set_version`。
6. 测试 `tests/test_rule_version_trace.py`：正例（可反查）/ 负例（未知规则 ⇒ 明确"未登记"，不得默认版本）/ 反向验证（改坏版本表 ⇒ 变红）。
7. 门禁 `check_rule_version_coverage`：每条例出规则必须登记版本，未登记 ⇒ ERROR。

**验收**：`pytest` 全绿；`tools/audit_consistency.py` ERROR 0；`tools/verify_release.py` 通过；`run_companies.py 1` 与改前产物 diff **风险结论零差异**（仅新增版本字段）；反向验证变红；报告页面上**可见**规则集版本与所引规则版本。

**备选**：`P1-A` `/api/v1` 别名路由层（满足"统一前缀 + 向后兼容"，风险最低但收益偏形式）；`P1-B` 权限点表（真实缺口，需先确认多用户场景）。
