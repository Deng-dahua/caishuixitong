## 2. 核心实现说明

### 2.1 数据库变更：走**既有 migration 底座**（★ 关键决策）

**★ 我上一轮文档中的错误已纠正**：初版《统一开发基线》写「建议引入 Alembic」，但 `engine/audit_trail.py` 的模块 docstring **早有明确裁定**——

> 「不引入 alembic：§6 要求'变更走 migration'，而换栈式引入 alembic 与'不擅自更换技术栈'冲突，故用『**幂等建表 + 幂等加列**』实现同一目的」

且任务约束第 1 条即「沿用现有技术栈」⇒ 引入 Alembic 会新增 `requirements.lock` 中不存在的依赖。**故 P0-1 沿用同一模式**（`project_store.ensure_schema()` 是那个模式的**第二个实例**，不是另立一套）：

```python
CREATE TABLE IF NOT EXISTS projects (...);          # 表不存在才建
cols = {c["name"] for c in inspect(conn).get_columns(tbl)}
if "新列" not in cols: ALTER TABLE tbl ADD COLUMN ...  # 新列一律 ADD COLUMN（SQLite 安全）
CREATE INDEX IF NOT EXISTS ...;                     # 索引缺失才建
```

**满足任务要求「数据库变更必须通过 migration」**：不手工改库、不绕过该函数；新增同类对象 = **只加一行**。

### 2.2 两表设计

| 表 | 列数 | 要点 |
|---|---|---|
| `projects` | 16 | `company_id` = **租户边界**（沿用现有账套口径，**不引入新租户表**）；`status` 默认 `draft`；`tax_scopes` 存 JSON 数组（读时解析为 list）；`code` 自动生成 `PJ-YYYYMMDD-####` |
| `project_members` | 6 | 唯一索引 `(project_id, user_id)` ⇒ **同人重复加入是幂等的**（视为角色变更而非报错） |

### 2.3 状态机（6 态，★ 唯一权威）

```
draft 草稿 → uploading 资料上传中 → analyzing 分析中 → reviewing 待复核 → reported 已报告 → archived 已归档
```
- **允许有限回退**：`analyzing → uploading`（补资料）、`reviewing → analyzing`（重跑）、`reported → reviewing`（复核后回退）
- `archived` 为**终态**，不可迁出（要复检须新建项目）
- **非法迁移 ⇒ 400**，并回显"允许迁移到：…"，**不静默接受**

> 任务书未规定迁移规则，此为本实现按业务合理性定义并**显式声明在 `STATUS_FLOW`**（新增一个状态只改一处）。

### 2.4 权限模型（三层，★ 单一实现 `_visible_sql` / `_can_write`）

| 层 | 规则 |
|---|---|
| **① 租户隔离** | `project.company_id` 必须 ∈ `session.allowed_company_ids`（admin 恒真）；**跨租户返回 404**（不是 403）⇒ **不泄露对象是否存在** |
| **② 可见** | admin ∨ 同租户（同租户内团队协作） |
| **③ 可写** | admin ∨ `owner` ∨ 成员且角色 ∈ `{owner, reviewer, member}`；**同租户非成员 = 只读**（不得因"同公司"就拿到写权限） |

**额外一层**：既有安全中间件（`security_web.enforce_request_security`）会从请求体的 `company_id` 收集候选账套并校验 `can_access_company` ⇒ **跨租户创建在中间件层即被 403 拦截**（与 Service 层形成双层防护）。

### 2.5 审计：复用既有唯一权威

- **唯一权威** = `engine/audit_trail.py`。`ACTIONS` **末尾**追加 4 个动作（既有顺序不变）：`project.create` / `project.update` / `project.delete` / `project.member_change`
- 同时补 `ACTION_CN` 中文名（面向界面的动作名**不得出现英文码**）
- Service 层 `_audit()` 是**薄转发**，且**不放 `try/except: pass`** —— 该函数自身已保证"不抛、不静默"，外层再吞一次就等于把留痕失败藏起来
- 项目详情的「操作日志」= 按 `target = 项目编号` 读 `audit_logs`（**薄读，不另建日志表**）
- **删除后留痕仍在**（已测）：留痕不随对象删除而消失

### 2.6 API 路径：`/api/v1/projects` 与 T-3 裁定的关系（★ 需说明）

用户曾裁定「`/api/v1` **仅形式要求** ⇒ 不给现有 167 个端点加前缀」（T-3）。本次任务书**明确列出** `/api/v1/projects` 系列路径。二者**不冲突**：

- T-3 约束的是**现有端点**不改前缀（全量迁移需 167 端点 + 4 页面 + 16 JS 维护两套，零收益）；
- 本模块是**新增**端点，挂在 `/api/v1` 下 ⇒ 现有端点**一字未改**，满足「接口变更必须向后兼容」。

### 2.7 前端：沿用原生技术栈

- **无框架、无构建**（与既有 16 个 JS 文件一致）
- **CSRF 不重复实现**：`security.js` 的全局 fetch 拦截器自动附加 `X-CSRF-Token`、401 自动跳登录；`projects.html` 显式引用它（不依赖 `_read_html` 注入）
- **字典不硬编码**：状态/角色中文名一律取后端 `/api/v1/projects/meta`（测试已断言前端**不得**出现硬编码的状态中文名）—— 避免"前端一份、后端一份"的多头维护

### 2.8 `main.py` 零行号漂移（★ 保护既有文档引用）

`main.py` 被多份文档按行号引用（`main.py:673` 类型白名单、`main.py:11622` `_execute_tax_risk_analysis` 等）。为避免"加两行导致全线漂移"，采用项目既有的「**同行内增删**」手法：

```python
# 第 59 行（import）
from file_parser import router as file_parser_router; from projects_api import router as projects_router, page_router as projects_page_router
# 第 631 行（include_router）
app.include_router(file_parser_router); app.include_router(projects_router); app.include_router(projects_page_router)
```

**实测**：`main.py` 行数 **15156 不变**；`main.py:673`/`11622` 内容**仍在原位**。
