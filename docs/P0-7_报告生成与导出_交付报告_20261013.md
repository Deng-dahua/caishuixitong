## 3. ★ 两处**根因**修复（本轮实测发现，非本任务表面需求）

### 3.1 报告二进制落盘的唯一原子写

`runtime_storage` 原有 `atomic_write_text`（文本原子写，fsync + `os.replace` + 失败清理临时文件），
但**没有二进制版本**。报告有 PDF/DOCX/XLSX 三种二进制格式 —— 若各自手写 `mkstemp` + `os.replace`
+ `os.unlink(tmp)`，就会出现 ① 又三份原子替换实现；② 闸门 `check_delete_exits` 逐行抓到
**未声明的删除调用**（实测：第一版就报 ERROR）。

⇒ 抽出 **`atomic_write_bytes()`** 作为**唯一原子实现**，`atomic_write_text` 改为**薄转发**
（写文本行为逐字节不变，已用现有测试与基线自检复核），并把 `atomic_write_bytes`
登记进闸门的**声明出口**（同为 `atomic_write_text` 的同一出口家族）。

### 3.2 报告产物目录跟随数据根

新增 `runtime_storage.report_output_root()`：设了 `APP_DATA_DIR` ⇒ `<APP_DATA_DIR>/reports`；
未设 ⇒ `<project>/output/reports`。**理由与 `offline_reports_root()` 完全一致**
（2026-10-06 事故：隔离实例越界写/删真实产出）。

### 3.3 ★★ 版本台账路径不随 `APP_DATA_DIR`（**实测事故**）

**现象**：本轮第一次冒烟后，**真实项目的** `data/report_versions.jsonl` 从 **1332 行涨到 1337 行**
（多出 `RW-1-…` 的 V136~V140 五行），版本号直接跳到 **V137**。

**根因**：`engine/report_compliance.py` 的台账路径是**模块级常量**
`_ROOT / "data" / "report_versions.jsonl"` —— **写死源码树路径、不随 `APP_DATA_DIR`**。
与 `runtime_storage.offline_reports_root()` 记录的 **2026-10-06 事故同类**（那次是产物目录）。

**处置（两步，均已做）**：
1. **清理污染**：先备份（`data/report_versions.jsonl.bak_before_p07_cleanup_20261014_000953`，486083 字节），
   再**精确移除**这 5 行（按 `change_note` 前缀 + `company_id` + 时间三重条件识别，原子重写），
   1337 → **1332**（与本次冒烟前一致），并逐行断言无残留。
2. **修根因**：改为 `ledger_path()`（**调用时**解析 `APP_DATA_DIR`），规则与
   `offline_reports_root()` 完全一致；验证：隔离实例写入落到临时目录，**真实台账字节不变**
   （前/后均 482772）。

★ 这是**我造成的污染**，如实报告；也正因为它暴露了一个真实的既有缺陷（任何隔离实例
——测试子进程、冒烟脚本、离线渲染——都会污染生产台账），故一并修掉而非只清数据。

### 3.4 ★★ 台账噪声的**两个真正累积源**（顺着 3.3 查出，均已修）

清理后复核发现台账仍有大量行，其中**绝大部分是合成 `company_id`**。

## 4. 核心实现说明

### 4.1 复用清单（**一个都不另造**）

| 章节 | 数据来源（唯一权威） |
|---|---|
| 封面 | `report_compliance.document_meta`（报告名）+ `reports` 表（文书编号/版本） |
| 免责声明 | `report_identity.identity_line()` + `report_compliance`（非执法声明/保密级别/留存/授权） |
| 项目概况 | P0-1 `project_service.get_project` |
| 数据来源 | P0-2 `document_service.list_documents` + P0-3 `extract_store.artifact_counts` + 载荷 `files_count/read_failures` |
| 风险总览 | P0-5/P0-6 `risk_service.stats` |
| 分税种明细 / 重点风险 | P0-5 `rule_executor.collect_from_report` + `risk_scoring` |
| 证据链 | P0-5 同上（按 `finding_seq` 归属） |
| 法规依据 | P0-5 `rule_catalog.get`（**占位值一律标注**） |
| 复核记录 | P0-6 `risk_review.states_of`（状态/批注/处置历史/整改编号） |
| 整改建议 | 发现自带 `suggestion` + P0-6 `risk_review.rectifications` |
| 附件 | P0-2 资料清单 + 本次产出 4 格式文件 + `report_compliance.change_log`（版本历史） |

**编号/时间/落盘/审计**：`engine/numbering`（报告编号由台账 `doc_no` 承担）·
`runtime_storage.now_cst()` · `atomic_write_bytes()` · `audit_trail.record`。

### 4.2 三条硬约束的**机器保证**（不是口头承诺）

| 约束 | 实现 | 判据 |
|---|---|---|
| **必须含免责声明** | `report_render._require_disclaimer()` 三条前置判据：① `disclaimer` 是 dict ② `identity_line` 非空 ③ **存在 `key="disclaimer"` 的章节且正文含 `identity_line`** | 任一不满足 ⇒ **500 + 说明**（不产报告）。★ 第③条是实测补的：字段存在但章节被裁掉时，用户拿到的报告里就**没有**免责声明 |
| **必须含人工复核标识** | 水印文字含复核状态（**未复核显式写出**）+ 每页页眉/页脚 + 下载响应头 `X-Review-Status` | `reviewed=None` ⇒ **按实际处置记录推断**（有任一处置记录才算已复核），**不得默认"已复核"** |
| **水印生效** | 4 格式**真嵌入**：PDF 逐页叠加（复用 `document_watermark`）、DOCX/XLSX 页眉、HTML CSS 层 | 渲染回执 `mode` 一律 `embedded`；格式→方式表 `WATERMARK_METHOD` 为唯一权威 |

### 4.3 文档模型 = 组装的唯一契约

组装层产出**结构化文档**（`sections[].blocks[]`，5 种块类型：`paragraph`/`kv`/`table`/`list`/`note`），
渲染层只认这 5 种 ⇒ 4 个渲染器**互不知道业务语义**，新增格式不影响组装层。

### 4.4 被裁章节**如实登记**（不静默省略）

视图裁剪章节时，① `reports.omitted_sections` 登记 ② 报告内追加「本视图未包含的章节」小节
并写明"改用全景视图重新生成" ③ 生成回执带 `omitted_sections`。
闸门断言：`保留 ∩ 未含 = ∅` 且 `保留 ∪ 未含 = 全 12 章节`（**不重不漏**）。

## 6. 未完成 / 风险

| # | 项 | 说明 |
|---|---|---|
| 1 | **报告文件无生命周期管理** | `output/reports/<cid>/` 只增不减；无"清理旧版本/保留 N 份"策略（每个视图×格式一份，长期会堆积） |
| 2 | **下载不校验文件完整性** | 只判"存在"，不比对登记的大小/哈希 ⇒ 手工改过的文件仍会被当作原件下发 |
| 3 | **PDF 中文字体为 reportlab 内置 CID 字体** | 排版与 Word/Excel 观感不同；若要统一字体需引入 TTF 并接受体积/许可问题 |
| 4 | **XLSX 为"每章节一张工作表"** | 未做跨表公式/透视；管理层摘要视图的可视化程度有限 |
| 5 | **HTML 预览为 iframe 直连下载 URL** | 未做沙箱隔离（同源、内容由本系统生成，风险低；但与其他页面共享 cookie） |
| 6 | **报告内容不含"复核批注全文"** | 复核记录节只取**最近一条**批注（避免报告膨胀）；全文需在 `/risks` 页看 |
| 7 | **未接入既有报告链的"多版本渲染"** | 既有 `report_pipeline.render_variants_from()` 产出 V1.4 版式 HTML；本模块是新链路，**两条并存**（建议后续裁定是否收敛） |
| 8 | **`reports` 表与台账的一致性只做单侧校验** | `get()` 校验"登记行能否在台账找到"；反向（台账有、登记表无）未做巡检 |
