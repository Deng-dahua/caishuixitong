## 一、结论（先回答两个问题）

### 1. 是否可用？

**可用，但有三条明确的使用边界**（不是"完美可用"，也不掩盖限制）。

| 维度 | 结论 | 依据 |
|---|---|---|
| 能跑通完整业务闭环 | **是** | 端到端实测：登录→建账套→建项目→传资料(201)→解析(200)→查覆盖率(200，行 2/字段 12)→生成报告(4 格式真渲染) |
| 分析结论是否有据可查 | **是**，且**无依据的会自己降级** | 无依据项（`legal_provisions_n=0`）自动降级为「待核线索」（等级封顶「待核验」+ 结论分级 L2），与有依据项分列 |
| 导出件是否有防伪 | **是** | 主页面导出改走服务端渲染（`report_render`，水印**真嵌入**、带文档号/版本/复核标识、写审计留痕） |
| 回归测试 | **20 failed / 2459 passed / 5 skipped**（基线 30 failed / 2314 passed） | 20 项失败**逐项比对为基线已有**（附录 A），本轮**无新增失败**；失败数 **-10**、通过数 **+145** |
| 一致性审计 | **ERROR 15 / WARN 25**（基线 14/22） | +1 ERROR 为闸门判据过期（已按新口径改写）；其余 14 项为既有产物级 `child_items` 问题（Backlog B-05） |
| 十二大质量机制 | **12/12 通过**（附实测数据） | `scripts/_verify_mechanisms.py` → `_audit_20261018/mechanisms.json` |

**三条使用边界（必须让使用者知道）**：

1. **单实例部署**。SQLite + WAL，同一库只允许一个服务进程；
   多实例并发写会互相争锁（Backlog B-04）。
2. **大账套有解析上限**。核心明细表（序时账/银行流水/发票/存货/科目余额）上限
   **5,000 行**；超限会**截断并给出可见回执**（"共 X 行，本次读入前 5,000 行，超出部分未参与分析"）。
   已在 5 万行文件上实测：读入 4,999 行、回执可见、耗时 24 秒。
3. **外部工商核验未对接**。天眼查/企查查 API 未接入，系统按"外部核验不可得"走中性口径
   （不臆断、不降级为风险），详见 Backlog B-01。

### 2. 能支撑多少规模稽查？

**按"项目"计，可支撑中小型稽查机构的日常项目量；按"单项目数据量"计，单份明细表 5,000 行上限是硬约束。**

| 规模维度 | 实测/可支撑 | 说明 |
|---|---|---|
| 单项目资料份数 | 未量化实测 | 未做"单项目 N 份资料"的压测，不敢给数字 |
| 单份明细表行数 | **5,000 行**（上限，超限有回执） | 5 万行实测：读 4,999 行、24 秒、峰值内存 10.6 MB |
| 科目余额表 | **5,000 行**（本轮从 2,999 修正到 5,000） | 见第二章"实测发现的额外缺陷"③ |
| 法规库规模 | **7,692 条**（税务核心 1,105 / 涉税相关 1,639 / 背景法 4,948） | 分层披露，**不得只报总数** |
| 法规库查询 | **0.13 秒**（现测） | 曾 3,532 ms，已优化 |
| 规则规模 | **127 条红线** + 检测器实现层 | 分层计数唯一权威 `rule_versions.layer_semantics`（禁把实现层计入规则数） |
| 并发用户 | 未量化实测 | 只验证过 5 角色串行流程与并发写 503 语义，未做 N 并发压测 |

> **不做规模承诺的理由**：并发与"单项目资料份数"两项没有实测数据。
> 按本项目铁律，**未量化就写"未量化"**，不用"可支撑百人团队"这类估算顶替。

## 二、三大闭环核对

### 闭环① 业务目标闭环

目标链：**上传资料 → 单项/多项交叉分析 → 匹配现行法规 → 发现冲突 → 风险定级 → 输出证据报告**

| 环节 | 状态 | 本轮实测证据 |
|---|---|---|
| 上传资料 | ✅ | 上传 201；分类走 `document_categories.json`（本轮补登 `trial_balance`/`journal`/`general_ledger`，此前账簿族判不出大类） |
| 解析与标准化 | ✅（本轮大幅修复） | 报表：资产负债表/利润表**真取到字段**（横向双栏不再金额错配）；申报表：真实增值税 PDF 从 **0 字段 → 15 字段**，数值与 PDF 一致 |
| 单项/多项交叉分析 | ✅ | 12 个域；上传报表勾稽（`cross_check`）**本轮接入分析**（此前算了不读） |
| 匹配现行法规 | ✅ | 引用 252 处，**引用可定位 100%**、**条号级可核对 214/214=100%**、仅到法名 38 处（如实披露） |
| 发现冲突 | ✅ | 127 条红线；**无法规依据的自动降级为线索**（不再与有依据项同列） |
| 风险定级 | ✅ | 等级词表唯一权威 `risk_levels.LEGAL_LEVELS`；★ 本轮修正一处：把展示名「涉嫌风险」当结构等级会**被封印静默丢弃** |
| 输出证据报告 | ✅ | 4 视图 × 4 格式；空章节整章剔除并说明原因；行业模板口径**如实声明**；导出走服务端（水印真嵌入） |

### ★ 实测发现的额外真缺陷（不在原差距清单内，本轮一并修复）

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| ① | `parse_enhance.safe_nrows()` 在 `worksheet.max_row is None` 时返回 **0** | 无 worksheet dimension 的 xlsx（`write_only` 生成、部分第三方导出）被当成"0 行空表" ⇒ **整份账套静默丢光**（5 万行实测 `rows_read=0`） | dimension 拿不到就走**有界实测扫描**（数到上限+1 为止） |
| ② | `bank_statement.keywords` 混入「记账日期/凭证号/发生额」等**账簿通用词** | 标准序时账被判成**银行流水**（7 分胜出）⇒ 整份账簿进错域，账务域反而无数据 | 新增 `require_any`：必须命中"只有银行流水才有"的信号（对方户名/账号/流水号/柜员号…） |
| ③ | `_parse_trial_balance_sheet` 用 `min(nrows, 3000)` | 而 `ROW_CAPS[5000]` 明写"核心明细表（含**科目余额**）" ⇒ 5,000 行科目余额表**静默只读 2,999 行**（少 40%） | 改 5000 + **行为断言**（★ "值登记过" ≠ "用对了值"，`check_row_cap_manifest` 抓不到这类） |
| ④ | 借贷六列缺英文键别名 | `open_debit`/`current_debit`/`close_debit` 未登记 ⇒ 期初/本期四列**永远取不到**（而科目余额表取数恰恰依赖本期发生额） | 字典补 8 个别名 |
| ⑤ | `trial_balance`/`journal`/`general_ledger` 未登记业务大类 | 账簿族类型判不出大类（落 `other`） | `document_categories.json` 补 3 行 |
| ⑥ | 项目 `taxpayer_id` 缺失被判"必须 18 位" | 与 API schema"不硬性阻断缺项"直接冲突，内部调用无法建项目 | 改为"填了才校验格式"；空税号不参与去重 |
