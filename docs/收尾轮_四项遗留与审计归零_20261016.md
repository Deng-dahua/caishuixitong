## 三、顺出的真缺陷

### ★★ `provision_id` 撞号 60 处（条款级关联的主键不唯一）
1. 「第X条**之N**」只取 X 号（刑法 53 条）⇒「第十七条」与「第十七条之一」同 ID；
2. **同一部法在库里有 2 个 `law` 名**（15 个短码，其中 **14 个只差一个空格**）⇒ 同一条文存两份。
修法：ID 加**子定位后缀**（「之N」⇒ `-Z{N}`、「第N款」⇒ `-K{N}`、「附件N」⇒ `{码}-ATT{N}-{X:03d}`，
既有 `{码}-{X:03d}` 格式**未变**，`CIT-LAW-018` 实测一致、映射零回归）；
`_storage_law()` 把库内 `law` **收敛到登记名**；`_dedupe_library()` 按 `(law, article)` 去重。

### ★ 三类「多头维护」收敛
1. 两个录入脚本**法名口径不同** ⇒ 每次 +17 条、下轮又去重（来回振荡）⇒ 统一 `_storage_law`
2. 短码表**重复登记 3 组**（文号型 vs 主题型）⇒ 法名→短码映射取决于**表行序**（不稳定）
   ⇒ `scripts/_merge_duplicate_law_codes.py` 合并 + 台账 `merged_codes`
3. 覆盖率现算**两套实现**（录入脚本 + 闸门）⇒ 收敛为 `engine/legal_coverage.py`

### ★ 两个判据缺陷（按铁律：误报改判据，不改对的文档）
1. **复合引用漏算**：`split_citation` 对「《增值税法》第二十八条**及**《增值税法实施条例》
   第三十九条」只取首部且**法名/条号错配**（增值税法只有 38 条）⇒ 新增
   `split_citations()` 逐处计入（旧签名不变）⇒ 覆盖率 → **100%**
2. **材料「已有」判据过粗**：`material_names.canonical` 把「成本明细账」与「应付账款明细」
   都归成「科目余额表」⇒ 同项里前者=已有、后者=**尚未取得**时，误判"已有又要补"
   ⇒ 改为**名称级严格匹配 + 类别级仅当该类别下全部来源都已有时**

### ★ 报告文本的两处语义问题
- **「这一步没有数据」被写成「看到的事实」**：`_OBS_META_GAP_PREFIX` 缺「因缺少资料」
  「本环节未产出对题读数」⇒ 这两句被判成 `fact`，报告出现「看到因缺少资料…未取得本环节数据」
  （实测 18+6 处）⇒ 补全前缀，缺口改由句尾缺口汇总陈述
- **自相矛盾措辞**：「第3步从上述比对结果**（本轮未提供）**中判断…」——"从某项中判断"
  与"该项未提供"冲突 ⇒ **相对指代**（上述/前述/该环节…）不再做「（本轮未提供）」标注

### ★ 个税口径（被新检测器暴露的真缺陷）
- `_TAX_BASE_NATURE["个人所得税"]` 写死 `"wage"` ⇒ 股息红利（基数为利润分配）被判"基数不符"；
- **「低于年度基本减除费用 ⇒ 0 影响」被套用到股息红利**（分红按次计税、**无**减除费用）
  ⇒ 报告写 `amount=0.0 / 无实际个税影响`，**漏计 20% 全额**。
修法：要求值改**可接受性质集合**（成员判据）；减除费用分支**只对综合所得**适用；
新增数据表 `_PIT_RATE_BY_INCOME`（股息红利/财产转让/偶然所得 20%）+ `infer_pit_income()`。
实测：分红个税 0 → **8,038.31（20%）**；工资<6万仍 0；工资差额算增值税仍**不估**（D12 保住）。
