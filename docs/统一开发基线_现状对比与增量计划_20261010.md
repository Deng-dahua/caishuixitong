## 0. 执行摘要

| 项 | 结论 |
|---|---|
| 技术栈 | **Python 3.13 + FastAPI + SQLAlchemy + SQLite**（与目标设计的"FastAPI"分支一致，非 Java 分支） |
| 前端 | **原生 HTML/CSS/JS**（4 页面 + 17 个 JS 模块），**无 Vue/React、无构建工具** |
| 现状成熟度 | 已远超目标设计 P0/P1：规则主体 **176** 条（红线 91 + 已验证规则 85）、引擎模块 188 个、测试文件 90 个、`pytest` 1712 passed |

| 建议第一个任务 | **P0-A：规则/法规/报告三版本命中留痕闭环**（可追溯性基线，纯增量、零破坏、可测） |

### 1.12 主要风险 / 技术债 / 重复实现 / 冲突设计

**技术债**

1. `tax_risk.py` **645 KB / 11,322 行**单体（含报告渲染 4 出口 + 10 路由），是最大的结构债。
2. `data/` 目录混入大量过程垃圾（`_*.txt`/`_*.log`/`_*.json` 约 40 项）+ 多个 `_bak` 包。
3. `main.py` 15,000+ 行（157 路由），前端为单页巨型 `index.html`。
4. 无容器化，部署依赖 Windows DPAPI（非 Windows 需进程管理器提供主密钥）。

**重复实现风险（已被闸门管控）**

- `tools/audit_consistency.py::check_duplicate_definitions` 监控跨模块同名函数，当前 27 组已逐组裁定并登记理由；`_DIVERGENCE_OK` 升级为带理由裁定表。
- 数值解析已收敛 `engine/numparse.py`；行业判定收敛 `industry_resolver.py`；期间键收敛 `findingkit.normalize_month`。

### 2.3 冲突项（列出对比表 + 推荐方案）

| # | 冲突 | 目标设计 | **现状（既有）** | 推荐 | 理由 |
|---|---|---|---|---|---|
| C1 | 数据库 | PostgreSQL / MySQL | **SQLite ×2**（WAL + 外键 + 索引） | **保留 SQLite** | 铁律"不擅自更换技术栈/数据库"；单机私有化部署定位下 SQLite 已足够；迁移成本高且无收益证据 |
| C2 | 前端 | Vue3+Element Plus 或 React+AntD | **原生 HTML/JS**（无构建） | **保留原生** | 铁律；90 个测试 + 前后端对齐审计绑定现有结构；引入框架＝重写 |
| C3 | 队列/缓存 | RabbitMQ / Kafka / Redis | **无**（进程内缓存 + 后台任务） | **保留**，P2 可选 Redis | 现状并发量下无必要；引入运维复杂度 |
| C4 | 对象存储 | MinIO / S3 / OSS | **本地 `data/uploads/`** | **保留本地** | 私有化"数据不出域"正好要求本地 |
| C5 | 规则引擎载体 | YAML/JSON/DSL 配置 | **Python 模块 + JSON 数据表** | **保留现有范式** | 见 §3.1：条数被 91 处文档/闸门/测试绑定；YAML 化会破坏"单一权威 + 闸门自证"体系；参数化意图改为落在集中式数据表 |
| C6 | 风险评分公式 | `基础严重度×置信度×金额影响×频次`，80/50 分档 | `phase4_synthesis`：`Σ分值/(发现数×10)×100×(1+交叉验证命中×0.15)`，5 档 | **保留现状** | 现有已通过 1712 项测试并与报告链绑定；分段与阈值差异需专项评估后再议 |
| C7 | 等级体系 | 高风险/中风险/低风险 3 档 | 事项级 **6 档**（极高/高/中/低/**待核验**/信息，`risk_levels.py`）+ 报告级 5 档 | **保留现状** | "待核验"是**证据状态**非风险档，是既有治理要点（防止同事项跨章节等级不一致） |
| C8 | **报告脱敏** | "敏感字段脱敏：身份证号、银行账号、手机号" | **报告不做脱敏** | **不采用该条**（以铁律为准） | 本项目既定铁律：**对外版报告一律不脱敏**——脱敏会破坏金额与主体的一致性，报告仅在企业内部与委托范围内流转。脱敏仅可考虑用于**日志/接口响应/前端展示**，不得用于报告正文。 |
| C9 | 水印 | "文件下载加水印" | 草稿带水印 HTML；正式报告无水印；报告内含人工复核标识 | **保留现状** | 与"正式报告交付"语义一致；如需可加"接收对象+时间"水印（P2） |
| C10 | API 前缀 | 统一 `/api/v1` | 7 种扁平前缀，无版本段 | **增量新增 v1 别名层**（不改现有端点） | 满足"统一前缀 + 向后兼容"；直接重命名会打断 167 端点与前端 |
| C11 | 数据模型 | 19 张表（users/projects/documents/analysis_jobs/risk_findings/...） | 45 张表，但项目/文档/作业/发现/报告以 **JSON/JSONL 落盘** | **保留混合模式**，按需补表 | 业务表已覆盖主体/交易/申报；落盘 JSON 承载不定形产物更灵活；强行表化会破坏现有链路 |

| C13 | AI 作用 | AI 用于 OCR/字段映射/异常检测/文本分类/报告摘要/法规匹配 | 仅 LLM 措辞重写（默认关闭） | **保留保守策略**，按需扩展 | 核心判断 100% 靠规则与统计，保证可解释可审计；与目标"AI 辅助不替代规则"一致 |

### 2.5 哪个更好（逐项结论）

- **规则治理**：现状**明显优于**目标设计——目标只给"规则 + 阈值参数化"，现状另有"归属唯一权威 + 冗余裁定 + 覆盖率三形态 + 反向验证闸门 + 要件/反证结构"，可防止"命中即结论"的退化。**结论：以现状为准，目标设计降级为"候选输入"。**
- **可追溯性**：现状在**证据链/Provenance/三性校验**上更强，但**规则版本留痕弱于**目标（目标明确要求"历史分析结果要记录当时命中的规则版本"）。**结论：这是本次最值得补的差距。**
- **脱敏**：目标更"教科书正确"，但与**业务事实**（报告须金额与主体一一对应、委托范围内流转）冲突。**结论：以铁律为准。**

## 6. 建议的第一个开发任务

### 建议：**P0-A 规则/法规/报告三版本命中留痕闭环**

**为什么是它（3 条硬理由）**

1. **它是目标 P0 与 P1 的交汇点**：目标 P0 要求"每个风险必须可解释、可追溯"；目标 P1 要求"规则版本管理"；你的候选清单第五节也明确写着"**历史分析结果要记录当时命中的规则版本**"。
2. **它是现状真实缺口**（已取证）：现有 finding 带 `trace_id`/`Provenance`/法规版本/报告版本，但**规则版本未随 finding 落盘**；`config/legal_versions.json` 只管法规，规则自身无版本。规则一旦修改，无法回答"这条历史结论当时是按哪版规则算的"。
3. **零破坏、可测、符合"增量"**：纯新增数据表 + 字段 + 出口，不改现有判定逻辑，不改技术栈，不删任何既有。判定结果应零扰动（可用 `run_companies.py 1` 与产物 diff 证明）。

**切片范围（一个垂直切片）**

1. 新增 `config/rule_versions.json`（唯一权威数据表）：每条 RL/VR 的 `version` + `effective_from` + `changed_note`；**新增同类对象 = 加一行**。
2. 新增 `engine/rule_versions.py`：`version_of(rule_id)`、`stamp(finding)`、`snapshot()`。
3. 在 `_rule_finding` / 红线 finding 构造处**打版本戳**（`rule_version` + `rule_set_version`）。
4. 报告载荷与证据链暴露"本次分析所用规则集版本 + 逐条命中规则版本"。
5. `engine/audit_trail.py` 记录分析事件时带 `rule_set_version`。
6. 测试 `tests/test_rule_version_trace.py`：正例（可反查）/ 负例（未知规则 ⇒ 明确"未登记"，不得默认版本）/ 反向验证（改坏版本表 ⇒ 变红）。
7. 门禁：新增 `check_rule_version_coverage`（每条例出规则必须登记版本，未登记 ⇒ ERROR）。

**验收（对齐你的 §8）**

- `pytest tests/ -q` 全绿；`tools/audit_consistency.py` ERROR 0；`tools/verify_release.py` 通过
- `scripts/run_companies.py 1` 与改前产物 diff：**风险结论零差异**（仅新增版本字段）
- 反向验证：故意改坏版本表 ⇒ 门禁变红（证明判据非假）
- 结果级验收：报告页面上**可见**规则集版本与所引规则版本

**需要你确认的 2 件事**

1. 版本号方案：用日期式 `2026.10.1`（每次规则变更递增）还是语义式 `1.0.0`？
2. 是否要求"改规则必须同步改版本"（即把版本校验做成阻断式门禁）？

**备选任务**（若你更想先补目标设计的 P0 形式项）

- **备选 1**：P1-A `/api/v1` 别名路由层（满足"统一前缀 + 向后兼容"，风险最低，但收益偏形式）
- **备选 2**：P1-B 权限点表（真实缺口，但需先确认多用户场景是否真实存在）
