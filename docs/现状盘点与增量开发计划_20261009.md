## 1. 技术栈（实测，不是建议）

| 层 | 现状 | 证据 |
|---|---|---|
| 后端 | **Python 3.13 + FastAPI 0.115.14 + Uvicorn 0.34.3** | `requirements.lock`；`.venv` |

| 数据库 | **SQLite**：`data/security.db`（6 表）、`data/accounting.db`（39 表） | 只读查询 `sqlite_master` |
| Migration | **无**（无 alembic/无 migrations 目录），建表用 `CREATE TABLE IF NOT EXISTS` | 见 §0 |
| 前端 | **原生 HTML + JS（无框架、无构建、无 npm）**：4 个 HTML + 16 个 JS 模块，合计 27,360 行 | `static/`；`index.html` 引入清单 |
| 异步/队列 | **无线程池外的队列**：分析跑在 `threading` 线程，进度靠 `GET /analyze-status/{task_id}` 轮询；`_analysis_tasks` 为内存字典 | `main.py`；`engine/analysis_jobs.py`（JSONL 台账） |
| 缓存 | **无 Redis**：内存 LRU 30 + `data/cache/*.json`（原子写） | `main.py:112-131`；`runtime_storage` |
| 对象存储 | **无**：本地 `data/uploads/`（受 `APP_DATA_DIR` 覆盖） | `runtime_storage.DATA_DIR` |
| OCR | **三档降级已接线**：`rapidocr-onnxruntime`（首选，纯 pip）→ `easyocr` → `pytesseract` | `main.py:1635-1668` |
| 报告 | **HTML（主）** + **XLSX**（openpyxl）+ **PDF**（reportlab，走 `/api/tax-risk/report/download`） | `engine/enterprise_report.py`；`engine/manual_inspection_worksheets.py`；`tax_risk.py:1206 _download_pdf` |
| 鉴权 | 会话式：scrypt 密码 + SHA-256 会话摘要（8h、可撤销）+ CSRF + 登录渐进锁定 + 失败留痕 | `security.py`；`security_web.py` |
| 部署 | `start8001.bat`（用户双击，回环地址）+ `start.sh`；**无 Dockerfile / docker-compose** | 根目录 |

> ⚠ 与指令 §3 的偏差：你给的默认栈（Java/Spring 或 FastAPI + Vue3 + PostgreSQL + Redis + MQ + MinIO + Drools）中，
> 本系统实际用的是 **FastAPI + SQLite + 原生 JS + 本地文件系统 + threading**。
> 按 §0/§3「以现有代码为准、不得更换技术栈」，本计划**全部按现有栈做增量**，不做栈替换。

### 20.2 ★ 为什么不直接导入（4 处结构性不兼容）

1. **载体**：本系统规则是 **Python 模块 + JSON 数据表**，不是 YAML；且**红线条数被 91 处文档/闸门/测试绑定**（`check_redline_overlap_ledger`／`_verify_authority_gates`／D1 数字权威…）。直接塞 60 条会全线打红。
2. **变量名不对应数据字典**：清单的 `vat_burden`/`invoice_sales`/`declared_sales` **不是**系统真实键（真实键是 `sal_invs`/`pur_invs`/`vouchers`/`salaries`/`social_security`/`trial_balance`/`tax_declarations`/`bank_txs`）。**必须先映射**，否则取数全为 0（本项目踩过：`float("12,000.00" or 0)` 静默返 0）。映射表见 `config/rulelist_v1.json → var_map`。
3. **阈值载体不同，且本系统反对"每条规则自带阈值"**：清单把阈值放 `params`；本系统的唯一权威是 `industry_benchmark`（行业均值）/`redline_benchmark`（红线基准，含 1 年期 LPR）/`tax_rates` —— 因为"同一阈值多处各写一份"正是本项目反复出事故的根因（多头维护）。**参数化的意图一致，落点不同**：集中登记，不在规则里内联。
4. **规则自带 `score` 会与唯一权威冲突**：清单每条自带 `score: 80` 且用 high/medium/low；本系统事项等级由 `engine/risk_levels.py`（极高/高/中/低/**待核验**/信息，6 档，其中「待核验」是证据状态不参与高低比较）裁定，规则不自带分数。

**已一致、值得肯定的三点**：① 法规依据只写引用不硬编码（系统有 `legal_version` + 失效拦截）；② 规则版本化（`report_compliance` + `data/report_versions.jsonl`）；③ 先小范围上线（与系统"逐条建链路 + 反向验证"一致）。

**另有一条最关键的差异**：本系统红线含「**构成要件 + 反证/正当情形**」结构，一条红线常含 4~6 个要件、要求**逐要件给证据**，且**明令禁止自动定性**（实测 170 项发现 → 26 条红线命中，**可定性 0 / 待补证 26**）。清单的 `condition` 是单条布尔式、命中即产"风险"，导入后会退化成"命中即结论"。
