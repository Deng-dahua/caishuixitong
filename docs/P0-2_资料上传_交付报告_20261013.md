## 2. 核心实现说明

### 2.1 对象存储：**以现有为准 = 本地文件系统**（★ 明确说明）

任务书写「对象存储：MinIO / S3 / OSS（**以现有为准**）」。实测结论：

| 检查 | 结果 |
|---|---|
| `requirements.lock` 是否有 `minio`/`boto3`/`oss2` | **均无** |
| 全仓是否有对象存储 SDK 调用 | **无** |
| 现有存储方式 | **本地磁盘** `data/uploads/<company_id>/`，路径唯一权威 `runtime_storage.company_upload_dir()` |

⇒ **以现有为准 = 本地文件系统**，**不引入对象存储 SDK**（那会新增依赖、并造成"一份资料两个存放地"）。

### 2.2 与既有资料清单的关系（★ 避免"两套清单"）

既有一键分析读的是**内存清单 + 磁盘扫描**（`shared_state._tax_risk_docs`）。若新接口只写新表，就会出现**"传了但分析看不到"**的功能缺口。处理办法：

| 维度 | 做法 |
|---|---|
| 目录 | **同一目录**（复用 `company_upload_dir`） |
| 命名 | **同一规范** `{cid}_{docid}_{原名}`（实测落盘 `1_1_大表.xlsx`） |
| 编号 | **同一编号空间**（复用既有 `main._tax_doc_counter`，避免两套 id 冲突） |
| 登记 | 上传后**桥接登记进既有清单**；删除时**同步移除**（已测） |
| 既有代码 | **一字未改**（既有上传处理器零改动，风险为零） |

### 2.3 分类：**两段薄转发，不新增第二套识别逻辑**（★ 关键设计）

`static/filename_type_map.json` **本来就是**「文件名 → 系统类型码」的单一权威（自带 `_description`/`_methodology`/`_rules_log`，明确写着"编辑此文件即可调整识别规则，无需改代码"）。因此分类做成两段：

```
文件名 ──(filename_type_map.json，既有权威)──▶ 系统类型码（如 bank_statement）
        ──(config/document_categories.json，本轮新增)──▶ 业务大类（银行流水）
```

- **新增一个可识别文件类型 = 两个 JSON 各加一行，不改代码分支**
- 本轮为 `filename_type_map.json` **末尾追加 6 条**（财务报表/账簿/合同/通用发票/通用申报表/工资表）
  ⇒ **追加在末尾**以保持既有优先级不变（已逐条比对：原 13 条**未变、顺序不变**）
- 业务大类 9 档：**财务报表 / 账簿 / 发票 / 申报表 / 银行流水 / 合同 / 薪酬 / 档案 / 其他**
- **未识别 ⇒ 落「其他」并可见**（列表中以红色标签显示）——**不猜测、不静默塞入某一类**

实测 7/7 用例正确（资产负债表→财务报表、银行流水→银行流水、销项发票→发票、增值税申报表→申报表、科目余额表→账簿、采购合同→合同、工资表→薪酬），既有 13 条规则识别结果未变。

### 2.4 查重（★ 口径须明确）

`MD5 + SHA256` 双哈希。**去重范围 = 同一项目**，理由：

- 同一份资料在**不同项目**里是**合法且必要**的（同一企业的不同期间/不同口径复核）⇒ 按公司去重会导致"B 项目传不进去"
- 同时仍检测「**同一公司内其他项目已有同内容文件**」并在响应里提示 `same_content_elsewhere`（既查重、又不阻断合法场景）
- 已实测：同项目重复 ⇒ 跳过并回报 `duplicate_of`；跨项目同内容 ⇒ **上传成功**且带提示

### 2.5 解析状态（5 态 + 迁移约束）

`待解析 pending → 解析中 parsing → 成功 success`，另有 `失败 failed` / `需人工校正 manual`。
迁移表 `PARSE_STATUS_FLOW`（唯一权威）：`success`/`failed` 可回 `pending`（重解析/重试）；**非法迁移 ⇒ 400**（不静默接受）。

### 2.6 断点续传（★ 真正实现，非占位）

| 步骤 | 接口 | 说明 |
|---|---|---|
| 发起 | `POST /api/v1/documents/chunk/init` | 返回 `upload_id` / `chunk_size`(5MB) / `chunks_total` |
| 传片 | `PUT /api/v1/documents/chunk/{uploadId}/{index}` | **幂等**（重复传同片覆盖，不重复计数） |
| 查缺 | `GET /api/v1/documents/chunk/{uploadId}` | 返回 `received` / `missing` ⇒ **续传依据** |
| 合并 | `POST /api/v1/documents/chunk/{uploadId}/complete` | 校验大小 + **MD5**，走**同一套**入库链路 |

- 会话落 `data/upload_sessions/<upload_id>.json`（原子写），分片落同目录子目录
- **单请求上限沿用既有 10MB 不变**；分片路径上限 `RESUMABLE_MAX_SIZE`(200MB)，**该放宽只作用于分片路径且显式声明**
- 前端断点续传：`upload_id` 存 `localStorage`，重新拖入同一文件时自动查缺续传
- 已实测：11MB 文件 3 片、只传 2 片时 `missing=[2]`、重复传 0 片后仍是 `[0,1]`、补齐合并后**大小与 MD5 完全一致**、会话目录已清理

### 2.7 下载水印（★ 诚实优先，不假装）

| 格式 | 处理 | 响应头 |
|---|---|---|
| **PDF** | `pypdf` + `reportlab` **逐页叠加**斜向文字（水印文字：`内部使用 · 用户名 · 时间 · 仅供本次核查（原文件名）`） | `X-Watermark-Mode: embedded` |
| **图片**（jpg/jpeg/png/bmp/tiff） | `Pillow` 叠加斜向文字 | `X-Watermark-Mode: embedded` |
| **其他**（xlsx/docx/csv/txt/xml/ofd/zip…） | **不改动文件内容**（内容级水印不可行）⇒ 返回原件 + 随附水印信息 | `X-Watermark-Mode: sidecar` + `X-Watermark-Text`（URL 编码）+ `X-Watermark-Message` |

- **原件绝不覆盖**（可追溯性铁律）；水印只作用于下载副本
- 前端按 `X-Watermark-Mode` **区分提示**（embedded 说"已嵌入"；sidecar 把说明原样显示）

**★ 本轮修正的真实缺陷**：水印最初用 `Helvetica` 字体 ⇒ **中文被渲染成黑块（■■■■）且不可提取**。改为 reportlab 内置 CJK 字体 `STSong-Light`（PDF）与系统 CJK TrueType（图片，找不到则**降级为 sidecar 并说明**，不渲染方块）。已实测：水印中文可被 `pypdf.extract_text()` 提取到。

### 2.9 修正基线自检的**错误判据**（★ 自我纠错）

`scripts/_verify_baseline_numbers.py` 原断言「`accounting.db` 表数 == 39」。本轮 migration 幂等加了 4 张表（`projects`/`project_members`/`documents`/`document_pages`）⇒ 变成 43，判据报错。

**这不是数据错，是判据错**：`ensure_schema()` 会随功能**合法**增加表 ⇒ 总数**本就会变**；而在干净环境下总数又是 39 ⇒ **同一判据在不同环境结论相反**（与我此前"引入 Alembic"同类错误：把会变的量当常量）。

**已改为**：断言「**必需表齐全**」（列出 18 张必需表，缺一即报错）；表**总数仅作信息输出，不作断言**。反向验证：往必需表清单塞一个不存在的表 ⇒ **必报错**（已实测 exit 1，还原后 exit 0）。

### 2.12 删除出口合规（★ 审计闸门抓到的真违规）

`check_delete_exits`（项目铁律「**删除必须走声明的出口**」）在第一轮审计就报 **2 个 ERROR**：

```
engine/document_service.py: 第 650 行出现未声明的删除调用（所属函数 `chunk_complete`）… shutil.rmtree(cdir, …)
engine/document_service.py: 第 651 行出现未声明的删除调用（所属函数 `chunk_complete`）… os.remove(_session_path(upload_id))
```

**处理（接权威，不是加白名单）**：

| 步骤 | 做法 |
|---|---|
| ① 权威内新增原语 | `runtime_storage.purge_tree(dir_path)` —— **目录级**（`move_to_trash`/`purge_file` 只处理文件）；做法是**逐文件移入回收站**再删空目录，**不物理删除**；任一文件移不动则**如实返回 False**（不谎报） |
| ② 业务出口独立成函数 | `document_service._cleanup_upload_session(upload_id)`，声明范围 = **上传会话临时态**（`data/upload_sessions/<id>/` + `<id>.json`），**明确不含**用户资料/交付物 |
| ③ 登记出口 | `check_delete_exits::_EXITS` 加该出口并写明范围 |
| ④ 原语入权威清单 | `_PRIMITIVES` 加 `purge_tree`；`_PAT` 加 `purge_tree(`（防将来"顺手删一下"） |
| ⑤ 闸门范围修正 | 出口存在性检查原**只扫 `main.py`** ⇒ 新模块的出口会被误判"找不到实现"；已**扩到 `engine/*.py`**（与 `_SCAN` 同范围） |
| ⑥ `_DIVERGENCE_OK` 登记 | `metadata` / `reset_cache` / `table_columns` 三组同名（各模块**自己的**字典/缓存/表，非同一概念） |

⇒ 未使用任何"加白名单绕过"的手法；新增删除能力**只增加了一个原语，且它在唯一权威里**。
