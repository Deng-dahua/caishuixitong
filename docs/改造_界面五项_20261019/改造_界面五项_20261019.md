# 界面五项改造（2026-10-19 第二批）

> 需求来源：用户 5 条口头要求。本文按「**你会看到什么** → 为什么之前做不到 →
> 怎么实现 → 我怎么验的 → 遗留」排列。**不含"我改了什么"式自证**。

## 一、你会看到什么

### ① `/risks`（风险结果与复核）顶栏
**没有【刷新】按钮了。** 切换项目（右上角项目下拉）会自动重新拉取；需要整页重取时按 F5。

### ② `/reports`（报告生成与导出）
**顶栏的【刷新】和报告列表内的【刷新】都删了。** 切页签会按需自动加载
（切「报告列表」自动拉列表、切「版本台账」自动拉台账），换项目触发全量重取。

### ③ 「切换模块时还会显示资料风险分析报告的页面」——**已修**
**真实原因**（先说结论，因为这决定了修法）：不是模块没删掉，而是**报告正文自带整页封面**。

| 层级 | 修前 | 修后 |
|---|---|---|
| 页面主标题 | 📄 报告生成与导出（h1，24px+） | 📄 报告生成与导出 |
| 报告封面标题 | **内部辅助分析工作底稿**（h1，大字号、居中、整页留白） | 同一行文字，但降为**信息卡标题**（15px、左对齐、卡片化） |
| 封面信息 | 报告编号 / 被审企业 / 报告日期 / 资料数量 | **一项未减** |

⇒ 页面上**不再有两个争主次的大标题**，层级变成：页面标题 → 分析报告页签 → 报告信息卡 → 正文。
实测：封面标题字号 **24px+ → 15px**（`evidence/browser_verify.txt`）。

> **为什么不直接删封面**：封面里的报告编号/被审查企业/报告日期/资料数量是"看报告"的
> 必要信息；且导出 PDF 走**同一条渲染链**，删了会连带影响交付物。故选择**降级而非删除**。

**顺带修掉一个误导性报错**：`renderTaxDocReport` 里仍在调 `refreshTaxDocList()`
（资料清单的刷新），但该清单**早在 2026-10-14 就并入 `/documents`** ⇒
`#tda-file-list` 在任何页面都不存在 ⇒ 每次渲染报告都白跑一次
`/api/tax-risk-docs/list` 请求 + 打印一行 `[tax-doc] tda-file-list 元素不存在` 的假错误。
已删除该调用（渲染报告不需要资料清单：报告正文自带「资料数量」字段）。

### ④ `/reports` →「报告列表 / 历史版本」
列表新增：**表头全选框** + **每行勾选框** + **【删除选中（N）】**按钮。

- 不勾选任何行 ⇒ 按钮**不显示**；
- 勾 1 行 ⇒ 按钮出现并显示 `删除选中（1）`；全选 ⇒ 显示本页全部条数；
- 点它 ⇒ 弹确认框（说明"文件进回收站、台账不删"）⇒ 逐条执行并汇总
  `删除完成：成功 N 份，跳过 N 份`，失败**逐条列出原因**（不笼统说"部分失败"）；
- 切页签/换项目 ⇒ **清空勾选**（绝不删"你当前看不到的行"）；
- 删除的是**交付物登记 + 落盘文件**（pdf/docx/xlsx/html，**移入回收站可恢复**）；
  **版本台账不删**（它是 append-only 审计留痕）。

### ⑤ 修改密码 → **搬到了登录页**
打开 `/login`，底部多了一个 **「修改密码 →」**（可折叠）：

- 填 **账号 + 原密码 + 新密码 + 确认** 即可改密，**不需要先登录**；
- 为什么允许未登录改：这个入口**最需要它的场景恰恰是"忘记密码、登不进去"的时候** ——
  强制先登录会让它在最需要时不可用；
- 成功后会提示并把账号填进上方登录框（**不填密码**），你按新密码登录即可；
- 侧边栏的 **「🔑 修改密码」条目已删除**。

> `GET /change-password` 页面**仍然保留**：它是**强制改密**（首次登录
> `must_change_password=true`）的落点，由登录页跳转 —— 那是**已登录态**下的强制动作，
> 与登录页的自助改密是两条不同路径。

## 二、为什么之前做不到（根因链）

### ③ 的根因：报告封面与页面标题"两个 H1"
`tax-doc-analysis.js` 渲染报告时注入 `<div class="cover"><h1>{报告名}</h1>…</div>`
（报告名如「内部辅助分析工作底稿」，来自 `config/report_identity.json` 唯一权威）。
这份封面在**原内页**里是页面的主标题（内页没有别的 h1），但**内嵌到 `/reports`** 后，
就与本页 `<h1>📄 报告生成与导出</h1>` 并存 ⇒ 视觉上像"两个模块叠在一起"。

### ④ 的根因：**系统本来没有"删除报告"能力**
`reports_api.py` 只有 `GET /reports`、`GET /reports/{id}`、`GET .../download`、
`POST /projects/{id}/reports`（生成）—— **没有任何删除端点**，
`engine/report_service.py` 也没有删除函数。
⇒ 需求 ④ 不是"加个按钮"，而是**要新建一条服务端删除能力**。

### ⑤ 的根因：改密入口在登录后
原入口在侧边栏（`/change-password`），需要**已登录**才能进 ——
忘了密码的人进不去，入口形同虚设。

## 三、怎么实现（单一权威）

### ③ 封面降级
`reports.js::_demoteReportCover()`：渲染后给封面加 `rpt-cover-card` 类、
给 `h1` 加 `rpt-cover-demoted` 类，样式在 `reports.html`（作用域限定 `#tda-report-area`）。
**不改 `tax-doc-analysis.js`** —— 那是报告渲染的唯一实现（导出/离线链路共用），
不能为一个页面的观感去动它。

### ④ 服务端删除（新建，含三处登记）
| 层 | 落点 | 关键设计 |
|---|---|---|
| 服务层 | `engine/report_service.delete_reports()` | 逐条处理；文件走 `move_to_trash`（**禁 `os.remove`**）；**版本台账 append-only 保留**；返回 `deleted/skipped/cleared/leftovers` 逐条如实 |
| 端点 | `POST /api/v1/reports/delete` | 权限 `report.generate` + **必须显式 `confirm=true`**（否则 400）；用 POST 而非 `DELETE /reports/{id}`：批量语义 + 确认放请求体更难被误触发 |
| 审计闸门 | `tools/audit_consistency.py::_EXITS` | 登记 `delete_reports` 的清理范围（**新增删除路径不登记即 ERROR**） |
| 权限守护 | `tests/test_write_endpoint_permissions.py` | 登记新写端点的权限点（漏配即红） |
| 前端权限表 | `config/frontend_perms.json` | 登记 `btn-del-reports` |

**顺序很重要**：先移文件、再删登记行。若反过来，中途失败会留下"文件在、登记没了"的
**孤儿文件**（无法再定位）。有文件未清干净 ⇒ **保留登记行**并如实回报，供重试。

### ⑤ 未登录改密（新增端点 + 三条安全护栏）
`POST /api/auth/change-password-public`（登记 `security.is_public_path` 免登录白名单）：

| 护栏 | 为什么必须 |
|---|---|
| ① **复用登录限流**（`login_is_allowed` / `record_login_result`） | 否则它是**绕过登录限流的密码爆破入口**：攻击者拿它反复试原密码，而登录端点那边风平浪静 |
| ② 失败**统一措辞**「账号或原密码不正确」 | 区分"账号不存在"与"原密码错误"会让账号可枚举 |
| ③ 成功后**撤销该用户全部会话** | 由 `change_password_with_old` 内建；改密即踢下线，不给旧会话留窗口 |

凭据强度 = 登录（都要知道原密码）⇒ **不是提权入口**：能通过它的人本来就能登录。

## 四、★ 本轮自查抓出的既有真隐患（不在需求内）

### `page-memory.js` 会把**明文密码写进 localStorage**

**隐患**：该模块的 `change` 事件监听只靠 **id 关键字**（`password|pwd`）跳过，
**不看 `type`**；而 `blur` 分支虽有 `type` 判断，`change` 分支却没有。
⇒ 只要输入框 id 不叫 "password"（例如本需求新增的 `pw-old` / `pw-new`），
**密码就被明文持久化**。既有 `change_password.html` 的三个框侥幸因 id 含 `password` 躲过。

**修法（根因）**：加 `isSensitive(el)` 类型级判据（`type=password/file/hidden` +
`autocomplete` 含 `password`），**三处**都过它：`remember()`（唯一写入点）+ `change` + `blur`。

> 判据由反向验证**校准过一次**：初版只查 `bind()` 里两处 `isSensitive`，
> 结果"删掉 `remember()` 里的守卫"这种注入仍能通过 ⇒ 补上"唯一写入点必须有守卫"。

## 七、遗留（未做，如实登记）

1. **删除报告时"部分文件清不干净"的极端情形**：已设计为"保留登记行 + 如实回报 + 可重试"，
   但**未构造该故障做实测**（需人为造一个无权限/被占用的文件）。
2. **未登录改密的账号锁定策略**：现复用登录限流（5 次失败后按 30s×2^n 退避，上限 900s）。
   是否需要"改密失败单独计数"未评估 —— 现口径与登录共用，属**有意为之**（同一凭据面）。
3. **`/change-password` 页面与登录页改密面板存在两套前端代码**（前者用于强制改密、
   后者用于自助改密）。二者调用不同端点（`/api/auth/change-password` 需登录 vs
   `/api/auth/change-password-public` 免登录），**未合并**（合并会让"强制改密"也走免登录端点，
   反而放宽了已登录态的校验路径）。
4. **报告封面降级只在 `/reports` 生效**：导出 PDF 时封面仍是完整封面（**有意如此** ——
   交付物本就该有封面）。
