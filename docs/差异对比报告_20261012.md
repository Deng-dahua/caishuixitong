## 6. 横切规范对比

### 6.1 API 前缀 `/api/v1`

| 项 | 内容 |
|---|---|
| 目标设计 | `/api/v1` |
| 现有实现 | **无任何版本前缀**；路由分布：`main.py` 149 条（`/api/...`）、`tax_risk.py` 9 条（prefix `/api/tax-risk`）、`tax_rules_api.py` 2 条、`file_parser.py` 7 条 = **167 条** |
| 重复 | 否（现有无版本概念） |
| 冲突 | **★ 是**：加 `/api/v1` 会与现有 167 端点路径冲突 |
| 缺失 | 版本化能力 |
| 哪个更好 | 目标设计在长期演进上更优；现有在**不破坏兼容**上更优 |
| **推荐处理方式** | **合并**：**别名并存**（新增 `/api/v1/*` 转发到现有处理函数，**不替换**现有路径）。理由：替换将打断 167 端点与全部前端调用，且无版本化收益兑现路径。 |

### 6.2 规则引擎形态（YAML/JSON/DSL，规则与代码分离）

| 项 | 内容 |
|---|---|
| 目标设计 | 规则用 YAML/JSON/DSL 表达，与代码分离 |
| 现有实现 | ① **判定逻辑在 Python**（`tax_redlines.py` 91 条 + `verified_rule_engine.py` 85 条 + 检测器层）；② **阈值/参数在 config JSON**（`tax_limits` / `industry_params` / `risk_conditions` 等）；③ **18 个 YAML 交换文件**已生成但 `wired=false` / `enabled=false`（**未接入运行期**）；④ **无规则解释器**（引擎路径无 `yaml.safe_load`） |
| 重复 | 部分（YAML 内容与 Python 规则**同源**，由 `tools/export_rulelist_yaml.py` 生成） |
| 冲突 | **★ 是**：规则的"**要件化 + 反证情形 + 禁止自动定性**"结构（如"构成要件 + 反证"）**无法用纯 YAML 表达**；强行外置会丢失判定语义 |
| 缺失 | 规则 DSL 解释器；YAML → 运行期接线 |
| 哪个更好 | **判定能力现有更强**（要件化/反证/闸门锁）；**可维护性目标更优**（改规则不改代码） |
| **推荐处理方式** | **合并**（渐进式）：① 保留 Python 判定内核作为"**执行器**"；② YAML 作为"**规则载体**"逐层接入（先接**参数类/阈值类**规则——它们天然可外置，再接简单判据）；③ 要件化复杂规则**保留在 Python**，只在 YAML 中登记引用。**不建议一次性全量外置**（会破坏 176 条规则的可追溯性与既有闸门）。 |

### 6.3 风险评分（0-100，高中低三级）

| 项 | 内容 |
|---|---|
| 目标设计 | 0-100 连续分 + 高/中/低三级 |

| 重复 | 否 |
| 冲突 | **★ 是**：① 粒度 6 vs 3（现有更细）；② 现有含**非风险态**（待核验/信息），三级模型无法表达；③ 降为三级会**破坏既有报告与闸门**（`risk_levels.py` 是单一权威，被 `test_risk_levels.py` 等锁定） |
| 缺失 | 0-100 连续分值 |
| 哪个更好 | **现有更好**（合规定性需细粒度；三级不足以表达"资料不足待核"） |
| **推荐处理方式** | **新增**（不替换）：保留 6 级定性作为**结论等级**（唯一权威 `risk_levels.py`）；**新增** `risk_score`（0-100）作为**排序/优先级辅助字段**。理由：分值便于排序与筛选，但**不能替代法律定性**（项目铁律「禁止自动定性」）。**需用户裁定**（待确认 T-2） |

## 8. 冲突项理由详述

### C-1 规则引擎形态（Python vs YAML/DSL）

**为什么不能简单"采用目标设计"**：
1. 现有 91 条红线含**要件化结构**（`indicator_constituents` 前提要件 / `violation_any_of` 任一即违规 / 反证情形），YAML 无法表达"要件组合逻辑"与"序号 1 基"语义；
2. 项目铁律要求「**禁止自动定性**」与「红线**可声明**要件」——纯 DSL 会削弱该约束；
3. 176 条规则已被**多处闸门与文档绑定**（含覆盖率 91/91/0/0），全量外置会一次性打断可追溯链。

**为什么也不能"废弃目标设计"**：目标设计的核心诉求（**改规则不改代码**）对**参数类/阈值类**规则完全成立，且现有 `tax_limits` / `industry_params` 已是 JSON 数据表，与目标同向。

⇒ **合并（渐进接入）** 是唯一同时满足两者的路径。

### C-2 API 前缀

**为什么"采用目标设计"（直接替换）不可行**：167 个端点 + 4 个前端页面 + 17 个 JS 全部指向 `/api/...`；替换是**破坏性变更**，且当前无第二版本并存需求（无外部 API 消费者）。

⇒ **别名并存**：新增 `/api/v1` 前缀转发，零破坏，可渐进迁移。**成本低、可回滚**。

### C-3 风险评分

**为什么不能降为三级**：
1. 现有 `待核验` 是**资料不足态**（合规必需），三级模型无位置安放；
2. `risk_levels.py` 是**单一权威**，被 `test_risk_levels.py` / `test_non_risk_not_flagged.py` 等锁定；降级将连带破坏报告分级与闸门；
3. 项目铁律「**禁止自动定性**」要求"资料不足不结论"——三级会诱导强行归档。

⇒ **新增 0-100 分值**（用于排序/筛选），**不动 6 级定性**（用于结论）。

### C-5 报告导出 Excel

**为什么是"新增"而非"采用目标设计"**：目标只要求"支持 Excel"，未要求格式规范；现有 `openpyxl` 依赖与载荷已就绪，**增量成本低**。

### 9.1 ★ T-5 根因实测（**不是「缺登记」，而是「切分缺陷」**）

**原假设**：47 个未登记法名 ⇒ 补登记 47 行即可。
**实测推翻**：47 中**约 7 个是切分缺陷造成的假缺口**，其余约 40 个才是真实未登记法。

**缺陷定位（代码级，`engine/legal_citation.py`）**：

| # | 缺陷 | 实证 | 位置 |
|---|---|---|---|
| 1 | **范围条文未识别** | `《企业所得税法实施条例》第四十条至第四十五条（各费用扣除限额）` → 法名被切成 `企业所得税法实施条例**第四十条至**` | `_ART_RE`（第 27-31 行）**只支持「第X条、第Y条」，不支持「第X条至第Y条」** |
| 2 | **并列法条被拼进法名** | `《企业所得税法》第四十六条及财税〔2008〕121号（关联方债资比）` → 法名变成 `企业所得税法第四十六条**及财税〔2008〕121号**` | `split_citation` 末段 `if rest: law = law + rest`（把非条文残段一律拼回法名） |
| 3 | **括号文号导致归一失配** | `《股权转让所得个人所得税管理办法（试行）》（国家税务总局公告2014年第67号）` → 法名含文号 ⇒ 与登记名不匹配 ⇒ 假「未登记」 | `norm_law` 未剥离尾部**文号型**括号 |

**量化结果**（只读实测）：

| 类别 | 数量 |
|---|---|
| 含条文残段（缺陷 1/2 造成） | **7** |
| 含括号文号（缺陷 3 造成，需剥离后比对） | 14 |
| 其余疑似真实未登记 | 23 |
| 合计 | **47** |

> **为什么必须先修切分再补登记**：若直接登记 47 行，等于把 `企业所得税法实施条例**第四十条至**` 这类**污染名**固化为"合法法名"——**把噪声写成权威**。这与项目铁律「判据先量化再收窄」冲突。

**实施结果（2026-10-12，提交 `318bef97`）**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 法名残留条文号（全库 204 处） | 6 处 | **0 处** |
| 未登记法名（审计可见） | 47 个 | **39 个** |
| `engine/legal_citation.py` 专项测试 | **0** | **15 项**（含反向验证） |

- 修法：`_ART_RE` 支持范围分隔符「至 ~ ～ - - — －」；条文出现即法名截止在其前；
  新增 `strip_article_from_law()` 兜底；无书名号分支交条文切分。
